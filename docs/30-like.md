# 글 좋아요 설계

> 작성일 2026-10-05 · 담당: 김민서 · 관련 요구사항: C-LIKE-1(글 좋아요)
> 이미 결정된 것을 따른다: `post_like` 복합 PK·`like_count` 미리 저장(03 E-6·E-7), 카운터는 `@Modifying` 쿼리(05 J-2), 읽을 수 없는 글의 좋아요는 안 보임(06 §3), 휴지통·탈퇴 처리(13), 카드에 좋아요 수 표시(10 §2).

## 1. 결정 사항

| # | 안건 | 결정 | 이유 |
|---|---|---|---|
| K-1 | 자기 글 좋아요 | **불가.** 버튼 대신 개수만 표시 | 트렌딩 점수의 재료라서 스스로 점수를 올릴 수 없게 한다 (나민서 SOC-01과 같음, 김민서 원안의 "가능"은 폐기) |

| K-3 | 이메일 인증 전 | **불가** | 인증 안 된 계정을 대량으로 만들어 트렌딩을 조작하는 것을 막는다 (07 "인증 전 쓰기 불가"와 같은 원칙) |

| K-7 | 화면 | 누르는 즉시 반영, 연타는 마지막 상태만 전송, 1만 이상은 `1.2만` | |
| K-8 | 목록 카드 | **수만 표시** (내가 눌렀는지는 표시 안 함) | 목록 SQL 1번 유지 (10 §7) |

| K-10 | 이벤트·알림 | **실제로 바뀐 경우만** 이벤트 발행, 같은 사람·같은 글 알림은 1번 | 알림 피로 방지 (김민서 P-15). 알림 쪽 처리는 강성찬과 협의 |
| K-11 | 공통에서 뺄 것 | 좋아요 누른 사람 목록, 내가 좋아요한 글 목록, 댓글 좋아요 | 개인 확장 |

## 2. 누가 누를 수 있나

| 보는 사람 \ 글 | 남의 읽을 수 있는 발행 글 | 내 글 | 임시글·휴지통 글·볼 수 없는 글·탈퇴 신청한 작성자의 글 |
|---|---|---|---|
| 비회원 | 버튼 표시 → 누르면 로그인 안내 (서버 401) | — | 404 |
| 이메일 인증 전 회원 | 버튼 표시 → 누르면 인증 안내 (서버 403) | 개수만 (서버 403) | 404 |
| 회원 | **누를 수 있음** | 개수만 (서버 403) | 404 |

판정 순서 (서버):
```
① 로그인했나?              아니면 401
② 글을 읽을 수 있나?        06 PostAccessPolicy.canRead + status = PUBLISHED, 아니면 404
③ 이메일 인증을 했나?       아니면 403 EMAIL_NOT_VERIFIED
④ 내 글인가?               맞으면 403 CANNOT_LIKE_OWN_POST
⑤ 요청 횟수                넘으면 429
⑥ 처리 (§4)
```

②를 ③·④보다 먼저 확인해서, 볼 수 없는 글은 다른 이유와 상관없이 항상 404로 응답한다.

## 3. API

```
PUT    /api/posts/{postId}/like     좋아요 상태로
DELETE /api/posts/{postId}/like     취소 상태로
```

| 응답 | 경우 | 본문 |
|---|---|---|
| `200` | 성공. 이미 그 상태여도 200이고 수는 바뀌지 않는다 | `{ "liked": true, "likeCount": 13 }` |
| `401` | 비회원 | — |
| `403` `EMAIL_NOT_VERIFIED` | 이메일 인증 전 | "이메일 인증 후 누를 수 있어요" |
| `403` `CANNOT_LIKE_OWN_POST` | 자기 글 | (화면에는 버튼이 없지만 서버도 막는다) |
| `404` | §2의 볼 수 없는 글 | — |
| `429` | 1분에 60번 초과 | `Retry-After` 헤더 |

**토글(`POST /like`)을 쓰지 않는 이유:** 네트워크 재시도나 더블클릭으로 같은 요청이 두 번 가면 원래대로 돌아간다. 사용자는 눌렀는데 결과는 취소가 된다. 상태 지정 API는 몇 번을 보내도 결과가 같다.

SSR을 쓰는 팀원은 같은 Service를 폼 POST(`_method=PUT`/`DELETE`)로 호출하고 글 상세로 돌아간다.

## 4. 처리와 동시성

```sql
-- 좋아요: 실제로 INSERT된 경우에만 +1
WITH ins AS (
    INSERT INTO post_like (post_id, member_id) VALUES (:postId, :memberId)
    ON CONFLICT DO NOTHING RETURNING post_id
)
UPDATE post SET like_count = like_count + 1 WHERE id IN (SELECT post_id FROM ins);

-- 취소: 실제로 DELETE된 경우에만 -1
WITH del AS (
    DELETE FROM post_like WHERE post_id = :postId AND member_id = :memberId RETURNING post_id
)
UPDATE post SET like_count = like_count - 1 WHERE id IN (SELECT post_id FROM del);
```

- 두 쿼리 모두 문장 하나라서 INSERT/DELETE와 카운터 변경이 함께 되거나 함께 안 된다.
- 응답의 `likeCount`는 같은 트랜잭션에서 `SELECT like_count`로 읽는다 (그 사이 다른 사람이 누른 것까지 반영).
- "실제로 바뀌었는지"(`ins`·`del`에 행이 있었는지)를 Service가 받아서 이벤트 발행 여부를 정한다 (§6).

### 4-1. 보정 배치

매일 새벽, `like_count`가 실제 행 수와 다른 글을 고친다. 정상이라면 0건이어야 하고, 고친 건수가 0이 아니면 경고 로그를 남긴다 (버그 신호).

```sql
WITH real AS (
    SELECT p.id, count(l.post_id) AS n
    FROM post p LEFT JOIN post_like l ON l.post_id = p.id
    GROUP BY p.id
)
UPDATE post p SET like_count = r.n
FROM real r
WHERE p.id = r.id AND p.like_count <> r.n
RETURNING p.id;
```

ShedLock으로 한 서버에서만 실행한다. 글이 많아지면 최근 7일 안에 좋아요가 바뀐 글만 대상으로 줄인다.

### 4-2. 검증 결과 (2026-10-05, PostgreSQL 18, 실제 동시 실행)

| 테스트 | 결과 |
|---|---|
| 같은 사람이 동시에 PUT 20번 | `like_count` 1 = 실제 행 1 |
| 같은 사람이 PUT 20번 + DELETE 20번을 동시에 섞어서 (3회 반복) | 매번 `like_count` = 실제 행 (0, 0, 1) |
| 서로 다른 50명이 같은 글에 동시에 PUT | 50 = 50 |
| 50명이 동시에 DELETE + 다른 8명이 동시에 PUT | 8 = 8 |
| `like_count`를 일부러 999로 틀리게 만든 뒤 보정 배치 | 1건 보정 → 8 = 8 |

| 숫자 표시 | 0~9,999는 쉼표(`1,234`), 1만 이상은 소수 첫째 자리까지 `1.2만` (내림) |

## 6. 남용 방지와 이벤트

| 항목 | 규칙 |
|---|---|
| 요청 횟수 | 사용자당 1분에 60번 (Redis 카운터 `rate:like:{memberId}`). 넘으면 429 |
| 이벤트 | **실제로 행이 생겼을 때만** `PostLiked{postId, likerId, authorId, likedAt}`, **실제로 지워졌을 때만** `PostUnliked{postId, likerId}`. 커밋 후 발행 (`@TransactionalEventListener(AFTER_COMMIT)`). 이미 그 상태였던 요청은 이벤트 없음 |
| 알림 중복 | 같은 사람이 같은 글에 눌렀다 취소하고 다시 눌러도 알림은 1번. 중복 판정은 알림 쪽 책임 (§9 강성찬) |
| 트렌딩 | `post.like_count`를 점수 재료로 쓴다 (32 T-2). `post_like.created_at`은 점수식을 "최근 반응" 방식으로 바꿀 때를 위해 남겨 둔다 |

## 7. 다른 상태와의 관계 (이미 결정된 것 정리)

| 상황 | 좋아요 |
|---|---|
| 글이 비공개·친구 공개로 바뀜 | 지우지 않는다. 글을 볼 수 없는 사람에게는 수·버튼이 함께 안 보인다 (06 V-7) |
| 글이 휴지통에 감 | 보존. 복구하면 그대로 (13 D-3) |
| 글이 완전 삭제됨 | CASCADE로 함께 삭제 (13 D-5) |
| 누른 사람이 탈퇴 신청 (유예 중) | 그대로 (13 §3-2) |
| 누른 사람이 탈퇴 30일 경과 | 해당 글의 `like_count`를 줄이고 행 삭제 (13 §3-3 ③) |
| 글 수정·다시 발행 | 그대로 (05 §8) |

## 9. 공통 완료 기준 (C-LIKE-1)

| # | 기준 |
|---|---|
| 1 | 한 사람이 한 글에 좋아요를 한 번만 남길 수 있고, 같은 요청을 동시에 20번 보내도 1건이다 |
| 2 | 좋아요·취소를 동시에 섞어 보내도 `like_count`가 항상 실제 행 수와 같다 |
| 3 | 같은 요청(`PUT` 또는 `DELETE`)을 여러 번 보내도 결과가 한 번 보낸 것과 같다 |
| 4 | 비회원은 401, 이메일 인증 전은 403, 자기 글은 403, 볼 수 없는 글은 404이고 수는 바뀌지 않는다 |
| 5 | 실제로 상태가 바뀐 요청만 `PostLiked`/`PostUnliked` 이벤트를 만든다 |
| 6 | 1분에 60번을 넘으면 429 |
| 7 | 보정 배치는 정상 상태에서 0건을 고친다 |

| 담당자 | 맞출 것 |

| **강성찬** (알림) | 이벤트 이름과 내용: `PostLiked{postId, likerId, authorId, likedAt}`, `PostUnliked{postId, likerId}`. 같은 사람·같은 글의 좋아요 알림은 1번만 (중복 판정은 알림 쪽). 자기 글은 좋아요가 불가하므로 "본인 행동 알림 제외"는 좋아요에서는 생기지 않는다 |
