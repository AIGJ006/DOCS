# 로그인·로그아웃 설계

> 작성일 2026-10-02 · 관련 요구사항: C-AUTH-1(로그인·로그아웃). 연관: C-AUTH-2(프로필), 블로그 주소(다음 안건)
> 팀 결정: **이메일 가입·로그인 + Google + GitHub.** 로그인 수단이 다르면 이메일이 같아도 **별도 계정**이다.

---

## 1. 결정 사항

| # | 안건 | 결정 |
|---|---|---|
| L-1 | 같은 이메일로 다른 로그인 수단을 쓸 때 | **별도 계정 생성.** 계정 하나 = 로그인 수단 하나. 자동으로 합치지 않고, 계정 연결 기능도 두지 않는다 |
| L-2 | 이메일 인증 | 필수. 인증 전에는 로그인은 되지만 글쓰기·댓글·사진 업로드·좋아요·신고는 막는다 (42 P-6) |
| L-3 | 비밀번호 규칙 | **8~16자, 영문·숫자·특수문자를 각각 1개 이상** |
| L-4 | 비밀번호 재설정 | 공통에 포함. 메일 링크 30분, 한 번만 사용 |
| L-5 | 네이버 로그인 | 이번 범위에서 제외 (`provider` 값만 추가하면 나중에 붙일 수 있음) |
| L-6 | 로그인 유지 | 14일(마지막 활동부터), 세션 쿠키 + Redis 세션(Spring Session) (2026-10-07 회의 Q2·H7) |
| L-7 | 로그인 실패 제한 | 같은 계정 5회 실패 시 15분 잠금, 같은 IP는 1분에 20회 |
| L-8 | 약관 동의 | 이용약관 + 개인정보 처리방침 필수. 동의한 **버전**과 시각을 `member_agreement`에 저장, 버전이 바뀌면 로그인 때 재동의 (2026-10-07 회의 H9·E2, §3-1) |
| L-9 | 메일 발송 | 개발은 Mailpit, 배포 방식은 환경 확인 후 결정 |
| L-10 | 인증 메일 재발송 | **1분에 1번, 하루 10번** |

## 2. 계정과 로그인 수단 (L-1)

| 로그인 수단 | 계정을 구분하는 값 | 예시 |
|---|---|---|
| 이메일 (`LOCAL`) | 소문자로 바꾼 이메일 | `kim755030@naver.com`으로 이메일 가입 → 계정 ① |
| Google (`GOOGLE`) | Google의 고유 사용자 ID (`sub`) | 같은 이메일의 Google 계정으로 로그인 → **계정 ②** (①과 별개) |
| GitHub (`GITHUB`) | GitHub의 고유 사용자 ID (숫자) | 같은 이메일의 GitHub 계정으로 로그인 → **계정 ③** |

- **같은 로그인 수단으로는 계정이 두 개 생기지 않는다.** 같은 이메일로 다시 이메일 가입을 하거나, 같은 Google 계정으로 다시 로그인하면 기존 계정이다. DB의 `UNIQUE(provider, provider_user_id)`가 이것을 보장한다.
- 계정마다 로그인 수단은 하나다(`UNIQUE(member_id)`). 계정 ①에 Google 로그인을 추가로 붙이는 기능은 없다.
- 소셜 계정은 **이메일이 아니라 고유 ID로 식별**한다. 소셜 서비스에서 이메일을 바꿔도 같은 계정으로 로그인된다.

**C-AUTH-1 완료 기준 변경:** "같은 사람이 계정 두 개가 되지 않는다" → **"같은 로그인 수단(같은 이메일 가입, 같은 소셜 계정)으로는 계정이 두 개 생기지 않는다."**

## 3. 이메일 가입

```
[가입] 이메일 · 블로그 주소(이메일로 미리 채움, 한 번 수정 가능) · 비밀번호 · 비밀번호 확인 · 닉네임 + 약관 동의(필수 2개)
  → 계정 생성 (email_verified_at = null)
  → 인증 메일 발송: 링크 24시간 유효, 한 번만 사용
  → 링크 클릭 → email_verified_at 기록 → "인증이 완료됐어요"
  인증 전: 로그인은 되지만 글쓰기·댓글·사진 업로드·좋아요·신고는 403 + "인증 메일 다시 보내기" 안내
```

| 항목 | 규칙 |
|---|---|
| 이메일 형식 | 일반적인 이메일 형식, 최대 254자. 소문자로 바꾸고 앞뒤 공백을 지워 저장 |
| 이미 이메일 가입된 주소 | "이미 가입된 이메일이에요. [로그인] [비밀번호 찾기]" |
| 인증 토큰 | 32바이트 난수를 URL용으로 인코딩. Redis `auth:verify:{토큰}` = memberId, TTL 24시간, 사용하면 삭제 |
| 재발송 | **1분에 1번, 하루 10번** (Redis 카운터 `auth:verify-resend:{memberId}:{yyyyMMdd}`). 새 메일을 보내면 이전 링크는 무효 |
| 만료·사용된 링크 | "링크가 만료됐어요. [인증 메일 다시 보내기]" |
| 약관 | 필수: 이용약관(`TERMS`), 개인정보 처리방침(`PRIVACY`). 가입 트랜잭션이 `member_agreement`에 두 행을 함께 넣는다 (§3-1) |

### 3-1. 약관·처리방침 동의 (2026-10-07 회의 H9·E2)

| 항목 | 규칙 |
|---|---|
| 문서 화면 | 이용약관 `/terms`, 개인정보 처리방침 `/privacy`. 각 문서에 **시행일과 버전**을 적는다. 가입 화면·소셜 가입 마무리 화면·설정 화면에서 링크 |
| 저장 | `member_agreement(member_id, type, version, agreed_at)`. `type`은 `TERMS`·`PRIVACY`·`AI`, 회원·종류마다 한 행(PK `(member_id, type)`) — 다시 동의하면 `version`·`agreed_at`을 바꾼다 |
| 가입 | 이메일 가입(§3)과 소셜 가입 마무리(§5) 모두, 계정을 만드는 트랜잭션에서 `TERMS`·`PRIVACY` 행을 현재 버전으로 함께 넣는다. `AI`는 AI 기능을 처음 쓸 때 따로 받는다(34) |
| 재동의 | 로그인할 때 저장된 `version`이 현재 버전과 다르면 재동의 화면으로 보낸다. 동의하기 전에는 다른 화면으로 넘어가지 않는다 |
| 처리방침 내용 | 수집 항목·보관 기간 등과 함께 "친구에게 최근 활동 시점 표시"(`member.last_active_at`)를 명시한다 |
| 탈퇴 | 30일 뒤 익명 처리할 때도 동의 이력은 지우지 않는다 |

```sql
-- 가입 트랜잭션 안에서 (member INSERT 직후)
INSERT INTO member_agreement (member_id, type, version)
VALUES (:memberId, 'TERMS', :termsVersion),
       (:memberId, 'PRIVACY', :privacyVersion);

-- 로그인 때 재동의가 필요한지
SELECT type, version
FROM member_agreement
WHERE member_id = :memberId
  AND type IN ('TERMS', 'PRIVACY');
```

## 4. 비밀번호

| 항목 | 규칙 |
|---|---|
| 길이 | **8~16자** |
| 조합 | **영문 대소문자 중 1개 이상, 숫자 1개 이상, 특수문자 1개 이상** |
| 쓸 수 있는 문자 | 영문, 숫자, 특수문자 `` ! @ # $ % ^ & * ( ) - _ = + [ ] { } ; : ' " , . < > / ? \ \| ` ~ `` (공백·한글 불가) |
| 금지 | 이메일 `@` 앞부분이 들어간 비밀번호, 흔한 비밀번호 목록(`Password1!`, `Qwer1234!` 등) |
| 저장 | BCrypt (`auth_identity.password_hash`). 원문은 저장·로그 기록하지 않음 |
| 화면 | 입력하는 동안 규칙별 충족 여부를 글자와 ✓로 표시 (색만으로 표시하지 않음) |

> 참고: 16자 상한은 팀 결정이다. 긴 문장형 비밀번호나 비밀번호 관리자가 만든 긴 비밀번호는 쓸 수 없으므로, 안내 문구에 "최대 16자"를 분명히 적는다.

### 4-1. 비밀번호 재설정

```
[비밀번호 찾기] 이메일 입력
  → 화면: 항상 "가입된 이메일이면 안내 메일을 보냈어요" (가입 여부를 화면으로 알 수 없게)
  → 메일 (그 이메일 주인에게만 감):
      이메일 가입 계정이 있으면  → 재설정 링크 (30분, 한 번만 사용)
      그 이메일로 Google·GitHub 계정도 있으면 → "이 이메일로 Google로 가입한 계정도 있어요. 그 계정은 Google로 로그인하세요" 안내 추가
      이메일 가입 계정이 없고 소셜 계정만 있으면 → "이 이메일은 Google로 가입되어 비밀번호가 없어요" 안내만
  → 새 비밀번호 저장 → 그 계정의 모든 세션 삭제 (모든 기기에서 로그아웃)
```

| 항목 | 규칙 |
|---|---|
| 토큰 | Redis `auth:reset:{토큰}` = memberId, TTL 30분, 사용하면 삭제 |
| 요청 제한 | 같은 이메일 1분에 1번, 하루 10번 / 같은 IP 1시간에 20번 |

L-1(별도 계정) 때문에 "어떤 수단으로 가입했는지 잊어버린" 사용자가 생길 수 있다. 재설정 메일에 같은 이메일의 소셜 계정을 함께 안내해서 이 혼란을 줄인다. 메일은 이메일 주인에게만 가므로 가입 여부가 남에게 드러나지 않는다.

## 5. 소셜 로그인 (Google·GitHub)

```
[Google로 계속하기] / [GitHub로 계속하기]
  → OAuth 인증 (state 검증) → 콜백
  ├─ (provider, 고유 ID)로 연결된 계정 있음 → 로그인
  └─ 처음
       → 가입 마무리 화면: 닉네임(필수, 소셜 이름을 정리해 미리 채움, [09 문서](./09-nickname.md)) · 블로그 주소(go-/gi- 고정 + 본문 수정 가능, [08 문서](./08-blog-address.md)) · 약관 동의(§3-1)
       → 완료 → 계정 생성 (email_verified_at = 가입 시각)
```

| 항목 | 규칙 |
|---|---|
| 가입 마무리 화면 | **반드시 거친다.** 소셜 이름이 닉네임 규칙(2~10자, 특수문자 불가)에 안 맞을 수 있다. 마무리 전에는 계정을 만들지 않고, 소셜 인증 정보는 세션에 10분만 보관 |
| 소셜 프로필 사진 | "프로필 사진 사용"(기본 체크)이면 계정 생성 직후 **브라우저가 소셜 사진을 받아 256×256으로 바꿔 우리 저장소에 복사**한다. 소셜 주소는 저장하지 않는다 ([11 문서 §4-2](./11-profile.md)). Google·GitHub 사진 주소는 이 화면의 CSP `img-src`에만 허용한다 (2026-10-07 회의 H3, [02 §5](./02-architecture.md)) |
| Google 이메일 | `email_verified = true`인 이메일만 사용 |
| GitHub 이메일 | `user:email` 권한으로 **인증된 대표 이메일**을 가져온다. 없으면 마무리 화면에서 이메일을 입력받아 §3과 같은 방식으로 인증 |
| 계정 식별 | Google `sub`, GitHub 숫자 ID (`provider_user_id`). 로그인 이름(GitHub login)은 바뀔 수 있어 식별에 쓰지 않음 |
| 네이버 | 이번 범위 제외 (L-5) |

## 6. 로그인 유지와 보안

| 항목 | 규칙 |
|---|---|
| 유지 기간 | 14일. 마지막 활동 시점부터 다시 계산 |
| 저장 | 서버 세션 + **Spring Session Data Redis** (서버를 늘려도 로그인 유지). 화면은 같은 도메인에서 서빙하는 React라 세션 쿠키를 그대로 쓴다 (2026-10-07 회의 Q2·H7). 정지·탈퇴·비밀번호 변경·재설정 때 그 회원의 세션을 삭제해 즉시 로그아웃. 개인 서비스에서 JWT를 쓰려면 Refresh 토큰 Redis 저장·교체 + 토큰 버전 확인을 갖춘다 |
| 쿠키 | `HttpOnly`, `Secure`, `SameSite=Lax`. 프록시 뒤 HTTPS 판별은 `X-Forwarded-Proto` ([02 §5](./02-architecture.md)) |
| Redis 장애 | 세션을 읽지 못하면 **비로그인으로 처리**해 글 읽기는 계속된다(로그인이 필요한 요청은 401). 새 로그인 시도와 인증·재설정 토큰 확인은 거부하고 "잠시 후 다시 시도해 주세요", 실패 횟수·재발송 제한 카운터는 통과 ([02 §2-1](./02-architecture.md), 2026-10-07 회의 H8) |
| 실패 제한 | 같은 계정 5회 연속 실패 → 15분 잠금 / 같은 IP 1분에 20회 (Redis 카운터, IP는 [02 §5](./02-architecture.md) 규칙). 잠금 중에는 "잠시 후 다시 시도해 주세요(약 15분)" |
| 실패 메시지 | "이메일 또는 비밀번호가 올바르지 않아요" — 어느 쪽이 틀렸는지 알려주지 않음 |
| 정지 계정 | 정지는 `member_suspension` 이력, 현재 상태는 `member.status = SUSPENDED` (2026-10-07 회의 E3). 비밀번호가 맞아도 **로그인 거부** + "정지된 계정이에요 (~기한). 사유: …" (열린 정지의 `ends_at`·`reason`, `ends_at`이 없으면 영구). 열린 정지(`lifted_at IS NULL`)의 `ends_at`이 지났으면 `lifted_at`을 기록하고 `status = ACTIVE`로 바꾼 뒤 로그인. 세션이 남아 있어도 쓰기 요청은 403 `ACCOUNT_SUSPENDED` (2026-10-07 회의 H7, 42 §3) |
| 로그인 후 이동 | 보던 페이지로. 우리 사이트 안의 상대 경로만 허용 (나민서 D-14) |
| 세션 고정 방지 | 로그인할 때 세션 ID 새로 발급 (Spring Security 기본값) |
| CSRF | Spring Security CSRF 유지. React는 상태를 바꾸는 요청에 CSRF 토큰을 헤더로 보낸다 ([02 §5](./02-architecture.md)) |
| 기록 | 로그인 성공 시 `auth_identity.last_login_at` 갱신. 갱신하기 **전 값**을 세션에 `previousLoginAt`으로 담아 두고, 본인 계정 화면에 **"직전 로그인: 일자, 로그인 방식"**(세션의 `previousLoginAt`·`provider`)으로 보여 계정 도용을 확인할 수 있게 한다. 첫 로그인이면 "첫 로그인"으로 표시. 방금 로그인한 시각은 보여 줘도 의미가 없기 때문이다 (스키마 변경 없음, 2026-10-07 결정). 비밀번호·토큰은 로그에 남기지 않음 |
| 최근 활동 | 로그인과 별개로, 요청이 오면 `member.last_active_at`을 **한 시간에 한 번 정도만** 갱신한다(Redis로 간격 조절). 친구(ACCEPTED)에게 "오늘·어제·N일 전·1주 이상"으로 보이며 `member.last_active_visible = false`면 숨긴다(숨기면 나도 남의 것을 못 봄). 익명 처리 때 비움 (2026-10-07 회의 "마지막 로그인·최근 활동 표시") |

## 6-1. 비밀번호 변경

로그인한 상태에서 바꾸는 기능은 [11 문서 §6-2](./11-profile.md)에 있다: 현재 비밀번호 확인, 07 §4 규칙, 변경 후 다른 기기 로그아웃 + 알림 메일, 소셜 계정은 불가.

## 8. 스키마 변경

[03-erd.md](./03-erd.md)에 반영했다. 컬럼 이름은 통합 ERD 기준 스키마(`erd/V1__common_schema.sql`)를 따른다.

| 변경 | 용도 |
|---|---|
| `auth_identity.email_verified_at` | 이메일 인증 여부 (소셜은 가입 시각) |
| `auth_identity`에 `UNIQUE(member_id)` | 계정 하나 = 로그인 수단 하나 (L-1) |
| `LOCAL`은 이메일 필수 + `provider_user_id = email` (CHECK) | 이메일 가입 계정의 식별값을 소문자 이메일로 고정 |
| `ix_auth_identity_email` | 재설정 메일에 같은 이메일의 계정들을 안내할 때 조회 |
| `member_agreement` (`TERMS`·`PRIVACY`·`AI` + `version`) | 약관·처리방침·AI 동의 기록과 재동의 판단 (§3-1, 2026-10-07 회의 E2) |
| `member_suspension` + `member.status` | 정지 이력과 현재 정지 상태 (§6, 2026-10-07 회의 E3) |
| `auth_identity.last_login_at` | 마지막 로그인 일자 (§6) |
| 인증·재설정 토큰, 실패 횟수, 재발송 횟수 | 테이블 대신 Redis (TTL) |

## 9. 공통 완료 기준 (C-AUTH-1)

| # | 기준 |
|---|---|
| 1 | 같은 로그인 수단(같은 이메일 가입, 같은 소셜 계정)으로는 계정이 두 개 생기지 않는다 |
| 2 | 로그아웃 뒤 쓰기 요청은 거부되고, 브라우저 임시 데이터가 지워진다 |
| 3 | 이메일 인증 전에는 글쓰기·댓글·사진 업로드·좋아요·신고가 거부된다 (42 P-6) |
| 4 | 규칙에 맞지 않는 비밀번호(8자 미만, 16자 초과, 영문·숫자·특수문자 중 하나라도 없음)로는 가입·재설정할 수 없다 |
| 5 | 비밀번호를 재설정하면 그 계정의 모든 세션이 끊긴다 |
| 6 | 같은 계정으로 5회 연속 실패하면 15분 동안 로그인할 수 없다 |
| 7 | 로그인 실패·비밀번호 찾기 화면으로는 가입 여부를 알 수 없다 |
| 8 | 인증·재설정 링크는 한 번만 쓸 수 있고 만료 시간이 지나면 쓸 수 없다 |
| 9 | 위조한 헤더로 IP 제한을 우회할 수 없다 (`X-Forwarded-For`는 로드 밸런서 내부 대역에서 온 것만 신뢰, 02 §5, 2026-10-07 회의 H4) |
| 10 | 정지된 계정은 로그인할 수 없고, 남아 있던 세션의 쓰기 요청은 403 `ACCOUNT_SUSPENDED`로 거부된다 (H7) |
| 11 | 약관·처리방침 버전이 바뀌면 다음 로그인 때 재동의를 받는다 (H9) |

## 10. 후속 제안 (미결)

| # | 제안 | 이유 |
|---|---|---|
| F-1 | 소셜로 처음 로그인할 때, 같은 이메일로 다른 수단의 계정이 이미 있으면 가입 마무리 화면에 "이 이메일로 이메일 가입한 계정이 이미 있어요. [기존 계정으로 로그인] [새 계정 만들기]" 안내 | L-1(별도 계정)은 유지하면서, 모르고 블로그를 하나 더 만드는 실수를 줄인다. 안내는 그 소셜 계정의 인증된 이메일 주인에게만 보이므로 가입 여부가 남에게 드러나지 않는다 |
