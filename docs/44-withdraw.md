# 회원 탈퇴·복구 화면 설계

> 작성일 2026-10-03 · 담당: 나민서 · 상태: **초안 (항목 확인 중)**
> 관련 요구사항: 회원 탈퇴 (Tier C). 연관: [13 삭제·탈퇴](./13-delete-withdraw.md) §3, [07 로그인](./07-auth.md), [11 프로필·설정](./11-profile.md) §2, [42 권한](./42-permission-matrix.md) P-12, [43 신고](./43-report-hide.md) §5
> 2026-10-06 수정: 강성찬 20(이벤트·`WithdrawalPurgeStep`)·21·23·24·25, 김민서 30·31·34 문서와 맞춤. 30일 뒤 처리를 단계 인터페이스 방식으로 바꿨다.
> 이미 결정된 것 (13 §3): **30일 유예 → 익명 처리**, 본인 확인(이메일 가입은 비밀번호, 소셜은 "탈퇴" 입력), 안내·동의 문구, 즉시 효과(모든 기기 로그아웃·블로그와 글 404·댓글 가림), 유예 중 로그인하면 복구 화면, 30일 뒤 처리 순서, 블로그 주소 영구 예약. **이 문서는 화면과, 30일 뒤 처리에서 담당자별 단계**를 정한다.

## 1. 결정 사항

| # | 안건 | 결정 | 이유 |
|---|---|---|---|
| W-1 | 들어가는 곳 | 설정(`/settings`) 맨 아래 [회원 탈퇴] → `/settings/withdraw` (11 §2) | |
| W-2 | 화면 단계 | **한 화면 안에 ① 안내·확인 체크 → ② 본인 확인 → [탈퇴하기]** | 단계를 여러 페이지로 나누면 중간에 이탈해 상태가 애매해진다. 대신 안내를 먼저 읽어야 버튼이 활성화된다 |
| W-3 | 잃게 되는 것 보여주기 | 내 글 수·댓글 수·받은 좋아요 수와 **"블로그 주소는 다시 쓸 수 없어요"** | 숫자로 보여주면 실수로 탈퇴하는 일이 줄어든다. 주소 영구 예약(13 D-9)은 본인도 30일 뒤 다시 쓸 수 없다는 점을 꼭 알려야 한다 |
| W-4 | 탈퇴 사유 | **받지 않는다** | 화면을 단순하게 하고, 탈퇴하는 사람에게 추가 입력을 요구하지 않는다. 저장할 데이터도 없다 |
| W-5 | 접수·복구 메일 | 이메일이 있는 계정에 **탈퇴 접수 메일**(복구 기한 안내)과 **복구 완료 메일** | 본인이 하지 않은 탈퇴(세션 탈취)를 알아챌 수 있다 |
| W-6 | 관리자 계정 | **관리자 권한이 있으면 탈퇴할 수 없다** ("관리자 권한을 해제한 뒤 탈퇴할 수 있어요") | 관리자가 모두 사라지는 일과 처리 기록 주인이 없어지는 일을 막는다 |
| W-7 | 탈퇴 전 글 내보내기 | 공통에서 제외 (개인 확장) | 1차 범위를 작게 유지 |
| W-8 | 본인 확인 실패 | 비밀번호를 5번 연속 틀리면 15분 잠금 — 11 §6-2와 같은 규칙 | 세션을 훔친 사람이 비밀번호를 추측해 탈퇴시키지 못하게 |
| W-9 | 복구 방식 | 로그인 → 복구 화면에서 **[복구하기]를 눌러야** 복구 (13 §3-1) | 로그인만으로 자동 복구하면, 본인이 탈퇴 상태를 확인할 기회가 없다 |

## 2. 탈퇴 화면 (`/settings/withdraw`)

```
회원 탈퇴

① 탈퇴하면 이렇게 돼요
   · 블로그 @kim755030과 글 24개가 바로 보이지 않아요
   · 남의 글에 쓴 댓글 18개는 "탈퇴한 사용자의 댓글이에요"로 가려져요
   · 30일(11월 2일 14:03까지) 안에 다시 로그인하면 모두 복구할 수 있어요
   · 30일이 지나면 글·사진·받은 좋아요 126개가 완전히 삭제되고 되돌릴 수 없어요
     (답글이 달린 댓글은 내용 없이 "탈퇴한 사용자의 댓글이에요"로 자리만 남아요)
   · 블로그 주소 @kim755030은 다른 사람도, 나도 다시 쓸 수 없어요
   ☐ 위 내용을 확인했어요

② 본인 확인
   이메일 가입:  비밀번호 [            ]
   소셜 가입:    "탈퇴"를 입력해 주세요 [      ]

                          [취소]  [탈퇴하기]   ← ①을 체크하고 ②를 채워야 활성화
```

| 규칙 | 내용 |
|---|---|
| 숫자 | 화면을 열 때 계산 (내 글 수: 휴지통 포함 전체, 댓글 수: 남의 글에 쓴 것, 받은 좋아요: `like_count` 합) |
| [탈퇴하기] 버튼 | 빨간색이지만 **기본 선택(포커스)이 아니다.** Enter로 바로 눌리지 않게 |
| 요청 | `POST /api/me/withdraw { password?, confirmText? }` |
| 실패 | 비밀번호 틀림 → `400 CURRENT_PASSWORD_MISMATCH`(5회 잠금, W-8), "탈퇴" 불일치 → `400 CONFIRM_TEXT_MISMATCH`, 관리자 → `409 ADMIN_CANNOT_WITHDRAW` (W-6) |
| 성공 처리 | 13 §3-1 "즉시": `status = WITHDRAWN`, `withdrawn_at = now()`, 모든 세션 삭제 → 커밋 후 `MemberWithdrawn(memberId, withdrawnAt)` 이벤트 (20 §3-6), 접수 메일(W-5) |
| 유예 중 알림 | 그 회원에게 새 알림을 만들지 않고, 그 회원의 행동으로도 만들지 않는다 ([25 알림](./25-notification.md) §8) |

**완료 화면** (로그아웃된 상태로 보임, `/withdrawn`)

```
탈퇴 신청이 완료됐어요
11월 2일 14:03까지 로그인하면 복구할 수 있어요.
그동안 블로그와 글은 다른 사람에게 보이지 않아요.
                                    [홈으로]
```

- 브라우저의 임시 글 데이터(IndexedDB)는 로그아웃과 같이 지운다 (07 §7).

## 3. 유예 중 로그인 → 복구 화면 (`/account/restore`)

```
탈퇴 신청한 계정이에요
11월 2일 14:03까지 복구할 수 있어요 (29일 남음).
복구하면 블로그·글·댓글이 모두 원래대로 돌아와요.

                 [로그아웃]  [복구하기]
```

| 규칙 | 내용 |
|---|---|
| 들어오는 경우 | 탈퇴 유예 회원이 로그인하면 **항상 이 화면**. 다른 주소로 가면 이 화면으로 되돌아온다 (SSR 302 / REST 403 `ACCOUNT_WITHDRAWN`, 42 P-12) |
| [복구하기] | `POST /api/me/restore` → `status = ACTIVE`, `withdrawn_at = null` → 커밋 후 `MemberRestored(memberId, restoredAt)` 이벤트 (20 §3-6), 복구 메일(W-5) → 홈으로 "다시 오신 걸 환영해요" |
| [로그아웃] | 로그아웃만. 유예는 계속 |
| 비밀번호를 잊음 | 로그인 화면의 [비밀번호 찾기]로 재설정 가능 (13 §3-2) |
| 같은 이메일로 새로 가입하려 함 | 가입 화면에 "탈퇴 신청한 계정이 있어요. 로그인하면 복구할 수 있어요" (13 §3-2). 이메일만으로 탈퇴 신청 여부가 보이는 것은 감수한다 (회의 P2) |

## 4. 30일 뒤 처리 (13 §3-3) — 모듈별 정리 단계

13 §3-3의 순서를 **모듈별 단계**로 나눈다. 방식은 [20 도메인 이벤트](./20-domain-events.md)의 제안을 따른다: 각 모듈이 `WithdrawalPurgeStep` 인터페이스를 구현하고, 배치가 **`order()` 순서대로 한 트랜잭션 안에서** 실행한다. 이벤트로 나누지 않는다 (일부만 성공할 수 있다).

```java
// shared (나민서): 배치가 Spring 빈 목록을 order() 순으로 실행
public interface WithdrawalPurgeStep {
    int order();
    void purge(long memberId);   // 호출한 쪽의 트랜잭션 안에서 실행
}
```

```
WithdrawPurgeJob (매일 새벽, ShedLock)  — 나민서
 for 대상 회원 (status = WITHDRAWN AND deleted_at IS NULL AND withdrawn_at < now() - 30일):
   @Transactional  steps.sortedBy(order).forEach(step -> step.purge(memberId))
```

| order | 단계 (구현 클래스) | 처리 | 13 §3-3 | 담당 |
|---|---|---|---|---|
| 10 | `PostWithdrawalPurgeStep` | 내 글 전부 완전 삭제 (13 §2-5). 남이 내 글에 쓴 댓글·좋아요·알림은 CASCADE | 1 | 공통 post |
| 20 | `CommentWithdrawalPurgeStep` | 답글 달린 댓글은 내용 비움(자리만), 없으면 삭제, `comment_count` 감소 (21 §11) | 2 | 강성찬 |
| 30 | `LikeWithdrawalPurgeStep` | 내가 누른 좋아요 삭제 + `like_count` 감소 (30 §7) | 3 | 김민서 |
| 40 | `ImageWithdrawalPurgeStep` | 프로필 이미지 비움, 올린 사진 `detached_at` 기록 (정리 배치가 삭제) | 4 | 강성찬 |
| 50 | `AuthIdentityWithdrawalPurgeStep` | `auth_identity` 삭제 | 5 | 공통 account |
| 60 | (친구 공개 적용자) `FriendshipWithdrawalPurgeStep` | `friendship` 삭제 | 6 | 적용자 |
| 65 | `FollowWithdrawalPurgeStep` | 팔로우 관계 양방향 삭제 (24 §6) | 6 다음 (24 추가) | 강성찬 |
| 70 | `NotificationWithdrawalPurgeStep` | 받은 알림 삭제, 묶음 알림에서 나를 빼고 다시 계산 (25 §8). **글·댓글 단계 다음** | 추가 (25) | 강성찬 |
| 80 | `ReportWithdrawalPurgeStep` | 내 콘텐츠에 대한 대기 신고 `CLOSED_NO_TARGET` (43 §5) | 추가 (43) | 나민서 |
| 90 | `MemberWithdrawalPurgeStep` | 회원 행 익명화 (13 §3-3 7번) + **`ai_consent_at`**(34)·`suspended_until`·`suspended_reason`(43)도 null. `handle`은 그대로 | 7 | 공통 account |
| 커밋 후 | — | Redis 세션·토큰·실패 횟수·요청 횟수 키 삭제 | 8 | 공통 account |

| 규칙 | 내용 |
|---|---|
| `order` 값 | 10 단위로 두고, 새 단계는 사이 값을 쓴다 (기존 단계 번호를 바꾸지 않는다) |
| ①(10)이 먼저 | 내 글이 지워지면 거기 달린 남의 댓글·좋아요·알림은 CASCADE로 함께 사라진다. 이후 단계가 다룰 데이터가 줄어든다 |
| 20·30은 10 다음 | 남의 글에 남긴 것만 남는다. 카운터(`comment_count`, `like_count`)를 실제 행 수와 맞춘다 (13 §5 탈퇴 기준 4) |
| 90이 마지막 | 앞 단계가 `member` 행을 참조하므로 익명화는 맨 끝 |
| 조회수 | 정리할 개인 데이터 없음. 중복 판정은 Redis에서 기간이 지나면 사라지고, `post_view_daily`는 글 삭제 때 CASCADE (31) |
| 이벤트 | 30일 뒤 처리는 이벤트를 만들지 않는다 (20 §3-6). 글 삭제로 생기는 `PostPurged`는 post 모듈 규칙을 따른다 |
| 실패 | 한 단계라도 실패하면 그 회원 전체를 롤백하고 다음 날 다시 시도 (13 §3-3) |

## 5. 공통 완료 기준 (회원 탈퇴 화면)

13 §5 "회원 탈퇴 데이터" 기준 5개에 더한다.

| # | 기준 |
|---|---|
| 1 | 안내 확인 체크와 본인 확인을 하지 않으면 [탈퇴하기]를 누를 수 없고, 서버도 거부한다 |
| 2 | 비밀번호를 5번 연속 틀리면 15분 동안 탈퇴를 시도할 수 없다 |
| 3 | 탈퇴하면 모든 기기에서 로그아웃되고 완료 화면에 복구 기한이 보인다 |
| 4 | 유예 중 로그인하면 복구 화면만 보이고, 다른 주소로 가도 복구 화면으로 돌아온다 |
| 5 | [복구하기]를 누르면 블로그·글·댓글이 탈퇴 전과 같다 |
| 6 | 관리자 권한이 있으면 탈퇴할 수 없다 |
| 7 | 30일 뒤 처리는 회원 1명 단위로 전부 성공하거나 전부 취소되고, 처리 후 반응 수가 실제 행 수와 맞는다 |
| 8 | `WithdrawalPurgeStep` 구현이 `order()` 순서대로 실행되고, 한 단계가 예외를 던지면 앞 단계까지 모두 롤백된다 |
| 9 | 처리 후 회원 행에 `handle` 외 개인 정보(닉네임·소개·사진·`ai_consent_at`·정지 사유)가 남지 않는다 |
