## 1. 결정 사항

| # | 안건 | 결정 | 이유 |
|---|---|---|---|
| T-1 | 노출 위치 | 홈 상단 탭 **`[최신] [트렌딩]`**, 10 문서와 같은 카드·9개·[더 보기] | 홈의 한 줄 3개 배치와 겹치지 않는다 |
| T-2 | 점수식 | **글 나이로 감쇠:** `(3·좋아요 + 2·댓글 + 0.1·조회) ÷ (공개 후 경과 시간(h) + 2)^1.5` | 강성찬·김민서 안의 가중치가 같다. 이미 있는 카운터만 써서 단순하고, 사용자가 적은 지금 결과가 안정적이다 |
| T-3 | 대상 기간 | **7일 안에 처음 공개된 글** (`first_public_at`) | 강성찬 안. 목록(10)과 같은 기준 시각 |
| T-4 | 댓글 점수 | `comment_count` 대신 **작성자를 뺀 서로 다른 댓글 작성자 수** | 작성자가 자기 글에 댓글을 계속 달아 점수를 올리는 것을 막는다 |
| T-5 | 최소 조건 | 좋아요 1개 **또는** 작성자 외 댓글 작성자 1명 이상 | 반응 없는 글은 "최신 순"과 다를 게 없다 |
| T-6 | 작성자 편중 | **작성자당 최대 3개** | 글을 많이 쓰는 한 사람이 트렌딩을 채우지 않게 |
| T-7 | 집계 | **10분마다**, 상위 **100개** 스냅샷을 Redis에 30분 보관 | 요청 때 계산하지 않는다 (김민서 PERF-5) |
| T-8 | 넘기기 | 커서에 **스냅샷 ID**를 넣어 보던 순위 그대로 이어서 | 보는 도중 순위가 바뀌어도 중복·누락이 없다 |
| T-9 | 장애 | Redis 장애 시 DB에서 바로 계산해 응답 (임시) | 트렌딩 탭이 비지 않게 |
| T-10 | `post_view_daily` | **공통에 유지.** 추가 이유를 "작성자 통계 + 점수식 B 전환 대비"로 고친다 (31 문서) | T-2는 누적 조회수로 충분해서 트렌딩에는 필요 없다. 그래도 통계(강 OPEN-15, 김 STATS-1)에 쓰이고, 나중에 "최근 반응" 방식으로 바꿀 때 데이터가 있어야 한다 |
| T-11 | 공통에서 뺄 것 | 오늘/주/월 탭, 사이드바 인기 글 5개, 첫 글·새 작가 탭, 주제·태그별 트렌딩 | 개인 확장 |

> **T-10 정정:** 31 문서를 정리할 때 점수식을 정하기 전에 "최근 조회수가 필요하다"고 판단해서 `post_view_daily`의 추가 이유를 트렌딩으로 적었다. T-2(글 나이 감쇠)는 7일 안의 글만 다루므로 누적 `view_count`로 충분하다. 테이블은 유지하고 이유만 바로잡는다.

## 2. 점수식

```
score = (3 × 좋아요 + 2 × 댓글 작성자 + 0.1 × 조회) ÷ (h + 2)^1.5

  좋아요       = post.like_count                (30: 자기 글 불가, 이메일 인증 회원만)
  댓글 작성자  = 작성자를 뺀 서로 다른 댓글 작성자 수, 삭제된 댓글 제외   (T-4)
  조회         = post.view_count                (31: 중복 제거, 작성자·봇 제외)
  h            = 공개 후 경과 시간(시간) = now() - first_public_at
```

| 요소 | 의미 |
|---|---|
| 가중치 3·2·0.1 | 좋아요가 가장 강한 신호, 조회는 부풀리기 쉬워서 낮게 (강성찬 근거) |
| `+ 2` | 막 올라온 글(h=0)의 점수가 무한대로 커지지 않게 |
| 지수 `1.5` | 시간이 지나면 점수가 빠르게 줄어든다. 같은 반응이면 1시간 된 글이 하루 된 글보다 약 25배 높다 |

동점이면 `first_public_at` 최신 → 글 ID 큰 순 (나민서 D-10 "동점이면 최신 먼저").

## 3. 집계

### 3-1. 계산 SQL

```sql
WITH scored AS (
    SELECT p.id, p.author_id, p.first_public_at, p.like_count AS likes, p.view_count AS views,
           (SELECT count(DISTINCT c.author_id) FROM comment c
             WHERE c.post_id = p.id AND c.author_id <> p.author_id AND c.deleted_at IS NULL) AS commenters
    FROM post p JOIN member m ON m.id = p.author_id
    WHERE p.status = 'PUBLISHED' AND p.visibility = 'PUBLIC' AND p.deleted_at IS NULL
      AND m.withdrawn_at IS NULL
      AND p.first_public_at >= now() - interval '7 days'
), ranked AS (
    SELECT *, (3 * likes + 2 * commenters + 0.1 * views)
              / power(extract(epoch FROM now() - first_public_at) / 3600 + 2, 1.5) AS score
    FROM scored
    WHERE likes >= 1 OR commenters >= 1                        -- 최소 조건 (T-5)
), capped AS (
    SELECT *, row_number() OVER (PARTITION BY author_id
                                 ORDER BY score DESC, first_public_at DESC, id DESC) AS rn
    FROM ranked
)
SELECT id, score FROM capped
WHERE rn <= 3                                                  -- 작성자당 최대 3개 (T-6)
ORDER BY score DESC, first_public_at DESC, id DESC
LIMIT 100;
```

- 대상 조건은 06 §7의 공용 조건(`VisibilityFilter`)과 같다. 구현할 때 공용 조건을 그대로 쓴다.
- 7일 안의 글만 보므로 `ix_post_feed`(`first_public_at`)로 범위를 좁힌다.
- 댓글 작성자 수는 글마다 하위 쿼리지만, 10분에 한 번이고 대상이 7일 안의 글뿐이라 부담이 없다. 글이 많아지면 `comment(post_id, author_id)` 인덱스를 검토한다.

### 3-2. 스냅샷

```
10분마다 (ShedLock, 한 서버에서만)
 ① §3-1 실행 → 상위 100개 글 ID
 ② RPUSH trending:{스냅샷ID} … ; EXPIRE 1800 (30분)
 ③ SET trending:current {스냅샷ID}
```

스냅샷 ID는 생성 시각(`yyyyMMddHHmm`)이다. 이전 스냅샷은 30분 동안 남아 있어 보던 사람이 이어 볼 수 있다.

## 4. API와 넘기기

```
GET /api/posts/trending?cursor={스냅샷ID}:{위치}&size=9
```

```
① cursor가 없으면 trending:current의 스냅샷, 위치 0부터
② LRANGE로 다음 ID들을 꺼내 글을 한 번에 조회 (SQL 1번, 10 §7과 같은 카드 컬럼)
③ 그 사이 볼 수 없게 된 글(비공개·휴지통·탈퇴 신청)은 빼고 다음 ID로 채워 9개를 맞춘다
④ { items, nextCursor: "{스냅샷ID}:{다음 위치}" }  — 스냅샷 끝이면 null
```

| 상황 | 처리 |
|---|---|
| 보는 도중 10분이 지나 새 스냅샷이 생김 | 커서의 스냅샷 ID로 **보던 순위 그대로** 이어진다 |
| 30분이 지나 스냅샷이 사라짐 | `410 SNAPSHOT_EXPIRED` → 화면에 "순위가 새로 바뀌었어요" 안내 후 최신 순위 처음부터 |
| 보는 도중 아직 안 본 글이 비공개·삭제됨 | 건너뛰고 다음 글로 채운다 |
| 이미 화면에 있는 카드가 비공개·삭제됨 | 카드는 남고 누르면 404 (10 §4-3과 같음) |
| 최대 | 100개 (9개씩 12번) |
| Redis 장애 | §3-1을 바로 실행해 첫 9개를 응답하고 `nextCursor: null` (임시) |

## ERD 변경 제안

**스키마 변경 없음.** 기존 `post.like_count`·`view_count`, `comment`, `ix_post_feed`로 계산한다.

- 31 문서의 `post_view_daily` 추가 이유를 "트렌딩"에서 **"작성자 통계 + 점수식 B 전환 대비"**로 고친다 (T-10). 이 PR에서 31 문서를 함께 고쳤다.
- 글이 많아져 §3-1이 느려지면 `CREATE INDEX ix_comment_post_author ON comment (post_id, author_id) WHERE deleted_at IS NULL`을 추가한다 (지금은 넣지 않음).
