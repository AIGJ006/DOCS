# 조회수 설계

> 작성일 2026-10-05 · 담당: 김민서 · 관련 요구사항: C-VIEW-1(조회수: 새로고침으로 부풀지 않는다, 작성자 본인 제외, 중복 판정 기준은 개인 설정값)
> 이미 결정된 것을 따른다: `post.view_count` 미리 저장(03 E-6), 중복 판정 데이터는 공통 ERD에 두지 않음(03 E-11), 카운터는 `@Modifying` 쿼리(05 J-2), 카드에는 조회수 없음(10 §2), 볼 수 없는 글은 404(06).

## 1. 결정 사항

| # | 안건 | 결정 | 이유 |
|---|---|---|---|
| W-1 | 중복 기준 | **기본 "같은 방문자·같은 글은 24시간에 1회"**, 설정값(`dedupe-window`, `max-per-window`)으로 변경 가능 | 나민서·김민서 안과 같다. 강성찬은 `30m`·`5`로 원래 안을 그대로 쓸 수 있다 (C-VIEW-1 "개인 설정값") |
| W-2 | 비회원 구분 | **익명 방문자 쿠키**, 쿠키가 없으면 IP + User-Agent의 해시 (날마다 바뀌는 비밀값) | IP만 쓰면 회사·학교(IP 공유)는 덜 세고 모바일(IP 변경)은 더 센다. 원래 IP는 저장하지 않는다 |
| W-3 | 제외 | 작성자 본인, 봇·링크 미리보기, 미리 불러오기, 볼 수 없는 글 | |
| W-4 | 기록 시점 | **글이 화면에 보이는 상태로 1초 이상 지나면 브라우저가 기록 요청** | 봇·미리 불러오기·백그라운드 탭이 자연히 빠져 "실제로 본 것"에 가깝다. 트렌딩 점수의 재료(32 T-2)라서 정확도가 중요하다 |
| W-5 | 응답 | **항상 204** (셌는지 알려주지 않음), 같은 방문자 1분에 60번 제한 | 중복 판정 규칙을 추측해 조작하기 어렵게 한다 |
| W-6 | 반영 방식 | Redis에 모아 두고 **1분마다 DB 반영**, Redis 장애 시 기록을 건너뜀 | 조회가 몰려도 상세 화면을 막지 않는다 (김민서 PERF-4, REL-4) |
| W-7 | 일별 조회수 | **`post_view_daily` 공통 테이블 추가**, 90일 보관 | 작성자 통계(강성찬 OPEN-15, 김민서 STATS-1)의 일별 추이와, 트렌딩 점수식을 "최근 반응" 방식으로 바꿀 때 필요하다. **트렌딩 기본 점수식(32 T-2)은 누적 `view_count`만 쓴다** (32 T-10에서 이유 정정) |
| W-8 | 화면 | 글 상세에만 "조회 N" + 안내 문구, 카드에는 표시 안 함 | 10 §2 팀 결정 유지 |

## 2. 방문자 구분과 중복 판정

### 2-1. 방문자 키

| 방문자 | 키 | 비고 |
|---|---|---|
| 회원 | `m:{memberId}` | 기기가 달라도 같은 사람 |
| 비회원 | `v:{방문자 쿠키 값}` | 첫 방문 때 무작위 UUID를 발급하는 쿠키 `vid` (1년, `HttpOnly`, `Secure`, `SameSite=Lax`) |
| 쿠키를 막은 비회원 | `h:{SHA-256(IP + User-Agent + 오늘의 비밀값)}` | 비밀값은 매일 0시(한국 시간)에 바꾸고 하루만 보관 → 날짜를 넘겨 같은 사람을 추적할 수 없다 |

비회원으로 보다가 로그인해서 다시 보면 1번 더 셀 수 있다. 드물어서 허용한다.

### 2-2. 중복 기준 (설정값)

```yaml
blog:
  view:
    dedupe-window: 24h     # 강성찬: 30m
    max-per-window: 1      # 강성찬: 5
```

같은 방문자가 같은 글을 **기간(`dedupe-window`) 안에 최대 `max-per-window`번**까지 센다. 기간은 그 방문자가 그 글을 처음 본 순간부터 시작한다.

## 3. 세지 않는 경우

| 제외 | 판정 |
|---|---|
| 작성자 본인 | 로그인한 사용자가 글 작성자 |
| 봇·링크 미리보기 | W-4 방식이면 JS를 실행하지 않는 봇은 자연히 빠진다. 추가로 User-Agent에 `bot`·`crawler`·`spider`·`preview`·`facebookexternalhit`·`Slackbot`·`kakaotalk-scrap`·`Discordbot`·`HeadlessChrome`이 있으면 제외 (목록은 설정 파일) |
| 미리 불러오기 | `Purpose: prefetch` 또는 `Sec-Purpose: prefetch` 헤더 |
| 볼 수 없는 글 | 06 `canRead` 실패 또는 `PUBLISHED`가 아님 → 404 |

## 4. 기록 요청

### 4-1. 브라우저

```js
// 글 상세 페이지에서: 화면에 보이는 상태로 1초가 지나면 한 번만 보낸다
let timer = null, sent = false;
function arm() {
  if (sent || document.visibilityState !== 'visible') return;
  timer = setTimeout(() => {
    sent = true;
    fetch(`/api/posts/${postId}/views`, { method: 'POST', keepalive: true,
      headers: { 'X-CSRF-TOKEN': csrfToken } });
  }, 1000);
}
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState !== 'visible') clearTimeout(timer); else arm();
});
arm();
```

- 백그라운드 탭으로 열린 글은 사용자가 그 탭을 볼 때 센다.
- 실패해도 다시 보내지 않고, 화면에도 아무것도 표시하지 않는다.

### 4-2. API

```
POST /api/posts/{postId}/views
```

| 응답 | 경우 |
|---|---|
| `204` | 받음. **셌든 중복이라 안 셌든 똑같이 204** (W-5) |
| `404` | 볼 수 없는 글 |
| `429` | 같은 방문자 키가 1분에 60번 초과 |

비회원도 호출할 수 있다. CSRF 토큰은 페이지에 들어 있는 값을 쓴다.

## 5. 저장과 반영

### 5-1. 기록 (요청마다, Redis)

```lua
-- KEYS[1] = view:seen:{postId}:{방문자키}, KEYS[2] = view:pending:{yyyyMMdd(한국 시간)}
-- ARGV[1] = dedupe-window(초), ARGV[2] = max-per-window, ARGV[3] = postId
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1])) end
if n <= tonumber(ARGV[2]) then
  redis.call('HINCRBY', KEYS[2], ARGV[3], 1)
  return 1
end
return 0
```

- 중복 판정과 "모아 두기"가 스크립트 하나로 원자적으로 처리된다.
- 모아 두는 키를 **날짜별**로 나눠서, 자정 무렵의 조회도 정확한 날짜의 일별 행에 들어간다.
- Redis에 연결할 수 없으면 기록을 건너뛰고 204를 돌려준다. 페이지는 정상이고, 그동안의 조회만 빠진다 (W-6).

### 5-2. DB 반영 (1분마다, ShedLock)

```
for 키 in SCAN view:pending:*
  ① 처리 중 키(…:processing:…)가 남아 있으면 그것부터 처리 (지난번에 서버가 죽은 경우)
  ② 아니면 RENAME view:pending:{날짜} → view:pending:{날짜}:processing:{시각}
     (이 순간부터 새 조회는 새 키에 쌓인다)
  ③ HGETALL → 글마다:
       한 트랜잭션으로
         UPDATE post SET view_count = view_count + :n WHERE id = :postId;     -- updated_at은 바꾸지 않는다
         INSERT INTO post_view_daily (post_id, view_date, views) VALUES (:postId, :date, :n)
           ON CONFLICT (post_id, view_date) DO UPDATE SET views = post_view_daily.views + EXCLUDED.views;
       커밋한 뒤 HDEL 처리 중 키 :postId        ← 반영한 글은 바로 지운다
  ④ 비어 있으면 처리 중 키 삭제
```

| 상황 | 결과 |
|---|---|
| 인기 글에 조회가 몰림 | DB에는 1분에 글당 UPDATE 1번. 상세 화면 속도에 영향 없음 |
| 반영 지연 | 최대 1분 (PERF-4) |
| ②와 ④ 사이에 서버가 죽음 | 처리 중 키가 남아 다음 실행 때 ①에서 처리한다 |
| ③ 도중 일부 글만 반영하고 죽음 | 반영한 글은 이미 `HDEL`로 지웠으므로 다음 실행 때 **남은 글만** 처리한다. 커밋과 `HDEL` 사이에 죽은 **그 글 하나**만 1분치가 한 번 더 더해질 수 있다. 조회수는 회계 값이 아니라서 허용한다 |
| 글이 그 사이 완전 삭제됨 | `UPDATE`가 0건, `INSERT`는 FK 오류 → 그 글만 건너뛴다 |

## 6. 일별 조회수 테이블

| 항목 | 규칙 |
|---|---|
| 테이블 | `post_view_daily(post_id, view_date, views)` — PK `(post_id, view_date)`, 날짜는 한국 시간 |
| 인덱스 | `(view_date, post_id) INCLUDE (views)` — "최근 N일 조회수 합계"를 글별로 구할 때 (통계, 점수식 B) |
| 글 완전 삭제 | `ON DELETE CASCADE` |
| 보관 | **90일.** 매일 새벽 배치가 `view_date < 오늘 - 90일` 행을 삭제 (김민서 SCALE-6). 누적은 `post.view_count`에 계속 남는다 |
| 쓰는 곳 | 작성자 통계(개인 확장), 트렌딩 점수식 B로 바꿀 때 (32 T-10) |

| 항목 | 규칙 |

## 9. 검증 결과 (2026-10-05, Redis 7 + PostgreSQL 18)

| 테스트 | 결과 |
|---|---|
| 방문자 v1이 글A를 5번 새로고침 + v2·v3가 1번씩 | 글A 3 (v1은 1번만) |
| 회원이 글B를 3번 | 글B 1 |
| DB 반영 전 | `view_count` 0 (1분 반영 전에는 DB를 건드리지 않음) |
| 1분 반영 실행 | `view_count` 글A 3·글B 1, 일별 행도 같은 값 |
| 같은 방문자가 24시간 안에 다시 봄 | 안 셈 |
| 이름만 바꾸고 서버가 죽음 → 그 사이 새 조회 → 다음 실행 | 남은 처리 중 키와 새 키를 모두 반영, 남은 키 0개 |
| 같은 방문자가 동시에 50번 | 1번만 셈 |
| 설정 "30분 5회": 같은 방문자 7번 | 5번 셈 |
| 기간이 지난 뒤 다시 봄 | 다시 셈 |
| 91일 전·89일 전 일별 행 → 보관 배치 | 91일 전만 삭제 |
| 글 완전 삭제 | 일별 행도 삭제 (CASCADE) |
| 글 3개 중 1개만 반영하고 서버가 죽음 → 다음 실행 | 남은 2개만 처리, 결과 10·20·30으로 중복 없음, 남은 키 0개 |

> 처음에는 `SET NX`(기간 안 1번)로 설계했는데, 테스트 중 "30분 5회" 같은 설정을 표현할 수 없다는 것을 발견해 `INCR` 방식(§5-1)으로 바꿨다.
> 반영도 처음에는 키 전체를 처리한 뒤 지웠는데, 도중에 죽으면 이미 반영한 글이 모두 한 번 더 더해져서 글마다 `HDEL`하도록(§5-2 ③) 바꿨다.

## ERD 변경 제안

**공통 테이블 1개 추가:**

```sql
-- V1 반영됨 (2026-10-07): 이 SQL은 erd/V1__common_schema.sql에 들어 있다. 기록용으로 남긴다.
-- 일별 조회수 (통계·트렌딩 점수식 B 대비, 90일 보관) — 31 문서
CREATE TABLE post_view_daily (
    post_id   bigint  NOT NULL REFERENCES post (id) ON DELETE CASCADE,
    view_date date    NOT NULL,                 -- 한국 시간 기준 날짜
    views     integer NOT NULL CHECK (views > 0),
    PRIMARY KEY (post_id, view_date)
);
CREATE INDEX ix_post_view_daily_date ON post_view_daily (view_date, post_id) INCLUDE (views);
```

- 03 E-11("중복 판정 데이터는 공통에 두지 않는다")은 그대로다. 이 테이블은 누가 봤는지가 아니라 **날짜별 합계**만 담는다. 중복 판정은 Redis에서만 한다.
- 03에 설계 결정 추가안: "E-24 `post_view_daily`: 날짜별 조회수 합계. 작성자 통계와 트렌딩 점수식 B 전환 대비. 90일 보관, 글 삭제 시 CASCADE."
