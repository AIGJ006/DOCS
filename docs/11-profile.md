# 프로필 수정·계정 설정 설계

> 작성일 2026-10-02 · 관련 요구사항: C-AUTH-2(프로필 수정). 연관: [07 로그인](./07-auth.md), [08 블로그 주소](./08-blog-address.md), [09 닉네임](./09-nickname.md), [04 사진 업로드](./04-draft-and-image.md)
> 팀 결정: 닉네임·소개·프로필 이미지를 **본인만** 수정한다. 블로그 주소(아이디)는 바꿀 수 없다.
> 수정 2026-10-07 (회의): 회원 테이블의 사진 컬럼 삭제 → 프로필 사진은 `image` 행으로 판별(§4-4), CSP(H3), 마지막 로그인·최근 활동 표시(§6-4). 스키마 기준은 [`erd/V1__common_schema.sql`](../erd/V1__common_schema.sql)

## 1. 결정 사항

| # | 안건 | 결정 | 이유 |
|---|---|---|---|
| R-1 | 소개 길이·형식 | **0~200자, 글자만**(HTML·Markdown 불가), 줄바꿈 최대 4줄, 이모지 허용 | 나민서 BLG-02와 같은 길이. 서식이 없으니 XSS 위험이 없다 |
| R-2 | 소개에 쓴 주소 | 자동으로 링크로 바꾸지 않는다 | 스팸 링크 방지. 외부 링크 칸은 김민서 개인 확장 |
| R-3 | 소개 금칙어 | 닉네임과 같은 금칙어 필터 (예약어 검사는 제외) | 블로그 상단에 공개된다 |
| R-4 | 프로필 이미지 크기 | 브라우저에서 정사각형으로 잘라 **256×256 WebP 한 가지** | 카드 아이콘(24px)부터 블로그 상단(96px, 고해상도 2배)까지 충분. 약 20KB |
| R-5 | 기본 이미지 | 닉네임 첫 글자 + 블로그 주소로 정한 배경색 (화면에서 그림, 파일 없음) | |
| R-6 | 소셜 프로필 사진 | **가입할 때 가져온다.** 브라우저가 소셜 사진을 받아 256×256으로 바꾼 뒤 우리 저장소에 **복사**한다 (§4). Google·GitHub 사진 주소는 **소셜 가입 마무리 화면의 CSP에만** 허용한다 (화면별 CSP, 12 §8, 10/7 H3) | 소셜 주소를 그대로 쓰면 독자 IP가 소셜 서비스에 노출되고 사진이 바뀌면 깨진다. 서버가 내려받으면 외부 주소 요청 위험(SSRF)이 생긴다. 브라우저 복사는 둘 다 없다 |
| R-7 | 사진 정리 배치가 프로필 이미지를 지우는 문제 | `image.purpose = PROFILE`. **지금 프로필 사진 = `image`에서 `uploader_id` = 회원, `purpose = 'PROFILE'`, `status = 'ATTACHED'`, `detached_at IS NULL`인 행 하나** (회원당 하나는 `uq_image_profile_current`). 회원 테이블은 사진을 가리키지 않는다. 바꾼 이전 이미지는 `detached_at`을 기록하고 7일 뒤 삭제, 연결된(`ATTACHED`) 프로필 사진은 정리 배치가 지우지 않는다 (2026-10-07 회의, 10-02 결정 변경) | 04의 배치는 "글에 연결되지 않은 사진"을 지워서, 그대로면 프로필 이미지가 하루 뒤 사라진다. 회원 ↔ 사진이 서로 가리키던 구조(`member.profile_image_id`)는 V1에서 없앴다 |
| R-8 | 저장 방식 | [저장] 한 번에 반영. 하나라도 검사에 실패하면 **아무것도 저장하지 않는다.** 동시 수정은 나중에 저장한 쪽이 반영 | 프로필은 짧아서 비교 창 없이 다시 고치기 쉽다 |
| R-9 | 이메일 변경 | 불가 | 이메일 가입은 이메일이 곧 계정 식별값이다 (07) |
| R-10 | 비밀번호 변경 | **공통에 추가.** 변경 후 다른 기기 로그아웃 + 알림 메일 | 로그인한 상태에서 비밀번호를 바꿀 방법이 없었다 |
| R-11 | 직전 로그인 표시 | 본인 계정 화면에 "직전 로그인: 일자, 로그인 방식" (이번 로그인 전의 `auth_identity.last_login_at`, §6-4) (2026-10-07 회의) | 계정 도용을 본인이 알아챌 수 있다 |
| R-12 | 최근 활동 표시 | 친구(ACCEPTED)에게 "오늘·어제·N일 전·1주 이상"으로 표시. `member.last_active_visible`(기본 공개)로 끌 수 있고, 끄면 나도 남의 것을 못 본다 (§6-4) (2026-10-07 회의) | 정확한 시각을 숨겨 감시처럼 느껴지지 않게 한다 |

## 4. 프로필 이미지

### 4-1. 직접 올리기

```
[이미지 변경] → 파일 선택 (jpg·png·gif·webp, 10MB 이하)
 → [브라우저] 정사각형 자르기 (끌어서 위치 조정, 확대·축소)
 → 256×256 WebP(품질 0.85), EXIF 제거 (GIF는 첫 장면으로 정지 이미지)
 → 사진 업로드 흐름 (04 §4-1): presign {purpose: PROFILE} → 업로드 → complete
 → 미리보기에 표시 → [저장]을 누르면 프로필에 연결
```

| 항목 | 규칙 |
|---|---|
| 서버 검사 (complete) | 형식·매직 바이트·**정확히 256×256**·1MB 이하. `purpose = PROFILE`이면 썸네일은 만들지 않는다 |
| 적용 시점 | [저장]을 눌러야 연결된다. 올리기만 하고 저장하지 않은 이미지는 `TEMP`로 남아 24시간 뒤 정리 배치가 지운다 |
| 이메일 인증 전 | 업로드 불가 (07 "인증 전 사진 업로드 불가"). 닉네임·소개는 수정 가능 |
| 요청 제한 | 사진 업로드 공통 제한 (사용자당 1분에 20장) |

### 4-2. 소셜 프로필 사진 가져오기 (R-6)

Google과 GitHub의 프로필 사진 서버는 다른 사이트의 브라우저가 이미지를 읽어 가는 것을 허용한다(`access-control-allow-origin: *`, 2026-10-02 확인). 그래서 **브라우저가 직접 받아서** 직접 올리기와 같은 흐름으로 복사할 수 있다.

```
소셜 가입 마무리 화면 (07 §5)
  ☑ Google 프로필 사진 사용   (미리보기)          ← 기본 체크, 끄면 기본 이미지
  → [가입 완료] → 계정 생성
  → [브라우저] 소셜 사진을 받음 (crossOrigin="anonymous", 5초 제한)
     → 가운데를 정사각형으로 잘라 256×256 WebP
     → presign {purpose: PROFILE} → 업로드 → complete → PATCH /api/me/profile {profileImageId} (§4-4 연결)
  → 실패하면 조용히 기본 이미지로 두고 "소셜 사진을 가져오지 못했어요. 설정에서 직접 올릴 수 있어요" 안내
```

| 항목 | 규칙 |
|---|---|
| 사진 주소 | 서버가 소셜 로그인 응답에서 받는다. Google `picture`(크기 매개변수를 256으로: `=s256-c`), GitHub `avatar_url`(`&s=256` 추가) |
| 허용 호스트 | `lh3.googleusercontent.com`, `avatars.githubusercontent.com`만. 서버가 가입 마무리 화면에 주소를 넘기기 전에 호스트를 확인하고, HTTPS가 아니거나 다른 호스트면 넘기지 않는다 |
| CSP | **가입 마무리 화면의 CSP `img-src`에만** 위 두 호스트를 더한다 (화면별 CSP). 다른 화면에는 넣지 않는다. 이 화면은 소셜 콜백 리다이렉트로 **전체 페이지로 열고**, 가입을 마치면 전체 페이지 이동으로 나간다 (12 §8). 저장소로 올리는 요청은 사이트 공통 `connect-src`의 저장소 공개 주소로 허용된다 (12 §8, 10/7 H3) |
| 서버는 외부 주소를 요청하지 않는다 | 사진 바이트는 브라우저 → 우리 저장소로만 흐른다. 서버는 04의 complete 검사만 한다 |
| 복사본 | 가입할 때 한 번 복사한다. 이후 소셜 쪽 사진을 바꿔도 따라 바뀌지 않는다 (원하면 설정에서 직접 올림) |
| 순서 | 가입 마무리 전에는 계정이 없어서 업로드할 수 없다 (07: 마무리 전 계정 미생성). 그래서 **계정을 만든 직후** 브라우저가 이어서 처리한다 |
| 소셜 사진이 없는 계정 | Google은 이름 첫 글자 이미지, GitHub은 기본 무늬 이미지를 준다. 그대로 가져온다 (체크를 끄면 우리 기본 이미지) |

### 4-3. 기본 이미지

이미지가 없으면 **닉네임 첫 글자가 들어간 동그란 아이콘**을 보여준다.

```
 ( 김 )   ( K )   ( 박 )
```

| 항목 | 규칙 |
|---|---|
| 글자 | 닉네임 첫 글자 (영문은 대문자로) |
| 배경색 | 블로그 주소의 해시값으로 미리 정한 8가지 색 중 하나. 사람마다 다르고 항상 같다. 라이트·다크 모드 모두 글자와 명도 대비 4.5:1 이상 |
| 구현 | 화면에서 SVG/CSS로 그린다. 파일을 저장하지 않는다 |
| [기본 이미지로] | 연결을 끊는다 (§4-4) |

### 4-4. 연결과 정리 (R-7)

회원 테이블에는 사진 컬럼이 없다 (2026-10-07 회의). **지금 프로필 사진은 `image`의 아래 조건 행 하나**이고, 회원당 하나는 `uq_image_profile_current`(부분 UNIQUE)가 보장한다.

```sql
-- 지금 프로필 사진
uploader_id = :memberId AND purpose = 'PROFILE' AND status = 'ATTACHED' AND detached_at IS NULL
```

| 동작 | 처리 (한 트랜잭션) |
|---|---|
| 새 이미지 연결 | ① `member` 행을 `FOR UPDATE`로 잠가 같은 회원의 동시 저장을 한 줄로 세운다 → ② 지금 프로필 사진에 `detached_at = now()` → ③ 새 이미지에 `status = ATTACHED`, `detached_at = NULL`. **떼기 → 붙이기 순서**여야 `uq_image_profile_current`에 걸리지 않는다 |
| 기본 이미지로 | 지금 프로필 사진에 `detached_at = now()`만. 조건에 맞는 행이 없으면 기본 이미지(§4-3) |
| 정리 배치 (04 §4-4) | `TEMP` 24시간, `detached_at` 7일이 지난 이미지 삭제. **`ATTACHED`이고 `detached_at IS NULL`인 프로필 사진은 지우지 않는다** |

```sql
-- 새 이미지 연결 (한 트랜잭션, :newId는 §5 이미지 ID 검사를 통과한 값)
SELECT id FROM member WHERE id = :me FOR UPDATE;
UPDATE image SET detached_at = now()
 WHERE uploader_id = :me AND purpose = 'PROFILE' AND status = 'ATTACHED' AND detached_at IS NULL;
UPDATE image SET status = 'ATTACHED', detached_at = NULL
 WHERE id = :newId AND uploader_id = :me AND purpose = 'PROFILE';
```

**작성자 사진을 보여 줄 때.** 목록 카드·글 상세·댓글은 `image`를 LEFT JOIN해 주소를 만든다. 주소는 저장하지 않고 `ImageStorage.publicUrl(COALESCE(thumb_storage_key, storage_key))`, 즉 공개 주소(`blog.image.public-base-url`) + 저장 키로 만든다 (23 §2-4). 프로필 사진은 썸네일을 만들지 않으므로 보통 `storage_key`가 쓰인다. 공개 주소가 바뀌어도 갱신할 복사 컬럼이 없다.

```sql
SELECT m.id, m.nickname, pi.storage_key, pi.thumb_storage_key
FROM member m
LEFT JOIN image pi ON pi.uploader_id = m.id AND pi.purpose = 'PROFILE'
                  AND pi.status = 'ATTACHED' AND pi.detached_at IS NULL   -- uq_image_profile_current
WHERE m.id = ANY(:authorIds);
```

## 5. 저장

```
PATCH /api/me/profile
{ "nickname": "김민서", "bio": "백엔드 개발을 공부하고 있어요.", "profileImageId": 87 }
```

| 항목 | 규칙 |
|---|---|
| 대상 | 주소에 회원 ID가 없다. **로그인한 본인만** 수정 (남의 프로필을 고칠 경로가 없다) |
| 보내는 값 | 바꾸려는 칸만 보낸다. `profileImageId: null`은 기본 이미지로 |
| 검사 | 닉네임(09), 소개(§3), 이미지(아래)를 모두 검사. **하나라도 실패하면 아무것도 저장하지 않고** 실패한 칸을 모두 돌려준다 |
| 이미지 ID 검사 | 본인이 올렸고(`uploader_id = 나`), `purpose = PROFILE`이고, 삭제되지 않은 이미지여야 한다. 아니면 400 `INVALID_PROFILE_IMAGE`. 연결은 §4-4 순서 |
| 닉네임 30일 제한 중 | 닉네임 칸만 비활성화, 서버도 `409 NICKNAME_CHANGE_TOO_SOON`. 다른 칸은 저장된다 — 단, 같은 요청에 닉네임 변경이 들어 있으면 전체 실패 (R-8) |
| 동시 수정 | 나중에 저장한 쪽이 반영된다 |
| 반영 | 목록·글 상세·댓글은 회원 정보와 프로필 사진(`image`, §4-4)을 JOIN해서 보여주므로 즉시 반영 |

검사 실패는 400, 본문은 공통 오류 형식 `{ code, message, errors: [{ field, code, message }], details }` (2026-10-07 O8).

```json
{ "code": "VALIDATION_FAILED",
  "message": "입력값을 확인해 주세요",
  "errors": [ { "field": "bio", "code": "BIO_TOO_LONG", "message": "소개는 200자까지 쓸 수 있어요" } ],
  "details": null }
```

## 6. 계정 설정

### 6-1. 이메일·로그인 수단
읽기 전용으로 보여준다. 이메일은 바꿀 수 없다 (R-9). 로그인 수단은 계정당 하나다 (07 L-1). 직전 로그인은 §6-4.

### 6-2. 비밀번호 변경 (R-10, 이메일 가입만)

```
POST /api/me/password
{ "currentPassword": "…", "newPassword": "…", "newPasswordConfirm": "…" }
```

| 항목 | 규칙 |
|---|---|
| 대상 | `LOCAL` 계정만. 소셜 계정은 버튼을 보이지 않고, 서버도 `400 PASSWORD_NOT_SUPPORTED` |
| 새 비밀번호 | 07 §4 규칙 (8~16자, 영문·숫자·특수문자 각 1개 이상, 금지 목록). 현재 비밀번호와 같으면 `400 PASSWORD_SAME_AS_CURRENT` |
| 현재 비밀번호를 틀리면 | `400 CURRENT_PASSWORD_MISMATCH`. 로그인과 같이 5회 연속 실패하면 15분 잠금 (세션을 탈취한 사람이 비밀번호를 추측하지 못하게) |
| 변경 후 | **다른 기기의 세션은 모두 끊고, 지금 기기는 유지**(세션 ID는 새로 발급). "비밀번호가 변경됐어요. 본인이 아니라면 [비밀번호 재설정]" 알림 메일 |

### 6-3. 새 글 기본 공개 범위
`PATCH /api/me/settings {"defaultVisibility": "PRIVATE"}`. `PUBLIC` / `PRIVATE` (친구 공개 규격 적용자는 `FRIENDS`). 06 §5.

### 6-4. 직전 로그인·최근 활동 (R-11·R-12, 2026-10-07 회의)

| 항목 | 규칙 |
|---|---|
| 직전 로그인 | 계정 영역에 "직전 로그인: 2026.10.07 14:03, Google"처럼 **이번 로그인 바로 전**의 일자와 로그인 방식을 보여 준다. 로그인 성공 때 `auth_identity.last_login_at`을 갱신하기 전 값을 세션(`previousLoginAt`)에 담아 두고 그것을 쓴다 (07 §6). 첫 로그인이면 "첫 로그인". 본인에게만 보인다 (계정 도용 확인용, 스키마 변경 없음) |
| 최근 활동 설정 | "최근 활동을 친구에게 보이기" 토글, **기본 켬**. `PATCH /api/me/settings {"lastActiveVisible": false}` → `member.last_active_visible` |
| 보이는 사람 | 친구(`friendship` ACCEPTED)만. 친구 맺기(요청·수락)는 공통으로 동작한다 (`FRIENDS` 공개 범위는 선택 기능) |
| 표시 | `member.last_active_at`을 **"오늘·어제·N일 전·1주 이상"**으로만 보여 준다 (정확한 시각은 보이지 않음). 값이 없으면 표시하지 않는다 |
| 서로 보기 | **내가 끄면 나도 친구의 최근 활동을 볼 수 없다.** 상대가 꺼도 그 사람 것은 보이지 않는다 |
| 갱신 | 로그인한 요청이 올 때 한 시간에 한 번 정도 `last_active_at` 갱신 (Redis로 갱신 간격 조절) |
| 탈퇴 | 익명 처리 때 `last_active_at`을 비운다 (13 §3) |
| 처리방침 | 개인정보 처리방침에 "친구에게 최근 활동 시점 표시"를 적는다 (H9) |

## 7. 스키마

기준은 [`erd/V1__common_schema.sql`](../erd/V1__common_schema.sql)이다 ([03-erd.md](./03-erd.md)는 설명용).

| 변경 | 내용 |
|---|---|
| `member.bio` | `varchar(200)` + CHECK `char_length(bio) <= 200` |
| 프로필 사진 | **회원 테이블에 사진 컬럼 없음** (`member.profile_image_id`·`profile_image_url` 삭제, 2026-10-07 회의). 지금 프로필 사진은 `image` 행으로 판별하고, 회원당 하나는 `uq_image_profile_current ON image (uploader_id) WHERE purpose = 'PROFILE' AND status = 'ATTACHED' AND detached_at IS NULL` (§4-4) |

## 8. 공통 완료 기준 (C-AUTH-2)

| # | 기준 |
|---|---|
| 1 | 닉네임·소개·프로필 이미지는 본인만 바꿀 수 있고, 블로그 주소·이메일은 바꿀 수 없다 |
| 2 | 하나라도 검사에 실패하면 프로필의 어떤 값도 바뀌지 않는다 |
| 3 | 소개의 HTML은 실행되지 않고 글자로 보인다 |
| 4 | 프로필 이미지는 256×256이 아니거나 남의 이미지·글용 이미지면 연결되지 않는다 |
| 5 | 연결된 프로필 이미지는 회원당 하나이고 정리 배치가 지우지 않으며, 바꾼 이전 이미지는 7일 뒤 지워진다 |
| 6 | 소셜 가입 때 소셜 사진을 가져오면 우리 저장소의 복사본이 프로필 사진(`image` 행)으로 연결된다 (소셜 주소를 저장하지 않고, 소셜 사진 호스트는 가입 마무리 화면 CSP에만 있다) |
| 7 | 비밀번호를 바꾸면 다른 기기는 로그아웃되고 알림 메일이 간다. 소셜 계정은 비밀번호를 바꿀 수 없다 |
| 8 | 계정 화면에 직전 로그인 일자와 로그인 방식이 보인다 (방금 한 로그인이 아니라 그 전 로그인, 첫 로그인이면 "첫 로그인") |
| 9 | 최근 활동은 친구에게만 "오늘·어제·N일 전·1주 이상"으로 보이고, 끄면 내 것도 안 보이고 나도 친구 것을 못 본다 |
