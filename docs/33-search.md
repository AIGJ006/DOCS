# 검색 설계

> 작성일 2026-10-05 · 담당: 김민서 · 관련: Tier C "검색 (제목·본문, 공개 글만)" (강성찬 OPEN-04, 나민서 SRC-01~05, 김민서 SEARCH-1·PERF-6)
> 이미 결정된 것을 따른다: 공개 범위·휴지통·탈퇴 공용 조건(06 §7, 13), 목록 카드·9개·[더 보기](10), 본문 정화(12), 닉네임·블로그 주소(08·09).

## 1. 결정 사항

| # | 안건 | 결정 | 근거 |
|---|---|---|---|
| Q-1 | 탭 | **글**(기본) + **사람**(닉네임·`@블로그주소`) | 회원 = 블로그라서 나민서의 "블로그 검색"은 사람 탭과 같다 |
| Q-2 | 검색어 길이 | 단어마다 **1글자는 무시, 2글자는 제목·태그만, 3글자 이상은 제목·태그·본문** | 측정: 드문 2글자 본문 검색은 인덱스를 못 써서 **400~2,055ms**, 제목만이면 34ms (§8) |
| Q-3 | 여러 단어 | 띄어쓰기로 나눈 단어가 **모두** 있어야 한다 (AND). 최대 5단어·50자 | |
| Q-4 | 관련도 | **단계별:** ① 제목에 모두 있음 → ② 제목·태그에 모두 있음 → ③ 본문까지 포함해 모두 있음. 단계 안에서는 최신순. 점수는 매기지 않는다 | 설명하기 쉽고, 단계마다 최신순이라 9개를 찾으면 멈출 수 있다 |
| Q-5 | 실행 | **최근 글 3,000개 안에서 먼저** 찾고, 모자라면 **인덱스로 전체**에서 찾는다 | 측정: 흔한 단어를 전부 모아 정렬하면 460ms → 이 방식으로 0.4~6ms |
| Q-6 | 결과 카드 | 10 문서 카드 + 미리보기 자리에 **검색어가 나온 부분의 앞뒤 문장**, 검색어는 `<mark>`로 강조 (**이스케이프한 뒤**) | |
| Q-7 | 블로그 안 검색 | **공통에 포함** (`/@주소?q=…`) | 작성자 조건 하나만 더하면 된다 (나민서 SRC-02) |
| Q-8 | 요청 제한·검색 엔진 | 같은 방문자 1분에 30번, 검색 결과 페이지 `noindex` | |
| Q-9 | 공통에서 뺄 것 | 기간·주제 조건, 의미·하이브리드 검색, 자동 완성, 인기 검색어, `pg_bigm`, Elasticsearch·OpenSearch | 개인 확장 |

## 2. 검색어 처리

```
입력 "  트랜잭션  정리 a  " 
 → NFC 정규화, 앞뒤 공백 제거, 50자로 자름
 → 띄어쓰기로 나눔: [트랜잭션, 정리, a]
 → 1글자 무시: [트랜잭션, 정리]           (최대 5단어)
 → 단어마다 찾는 곳:  트랜잭션(4자) → 제목·태그·본문 / 정리(2자) → 제목·태그만
 → 모든 단어가 있어야 결과 (AND)
```

| 항목 | 규칙 |
|---|---|
| 대소문자 | 무시 (`ILIKE`) |
| 특수문자 | `%`, `_`, `\`는 이스케이프해서 **글자 그대로** 찾는다 (`'100%'`가 "100으로 시작하는 모든 것"이 되지 않게) |
| 태그 비교 | 검색어를 소문자로 바꿔 태그 이름과 부분 일치 (강성찬 C-TAG-1 정규화와 같은 방식) |
| 본문 | `content_md`(Markdown 원문). 코드 블록 안의 글자도 찾는다 (개발 글) |
| 빈 검색어 | 단어가 하나도 남지 않으면 "두 글자 이상 입력해 주세요" |
| 2글자 안내 | 2글자 단어가 있으면 결과 위에 "두 글자 단어는 제목·태그에서만 찾았어요" |

## 3. 정렬

### 3-1. 관련도순 (기본)

| 단계 | 조건 | 예: "롬복" |
|---|---|---|
| ① | 모든 단어가 **제목**에 있음 | 제목에 "롬복"이 있는 글 |
| ② | ①이 아니고, 모든 단어가 **제목 또는 태그**에 있음 | 태그가 `롬복`인 글 |
| ③ | ①②가 아니고, 모든 단어가 **제목·태그·본문(3글자 이상만)** 어딘가에 있음 | (2글자라 본문은 찾지 않음) |

단계 안에서는 `first_public_at` 최신 → ID 큰 순. 한 단계가 끝나면 같은 페이지에서 다음 단계로 이어서 9개를 채운다.

### 3-2. 최신순

모든 단어가 어딘가에 있는 글을 `first_public_at` 최신순으로.

### 3-3. 커서

`{단계}:{first_public_at}:{id}` (최신순은 단계 `0`). 다음 페이지는 같은 단계에서 커서 이후부터, 단계가 끝나면 다음 단계 처음부터.

## 4. 실행 방식

```
단계마다 (최신순은 한 번):
 ① [최근창] 커서 이후 최근 글 3,000개 안에서 조건에 맞는 글을 최신순으로 10개
    → 10개를 찾으면 끝. 이것이 곧 전체에서 가장 최신인 10개와 같다
 ② [인덱스] 모자라면(그리고 최근 글이 3,000개보다 많으면):
    가장 긴 단어 하나로 "제목 / 태그 / 본문(3글자 이상)"을 각각 인덱스로 조회해 후보를 합치고(UNION),
    그 후보에서 전체 조건을 확인해 최신순 10개
 (10개 = 9개 + 다음 페이지가 있는지 확인용 1개)
```

```sql
-- ② 인덱스 단계 (③단계, 단어 "희귀어사전" 예)
SELECT p.id, p.first_public_at
FROM post p JOIN member m ON m.id = p.author_id
WHERE p.id IN (
        SELECT id FROM post WHERE title ILIKE :t                         -- ix_post_title_trgm
        UNION SELECT pt.post_id FROM post_tag pt JOIN tag g ON g.id = pt.tag_id
              WHERE g.name ILIKE :t
        UNION SELECT id FROM post WHERE content_md ILIKE :t)             -- ix_post_content_trgm
  AND p.status = 'PUBLISHED' AND p.visibility = 'PUBLIC' AND p.deleted_at IS NULL
  AND m.withdrawn_at IS NULL
  AND (p.first_public_at, p.id) < (:cursorAt, :cursorId)
  AND <단계 조건 (§3-1)>
ORDER BY p.first_public_at DESC, p.id DESC
LIMIT 10;
```

| 항목 | 규칙 |
|---|---|
| 최근창 크기 | 설정값 `blog.search.recent-window=3000`. 실제 데이터가 쌓이면 다시 재서 조정 (1,000이면 드문 단어가 68ms → 24ms) |
| 후보를 따로 조회하는 이유 | 태그 조건(`EXISTS`)이 `OR`에 섞여 있으면 DB가 본문 인덱스를 쓰지 못한다. 처음 구현에서 이 때문에 1,129ms가 걸렸다 (§8) |
| 공개 범위 조건 | 06 §7 공용 조건(`VisibilityFilter`)을 그대로 쓴다. 친구 공개 글은 검색에 나오지 않는다 (06 §3) |
| 블로그 안 검색 | `AND p.author_id = :blogOwner`만 더한다 |


```json
{ "items": [ { "id": 95001, "url": "/@user002/posts/95001", "title": "…",
               "snippetHtml": "…배포 환경을 구성했다. <mark>희귀어사전</mark> &lt;script&gt;…",
               "thumbnailUrl": "…", "firstPublicAt": "…", "commentCount": 0, "likeCount": 0,
```

| 항목 | 규칙 |
|---|---|
| 글 카드 | 10 §2 카드. 미리보기 3줄 자리에 `snippetHtml` |
| 검색어 주변 문장 | 본문(없으면 제목)에서 첫 번째로 나온 곳의 앞뒤 40자, 앞뒤가 잘리면 `…` |
| **강조 순서** | **① 문장 전체를 HTML 이스케이프 → ② 이스케이프된 검색어에 `<mark>`.** 순서를 바꾸면 `<mark>`가 글자로 깨지고, 이스케이프를 빠뜨리면 본문의 `<script>`가 실행된다 |
| 사람 결과 | 프로필 이미지 · 닉네임 · `@주소` · 소개 첫 줄. 닉네임·주소가 정확히 일치하면 먼저, 탈퇴 신청한 회원 제외, 최대 20명 |
| 빈 결과 | "'롬복'에 대한 글이 없어요" (+ 2글자 안내) |
| 요청 제한 | 같은 방문자 키(31 §2-1과 같은 키) 1분에 30번, 넘으면 429 |
| 검색 엔진 | 검색 결과 페이지는 `<meta name="robots" content="noindex">` |
| 기록 | 검색어를 회원 정보와 함께 저장하지 않는다. 운영 로그에는 검색어 길이와 걸린 시간만 |

## 6. 인덱스

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ix_post_title_trgm      ON post   USING gin (title gin_trgm_ops);
CREATE INDEX ix_post_content_trgm    ON post   USING gin (content_md gin_trgm_ops);
CREATE INDEX ix_member_nickname_trgm ON member USING gin (nickname gin_trgm_ops);
CREATE INDEX ix_member_handle_trgm   ON member USING gin (handle gin_trgm_ops);
```

- trigram은 **3글자 단위**로 쪼개서 색인한다. 그래서 2글자 검색어는 인덱스를 쓰지 못한다 (Q-2의 이유).
- 본문 인덱스는 글이 늘면 커진다. 실제 데이터에서 크기를 재고, 너무 크면 본문 검색 범위를 줄이는 것을 검토한다.

## 8. 검증 결과 (2026-10-05, PostgreSQL 18, 실제 스키마 + 글 10만 개, 본문 평균 1,990자)

### 8-1. 설계 전 측정 — 왜 이렇게 정했나

| 측정 | 결과 | 반영 |
|---|---|---|
| 드문 2글자 "희귀"·"롬복" 제목+본문 | 400ms·1,200ms (전체 스캔), 인덱스로 강제해도 45~266ms | Q-2: 2글자는 제목·태그만 |
| 2글자 "롬복" 제목만 | 34ms | |
| 드문 3글자 이상 | 0.5ms (인덱스) | |
| 흔한 단어(일치 25,000개)를 정렬해 9개 | 460~476ms | Q-5: 최근창 먼저 |
| 본문 압축을 끄면 | 오히려 느려짐 (515ms, 저장 공간 16배) | 압축 유지 |
| 최근 3,000개 먼저 → 모자라면 인덱스 | 흔한 0.8ms, 중간 빈도 20ms, 드문 61ms | Q-5 채택 |

### 8-2. 최종 설계 검증 (실제 `post`·`member`·`tag` 스키마)

| 검색 | 결과 | 가장 느린 요청 |
|---|---|---|
| "롬복" (2글자) | ① 제목 3개 → ② 태그 3개. **본문에만 있는 3개는 제외**, 비공개·휴지통·탈퇴자 글도 제외. 2글자 안내 표시 | 101ms |
| "희귀어사전" (드문 단어) | ① 제목 1개 → ③ 본문 20개, 3페이지, 중복 0 | 68ms |
| "트랜잭션 정리" (4글자 + 2글자) | ① 제목에 둘 다 있는 글 최신순, 2페이지 중복 0 | 0.5ms |
| "REQUIRES_NEW" 최신순 / 관련도순 | 최신순으로 2페이지, 중복 0 | 0.9ms / 6.0ms |
| "100% 할인", "snake_case" | 각각 정확히 그 글 하나 (`%`·`_`를 와일드카드로 해석하지 않음) | — |
| 블로그 안 검색 | 그 작성자의 글만 | 16ms |
| 사람 검색 "김민서", "kim7550" | 활동 중인 회원만 (탈퇴 신청한 같은 닉네임 회원 제외), 정확히 일치가 먼저 | — |
| 강조 | 결과 HTML에 `<mark>` 외 태그 없음. 본문의 `<script>`, `<img onerror>`는 글자로 | — |

> 처음 구현에서는 인덱스 단계 조건에 태그 `EXISTS`가 `OR`로 섞여 있어 본문 인덱스를 쓰지 못했고, 최근창을 단계마다 반복해서 **1,129ms**가 걸렸다. 후보를 제목·태그·본문으로 따로 조회해 합치도록(§4) 바꿔 68ms로 줄였다.
>
> 테스트 데이터는 같은 문장을 반복해 만든 것이라 실제 글보다 단순하다. 구현 후 실제와 비슷한 데이터로 다시 재야 한다.
