## User Scenarios & Testing *(mandatory)*

### User Story 1 - 글에 사진 넣기 (Priority: P1)

이메일 인증을 마친 회원이 에디터에 사진을 붙여넣거나 끌어놓으면, 사진은 브라우저에서 가볍게 줄이고 촬영 위치 같은 메타데이터를 지운 뒤 곧바로 사진 저장소에 올라간다. 본문에는 사진 데이터가 아니라 사진 주소만 남고, 다음 자동 저장 때 함께 저장된다. 목록 카드에 쓸 작은 썸네일도 같은 순간에 만들어진다.

**Why this priority**: C-IMG-1(Tier B)의 핵심이다. 사진을 넣을 수 없으면 글 카드 썸네일(C-READ-1)과 본문 사진 모두 동작하지 않는다.

**Independent Test**: 인증된 회원으로 5MB 휴대폰 사진(GPS 정보 포함)을 붙여넣고, 본문에 사진 주소가 들어가고 사진이 보이며, 올라간 파일에서 위치 정보가 사라졌고, 파일 이름이 서버가 만든 무작위 이름인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 인증된 회원이 에디터를 열었을 때, **When** 5MB JPEG 사진을 붙여넣으면, **Then** 긴 변 1920px 이하·WebP로 줄어든 원본과 가로 640px 이하 썸네일이 올라가고, 본문에는 사진 주소만 들어가며 사진이 화면에 보인다 (C-IMG-1).
2. **Given** 사진에 촬영 위치(EXIF GPS)가 들어 있을 때, **When** 업로드가 끝나면, **Then** 저장된 원본·썸네일 어디에도 촬영 위치가 남아 있지 않다.
3. **Given** 확장자만 `.jpg`로 바꾼 다른 형식의 파일(확장자 위장)일 때, **When** 업로드 완료 확인을 하면, **Then** 서버가 실제 파일 내용으로 형식을 판별해 거부하고 올라간 파일을 지운다 (C-IMG-1).
4. **Given** 10MB를 넘는 파일이거나 jpg·png·gif·webp가 아닌 형식일 때, **When** 업로드를 요청하면, **Then** 업로드가 거부된다 (C-IMG-1).
5. **Given** 업로드가 끝난 사진일 때, **When** 저장 이름을 확인하면, **Then** 서버가 만든 추측할 수 없는 이름이고 원래 파일 이름은 어디에도 저장·표시되지 않는다 (C-IMG-1, 2026-10-07 회의).
6. **Given** 비회원이거나 이메일 인증 전 회원일 때, **When** 사진 업로드를 요청하면, **Then** 비회원은 로그인 필요, 인증 전 회원은 이메일 인증 필요로 거부된다 (42 §10, 07 L-2).
7. **Given** 한 회원이 1분 안에 사진 20장을 올렸을 때, **When** 21번째 업로드를 요청하면, **Then** 요청 횟수 초과로 거부된다 (04 §4-2).

### User Story 2 - 내 사진은 나만 내 글에 연결된다 (Priority: P1)

사진은 올린 사람의 것이다. 다른 사람이 내 사진 주소를 자기 글에 붙여 넣어도 그 사람 글에 연결되지 않고 링크로만 보이며, 내 사진이 그 사람 때문에 지워지거나, 그 사람 용량에서 빠지거나, 내 비공개 글의 사진이 그 사람 글을 통해 공개 이미지로 보이지 않는다.

**Why this priority**: 남의 사진을 연결할 수 있으면 원래 주인의 사진이 정리 배치에서 지워지거나 비공개 글 사진이 다시 공개되는 보안·데이터 손실 문제가 생긴다 (23 §6-1, 2026-10-07 회의 채택).

**Independent Test**: 회원 2명으로, A가 올린 사진 주소를 B의 글 본문에 넣고 발행한 뒤 B의 글에서는 링크로 보이고, A의 글에서는 그대로 이미지로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원 A가 올린 사진 주소를 회원 B가 자기 글에 넣었을 때, **When** B가 발행하면, **Then** 그 사진은 B의 글에 연결되지 않고 외부 이미지처럼 링크로 표시되며, A의 글에서는 그대로 보인다 (23 §7 #9).
2. **Given** 회원 B가 A의 업로드 번호로 업로드 완료 확인을 요청할 때, **When** 서버가 처리하면, **Then** 없는 사진과 같은 404로 응답한다 (23 §6-1).
3. **Given** 사진 주소를 아는 사람일 때, **When** 비공개 글에 들어 있는 사진 주소를 직접 열면, **Then** 사진을 볼 수 있다 (04 결정 2, 주소를 알면 보임). 단, 저장소의 사진 목록은 누구도 익명으로 조회할 수 없다 (23 §2-2).

### User Story 3 - 오프라인·실패 시에도 사진을 잃지 않는다 (Priority: P2)

네트워크가 끊겼거나 업로드가 실패해도 사진은 이 기기에 보관되고 에디터에는 정상적으로 보인다. 연결되면 자동으로 다시 올라가고 진짜 주소로 바뀐다. 다만 아직 올라가지 않은 사진이 남아 있으면 발행은 막힌다.

**Why this priority**: 자동 저장(C-POST-2)의 "사라지지 않는다" 약속을 사진에도 지킨다. 핵심 업로드(US1) 위에 붙는 신뢰성 기능이다.

**Independent Test**: 오프라인 상태에서 사진을 붙여넣고, 에디터에 보이는지, 자동 저장이 계속되는지, 발행이 거부되는지, 다시 연결하면 진짜 주소로 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 오프라인 상태일 때, **When** 사진을 붙여넣으면, **Then** 사진은 이 기기에 보관되고 본문에는 임시 표시가 들어가며 화면에는 사진이 정상적으로 보인다 (04 §4-3).
2. **Given** 임시 표시 사진이 있는 글일 때, **When** 자동 저장이 실행되면, **Then** 자동 저장은 그대로 성공한다.
3. **Given** 임시 표시 사진이 남아 있을 때, **When** 발행을 요청하면, **Then** 발행이 거부된다 (04 §4-3, 05 §7).
4. **Given** 연결이 다시 살아났을 때, **When** 자동 재시도가 성공하면, **Then** 임시 표시가 진짜 사진 주소로 바뀐다.

### User Story 4 - 사용자별 저장 공간 한도 (Priority: P2)

한 사람이 저장소를 가득 채우지 못하게 1인 1GB, 하루 200장까지만 올릴 수 있다. 회원은 설정에서 지금 얼마나 썼는지 보고, 한도에 가까워지거나 넘으면 에디터에서 안내를 받는다.

**Why this priority**: 공유 저장소 보호. 업로드(US1)가 있어야 의미가 있다.

**Independent Test**: 사용량을 1GB 가까이 채운 회원으로 동시에 10건의 업로드 준비를 요청해 한도를 넘지 않는지, 하루 201번째 요청이 거부되는지, 설정 화면에 사용량이 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 지금 사용량 + 이번에 올릴 원본·썸네일 크기가 1GB를 넘을 때, **When** 업로드 준비를 요청하면, **Then** 저장 공간 초과로 거부되고 에디터에 "사진 저장 공간(1GB)을 다 썼어요. 쓰지 않는 사진이 든 글을 지우면 7일 뒤 공간이 돌아와요"가 보인다 (23 §3).
2. **Given** 한도 근처의 회원이 업로드 준비를 동시에 10건 요청할 때, **When** 모두 처리되면, **Then** 합계가 1GB를 넘는 요청은 하나도 받아들여지지 않는다 (23 §7 #1).
3. **Given** 오늘(한국 시간 0시 기준) 이미 200장을 요청했을 때, **When** 201번째를 요청하면, **Then** 하루 한도 초과로 거부되고 "오늘은 사진을 200장까지 올릴 수 있어요. 내일 다시 시도해 주세요"가 보인다 (23 §7 #2).
4. **Given** 회원이 설정 화면을 열었을 때, **When** 사진 저장 공간 항목을 보면, **Then** "사진 저장 공간 312MB / 1GB" 막대와 "지운 사진의 공간은 7일 뒤 돌아와요"가 보인다.
5. **Given** 사용량이 90%를 넘었을 때, **When** 에디터를 열면, **Then** 사진 버튼 옆에 "남은 공간 약 100MB" 같은 안내가 보인다.

### User Story 5 - 대체글 권유 (Priority: P2)

사진에 대체글(화면 낭독기가 읽어 줄 설명)을 넣도록 발행 설정에서 권유하지만, 넣지 않아도 발행은 된다. 빈 대체글은 꾸밈 이미지로 처리되고 원래 파일 이름은 절대 쓰지 않는다.

**Why this priority**: 접근성 기본기이지만 발행을 막지 않는 보조 기능이다 (23 I-3).

**Independent Test**: 대체글 없는 사진 2장이 든 글을 발행하면서 안내가 뜨는지, 무시하고 발행해도 성공하는지, 결과 화면에서 빈 대체글로 그려지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 에디터가 사진을 본문에 넣을 때, **When** 넣은 결과를 보면, **Then** 대체글 자리는 비어 있고 원래 파일 이름이 들어가지 않는다.
2. **Given** 대체글이 없는 사진이 2장 있는 글일 때, **When** 발행 설정 창을 열면, **Then** "대체글이 없는 사진이 2장 있어요 [대체글 넣기]" 안내가 보이고, 누르면 사진마다 작은 미리보기와 입력칸이 나오며 입력한 값이 본문에 반영된다.
3. **Given** 대체글을 넣지 않았을 때, **When** 발행하면, **Then** 발행은 성공하고 그 사진은 빈 대체글(꾸밈 이미지)로 그려진다 (23 §7 #3).

### User Story 6 - 움직이는 GIF (Priority: P3)

GIF는 변환 없이 그대로 올라가 움직임이 살아 있다. 본문에서는 처음에 첫 장면과 ▶ 표시만 보이고, 누르면 재생된다. 너무 크거나 프레임이 많은 GIF는 거부된다.

**Why this priority**: 데이터 절약과 접근성(계속 움직이는 화면 줄이기)을 위한 개선이다. 일반 사진 업로드 없이는 의미가 없다.

**Independent Test**: 1920px 이하·300프레임 이하 GIF를 올려 글 상세에서 정지 장면 + ▶ → 클릭 시 재생을 확인하고, 2000px GIF와 301프레임 GIF가 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가로·세로 1920px 이하, 300프레임 이하, 10MB 이하 GIF일 때, **When** 올리면, **Then** 원본은 압축·변환 없이 저장되고 썸네일은 첫 장면으로 만들어진다.
2. **Given** 가로나 세로가 1920px를 넘는 GIF를 고를 때, **When** 고르는 순간, **Then** "GIF는 가로·세로 1920px까지 올릴 수 있어요"가 보이고, 우회해서 올려도 서버 확인에서 거부되고 파일이 지워진다 (23 §7 #5).
3. **Given** 프레임이 300장을 넘는 GIF일 때, **When** 업로드 완료 확인을 하면, **Then** 거부되고 파일이 지워진다.
4. **Given** 본문에 GIF가 있는 글 상세일 때, **When** 독자가 처음 보면, **Then** 첫 장면 정지 이미지와 ▶ 표시가 보이고, 누르거나 키보드 Enter를 누르면 원본이 재생되며, 다시 누르면 정지 장면으로 돌아간다 (23 §7 #4).
5. **Given** 스크립트가 동작하지 않는 환경일 때, **When** 정지 이미지를 누르면, **Then** 원본 GIF가 새 탭에서 열린다.

### User Story 7 - 버려진 사진 정리 (Priority: P3)

올리기만 하고 글에 쓰지 않은 사진, 글에서 빠진 사진은 일정 기간 뒤 저장소와 기록에서 자동으로 지워져 공간이 돌아온다. 지금 쓰고 있는 프로필 사진은 지워지지 않는다.

**Why this priority**: 저장 공간 회수와 개인 정보 정리. 사용자에게 직접 보이는 기능은 아니다.

**Independent Test**: 연결하지 않은 지 24시간이 지난 사진, 글에서 빠진 지 7일이 지난 사진, 현재 프로필 사진을 준비하고 정리 배치를 돌린 뒤 앞의 둘만 지워졌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 올린 뒤 글에 연결되지 않고 24시간이 지난 사진일 때, **When** 매일 새벽 정리가 돌면, **Then** 원본·썸네일 파일과 기록이 지워지고 사용량에서 빠진다 (04 §4-4).
2. **Given** 글에 연결되었다가 빠진 지 7일이 지난 사진일 때, **When** 정리가 돌면, **Then** 파일과 기록이 지워진다.
3. **Given** 지금 쓰고 있는 프로필 사진일 때, **When** 정리가 돌면, **Then** 지워지지 않는다.
4. **Given** 저장소에서 파일 삭제가 실패했을 때, **When** 정리가 끝나면, **Then** 기록은 남아 있고 다음 정리 때 다시 시도된다.

### User Story 8 - 사진 공개 주소를 바꿔도 옛 글 사진이 유지된다 (Priority: P3)

운영자가 사진을 내려주는 공개 주소(저장소 주소 → CDN 등)를 바꿔도, 옛 주소로 쓰인 우리 사진이 외부 이미지 링크로 바뀌지 않고 계속 이미지로 보인다.

**Why this priority**: 개발·운영·CDN 주소가 이미 서로 다르다 (23 I-5). 주소 변경은 드물지만 실패하면 모든 옛 글의 사진이 깨진다.

**Independent Test**: 공개 주소를 옛 주소·새 주소 두 개로 설정해 옛 주소로 쓴 본문을 다시 그리면 새 주소의 이미지로 보이는지, 목록에 없는 주소의 사진은 외부 이미지 링크가 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 옛 공개 주소로 쓰인 우리 사진이 있는 글일 때, **When** 공개 주소를 바꾸고 다시 렌더링하면, **Then** 그 사진은 지금 공개 주소의 이미지로 보이고 링크로 바뀌지 않는다 (23 §7 #8).
2. **Given** 공개 주소·옛 주소 목록 어디에도 없는 주소(예: 다른 환경의 로컬 주소)의 사진일 때, **When** 렌더링하면, **Then** 외부 이미지 링크가 된다 (의도된 동작).
3. **Given** 공개 주소를 바꿀 때, **When** 사용자가 쓴 원문을 확인하면, **Then** 원문은 바뀌지 않는다.

### Edge Cases

- 업로드 준비 후 5분 안에 파일을 올리지 않으면 업로드 권한이 만료되어 거부된다.
- 올린 파일의 실제 크기가 준비 때 신고한 크기보다 크면 완료 확인에서 거부되고 파일이 지워진다 (23 §3).
- 해상도가 비정상적으로 큰 사진(예: 1만 px 초과)이나 손상된 파일은 완료 확인에서 거부된다 (04 §4-1 ⑤).
- 썸네일이 가로 640px 또는 1MB를 넘으면 완료 확인에서 거부된다.
- 움직이는 WebP·APNG는 브라우저 처리 과정에서 첫 장면만 남는다. 움직임을 살리는 형식은 GIF뿐이며 업로드 화면에 안내한다 (23 §5-1).
- GIF의 XMP 같은 메타데이터는 서버가 파일을 고치지 않으므로 남을 수 있다 (알려진 한계, GIF에는 촬영 위치 EXIF가 없다).
- 실패한 업로드도 하루 200장에 1장으로 센다 (반복 요청 방지).
- 글을 지워도 사진 공간은 바로 돌아오지 않고, 정리가 실제로 파일을 지울 때 돌아온다 (글 완전 삭제 → 연결 해제 → 7일 뒤).
- 정리로 지운 사진도 이미 본 독자 브라우저에는 최대 1년 남을 수 있다 (허용 한계, 23 §6-3). 저장소에서는 즉시 찾을 수 없음이 된다.
- 같은 사진이 다른 글에서도 쓰이면, 한 글이 지워져도 연결 해제로 기록되지 않는다 (13 §2-5).
- 운영 저장소에서 브라우저 직접 업로드(교차 출처 허용)를 설정할 수 없으면 앱 서버를 거쳐 올리는 방식으로 바꾸되 규칙은 같다 (23 §2-2).
- 요청 횟수를 세는 기록을 쓸 수 없는 장애 중에는 요청 횟수 제한(1분 20장·하루 200장)이 통과된다 (02 §2-1).

## Requirements *(mandatory)*

### Functional Requirements

**형식·크기·브라우저 준비**

- **FR-001**: System MUST jpg·png·gif·webp 형식의 10MB 이하 사진만 받는다 (C-IMG-1).
- **FR-002**: 브라우저는 GIF가 아닌 사진을 올리기 전에 긴 변 최대 1920px로 줄이고, WebP(품질 0.8)로 바꾸고, 촬영 위치를 포함한 EXIF 메타데이터를 제거해야 한다 (04 §4-1 ②, C-IMG-1).
- **FR-003**: 브라우저는 모든 사진에 대해 가로 최대 640px의 WebP(품질 0.8) 썸네일을 함께 만들어 올려야 한다. GIF의 썸네일은 첫 장면 정지 이미지다 (10 L-8, 2026-10-07 O5 "640px 썸네일 생성은 공통 데이터 규칙").
- **FR-004**: 사진 데이터는 본문(자동 저장 경로)에 넣지 않고 올리는 즉시 사진 저장소로 업로드하며, 본문에는 사진 주소만 남긴다 (04 D-4). 사진 데이터는 앱 서버를 거치지 않고 브라우저에서 저장소로 직접 올라간다.

**업로드 절차·서버 검사**

- **FR-005**: System MUST 업로드 준비 요청에서 형식·크기·요청 횟수·저장 공간 한도를 확인한 뒤에만 원본·썸네일 두 개의 업로드 권한을 발급하고, 그 권한은 5분 뒤 만료된다 (04 §4-1 ③).
- **FR-006**: System MUST 업로드 완료 확인에서 요청한 사람이 그 사진을 올린 사람인지 먼저 확인하고, 아니면 없는 사진과 같은 404로 응답한다 (23 §6-1).
- **FR-007**: System MUST 업로드 완료 확인에서 두 파일의 존재, 실제 크기, 파일 앞부분 내용(매직 바이트)으로 판별한 실제 형식, 이미지 해상도를 다시 검사하고, 썸네일은 가로 640px·1MB 이하인지 확인한다. 하나라도 실패하면 파일을 지우고 거부한다. 형식 위장, 손상 파일, 초대형 해상도(예: 1만 px 초과)는 여기서 거부된다 (04 §4-1 ⑤).
- **FR-008**: System MUST 실제 크기를 완료 확인 때 기록하고, 준비 때 신고한 크기보다 크면 거부·삭제한다 (23 §3).
- **FR-009**: System MUST 저장 이름을 서버가 만든 추측할 수 없는 무작위 이름(연·월 단위 경로 + UUID)으로 정하고, 원래 파일 이름은 저장하지도 화면 어디에도 보여주지도 않는다 (C-IMG-1, 23 §4, 2026-10-07 회의).
- **FR-010**: 완료 확인을 통과하면 System MUST 사진 주소(지금의 공개 주소 + 저장 이름)를 돌려주고, 에디터는 임시 표시를 이 주소로 바꿔 다음 자동 저장 때 본문에 함께 저장한다 (04 §4-1 ⑥). 본문에는 절대 주소를 쓴다 (23 §2-4).
- **FR-011**: System MUST 사용자당 1분에 20장을 넘는 업로드 요청을 거부한다 (04 §4-2).
- **FR-012**: 비회원의 업로드 요청은 로그인 필요로, 이메일 인증 전 회원의 요청은 이메일 인증 필요로 거부해야 한다 (42 §10, 07 L-2). 판정 순서·응답 규칙은 → [specs/004-visibility-permission](../004-visibility-permission/spec.md).

**사용자별 저장 공간 (23 I-2)**

- **FR-013**: System MUST 사용자별 사진 저장 공간을 1GB, 하루 업로드를 200장(한국 시간 0시 기준)으로 제한하고, 두 값은 설정값으로 바꿀 수 있어야 한다.
- **FR-014**: 사용량은 그 사람이 올린 모든 사진(올리기만 한 것, 연결된 것, 연결이 끊겨 정리를 기다리는 것, 프로필 사진 포함)의 원본 + 썸네일 크기 합계로 센다. 다른 사람이 올린 사진은 내 사용량에 세지 않는다 (23 §3, §6-1).
- **FR-015**: System MUST 업로드 준비 때 "지금 사용량 + 이번에 올릴 원본·썸네일 크기"가 한도를 넘으면 저장 공간 초과로 거부하고, 여러 장을 동시에 요청해도 합계가 한도를 넘지 않게 해야 한다.
- **FR-016**: System MUST 하루 200장을 넘는 업로드 준비 요청을 하루 한도 초과로 거부하고, 실패한 업로드도 1장으로 센다.
- **FR-017**: 사용한 공간은 정리 작업이 파일을 실제로 지울 때 돌아온다. 글을 지워도 바로 돌아오지 않는다.
- **FR-018**: System MUST 본인의 사용량·한도·오늘 올린 장수·하루 한도를 보여주어야 한다. 설정 화면에 "사진 저장 공간 312MB / 1GB" 형태의 막대와 "지운 사진의 공간은 7일 뒤 돌아와요"를, 한도 초과 시 에디터에 "사진 저장 공간(1GB)을 다 썼어요. 쓰지 않는 사진이 든 글을 지우면 7일 뒤 공간이 돌아와요"를, 하루 한도 초과 시 "오늘은 사진을 200장까지 올릴 수 있어요. 내일 다시 시도해 주세요"를, 사용량이 90%를 넘으면 에디터 사진 버튼 옆에 남은 공간(예: "남은 공간 약 100MB")을 보여준다 (23 §3-1).

**오프라인·실패 (04 §4-3)**

- **FR-019**: 업로드가 실패하거나 오프라인이면 브라우저는 원본을 이 기기의 임시 저장소에 보관하고, 본문에 임시 표시를 넣고, 화면에는 기기 안 사본으로 사진을 정상 표시해야 한다. 연결되면 자동으로 다시 올리고 성공하면 임시 표시를 진짜 주소로 바꾼다.
- **FR-020**: 자동 저장은 임시 표시가 있어도 그대로 진행해야 한다 (글이 사라지면 안 된다).
- **FR-021**: System MUST 임시 표시 사진이 남아 있는 글의 발행을 거부한다 (다른 사람이 볼 수 없는 주소가 공개 글에 들어가는 것을 막는다). 발행 절차는 → [specs/002-post-authoring](../002-post-authoring/spec.md).

**사진 소유와 글 연결 (23 §6-1, 2026-10-07 회의)**

- **FR-022**: System MUST 수동 저장·자동 저장 DB 반영·발행 때 본문에서 우리 사진을 찾아 **글 작성자가 올린 사진만** 그 글에 연결하고 "연결됨" 상태로 바꾼다. 본문에서 빠진 사진은 연결 해제 일자를 기록한다 (04 §4-4).
- **FR-023**: 다른 사람이 올린 우리 저장소 사진 주소는 내 글에 연결하지 않고, 본문에서는 외부 이미지처럼 링크로 표시해야 한다. 표시 규칙의 세부는 → [specs/002-post-authoring](../002-post-authoring/spec.md) (12 S-6).
- **FR-024**: "우리 사진" 판별은 주소가 지금의 공개 주소 또는 옛 공개 주소 목록 중 하나로 시작하고 나머지가 저장 이름 모양일 때만 성립하며, 판별·저장 이름 추출은 한 곳에서만 한다. 사진 연결은 주소 문자열이 아니라 저장 이름으로 비교한다 (23 §2-4).

**사진 공개·저장소 보호**

- **FR-025**: 사진은 주소를 알면 누구나 볼 수 있다. 비공개 글의 사진도 같다 (04 결정 2, 01 Q10). 공개 범위가 `FRIENDS`(선택 구현)인 글의 사진 접근 방식은 [NEEDS CLARIFICATION: 04 결정 2와 01 결정 기록(Q10)은 "친구 공개 도입 시 서명된 주소 방식으로 재검토"라고만 남겼다. `FRIENDS` 적용자의 사진도 "주소를 알면 보임"을 유지할지, 사진마다 권한을 확인하는 방식으로 바꿀지 정해지지 않았다]
- **FR-026**: 사진 저장소는 다음을 만족해야 한다 (23 §2-2·§2-3): 서명된 업로드만 허용(서명 위조·서명 후 경로 변경·서명과 다른 형식·만료된 업로드 거부), 서명 없는 익명 쓰기 거부, 익명 목록 조회 거부, 사진 경로 아래 파일 하나 익명 읽기만 허용, 사진 경로 밖 익명 읽기 거부, 우리 사이트 출처에서만 업로드 허용(다른 출처 거부). 관리 콘솔은 외부에 열지 않는다.
- **FR-027**: 저장소 보호 검증 11가지(FR-026 항목)는 로컬 개발용 고정 버전과 운영 저장소 **두 곳 모두**에서 통과해야 하며, 운영은 배포 전에 반드시 실행한다. 저장소 버전을 올리거나, 운영 저장소 변경 공지가 있거나, 버킷 정책·교차 출처·키 권한을 바꿀 때 다시 실행한다 (23 §2-3).
- **FR-028**: 운영 저장소에서 브라우저 직접 업로드용 교차 출처 허용을 설정할 수 없으면 앱 서버를 거쳐 업로드하는 방식으로 바꾸되 FR-001~FR-024 규칙은 같아야 한다 (23 §2-2).
- **FR-029**: 사진 주소는 바뀌지 않으므로 브라우저·CDN이 1년 동안 변경 없이 캐시해도 된다 (04 §4-2).

**공개 주소 변경 (23 I-5)**

- **FR-030**: 렌더링 때 우리 사진은 옛 주소로 쓰였더라도 **지금의 공개 주소**로 바꿔 출력하고, 사용자가 쓴 원문은 바꾸지 않는다. 공개 주소·옛 주소 목록에 없는 주소는 외부 이미지 링크가 된다 (23 §2-4).
- **FR-031**: 공개 주소를 바꿀 때는 ① 새 주소가 같은 파일을 내주는지(옛 주소도 계속 열려 있는지) 확인 → ② 공개 주소를 새 주소로, 옛 주소를 옛 주소 목록에 추가하고 사진 허용 출처에 새 주소 추가 → ③ 발행 글 전체 다시 렌더링 → ④ 글 카드 썸네일 주소 일괄 갱신 → ⑤ 다시 렌더링이 끝나면 허용 출처에서 옛 주소 제거 순서를 따른다. 옛 주소 목록에서는 주소를 지우지 않는다 (23 §2-4).

**대체글 (23 I-3)**

- **FR-032**: 에디터는 사진을 넣을 때 대체글 자리를 비워 두고 원래 파일 이름을 넣지 않는다.
- **FR-033**: 발행 설정 창은 대체글이 빈 사진이 있으면 "대체글이 없는 사진이 N장 있어요 [대체글 넣기]"를 보여주고, 누르면 사진마다 작은 미리보기와 입력칸을 보여주며, 입력하면 본문에 반영한다. 입력칸 아래에 "사진을 볼 수 없는 분께 읽어 줄 설명이에요. 예: 'fetch join 전후 쿼리 수 비교 그래프'"를 보여준다.
- **FR-034**: 대체글이 없어도 발행을 막지 않는다. 빈 대체글은 빈 값(화면 낭독기가 꾸밈 이미지로 건너뜀)으로 그리며, 대체글 속성 자체를 빼지 않는다. 권장 길이는 125자 이내이며 넘어도 거부하지 않고 안내만 한다.
- **FR-035**: 글 카드 썸네일의 대체글은 글 제목, 프로필 사진의 대체글은 빈 값이다 (23 §4).

**GIF (23 I-4)**

- **FR-036**: GIF 원본은 압축·크기 조정·변환 없이 그대로 올리고, 10MB 이하, 가로·세로 각 1920px 이하, 프레임 300장 이하만 받는다. 1920px를 넘으면 고르는 순간 "GIF는 가로·세로 1920px까지 올릴 수 있어요"를 보여준다 (23 §5-1).
- **FR-037**: System MUST 업로드 완료 확인에서 GIF의 해상도·프레임 수를 파일 전체를 해독하지 않고 다시 확인하고, 넘으면 거부·삭제한다.
- **FR-038**: 업로드 화면은 움직이는 WebP·APNG는 첫 장면만 남고 움직임을 살리는 형식은 GIF뿐이라는 안내를 보여준다.
- **FR-039**: 본문의 우리 저장소 GIF는 처음에 첫 장면 정지 이미지(썸네일)와 ▶ 표시로 보이고, 누르면 원본이 재생되며, 다시 누르면 정지 장면으로 돌아간다. 키보드 Enter로도 재생된다. 링크 이름은 대체글, 대체글이 비었으면 "움직이는 이미지 재생"이다. 스크립트가 동작하지 않으면 정지 이미지를 눌렀을 때 원본이 새 탭에서 열린다. 재생 기능은 인라인 스크립트 없이 동작해야 한다 (23 §5-2).
- **FR-040**: 글 카드 썸네일은 GIF의 첫 장면, 링크 미리보기 대표 이미지는 원본 GIF를 쓴다 (10 §6).

**정리 (04 §4-4)**

- **FR-041**: 매일 새벽 정리 작업은 연결되지 않은 채 24시간이 지난 사진과 연결 해제된 지 7일이 지난 사진의 원본·썸네일 파일을 저장소에서 지운 뒤 기록을 지운다. 지금 쓰고 있는 프로필 사진(연결됨, 연결 해제 일자 없음)은 지우지 않는다.
- **FR-042**: 저장소 삭제는 데이터 저장 작업 밖에서 하고, 저장소 삭제에 성공한 뒤에만 기록을 지운다. 실패하면 다음 정리에서 다시 시도한다. 서버가 여러 대여도 정리 작업은 한 번만 실행된다.
- **FR-043**: 탈퇴 회원이 올린 사진은 탈퇴 30일 익명 처리 뒤 다음 정리 때 모두 지워진다 (2026-10-07 회의 "탈퇴 회원 사진"). 처리 절차는 → [specs/015-withdraw](../015-withdraw/spec.md).

### Key Entities *(include if feature involves data)*

- **사진(Image)**: 한 번의 업로드로 만들어진 원본 1개와 썸네일 0~1개. 올린 회원, 저장 이름(유일), 썸네일 저장 이름(없을 수 있음, 썸네일이 없는 옛 사진 구분), 형식(jpg·png·gif·webp), 원본 크기(1바이트~10MB), 썸네일 크기(1바이트~1MB), 가로·세로 픽셀, 상태(올리기만 함 / 연결됨), 용도(글 사진 / 프로필 사진), 연결 해제 일자, 올린 일자. 원래 파일 이름은 갖지 않는다.
- **글-사진 연결**: 어떤 글이 어떤 사진을 쓰는지(N:M). 글이나 사진이 완전히 지워지면 함께 지워진다. 작성자가 올린 사진만 연결된다.
- **사진 저장 공간 사용량**: 회원별로 따로 저장하지 않고 그 회원이 올린 사진들의 원본 + 썸네일 크기 합계로 계산한다 (합계와 어긋날 위험을 피함, 23 §8).
- **사진 공개 주소 설정**: 지금 공개 주소 하나 + 옛 공개 주소 목록. 우리 사진 판별, 렌더링 출력 주소, 사진 허용 출처가 모두 이 값을 함께 쓴다.
- **오프라인 대기 사진**: 업로드를 기다리는 사진 원본과 본문의 임시 표시. 이 기기에만 있고 서버에는 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 일반 휴대폰 사진(약 5MB)은 업로드 전 약 300~500KB로 줄어 전송량이 원본의 약 1/10이 된다 (04 §4-1).
- **SC-002**: 업로드된 GIF 이외 사진 중 촬영 위치 정보가 남은 사진은 0장이다.
- **SC-003**: 확장자 위장·형식 불일치·손상 파일·크기 초과 파일은 100% 거부되고, 거부된 파일은 저장소에 남지 않는다.
- **SC-004**: 한도 근처에서 업로드 준비를 동시에 10건 요청해도 사용량이 1GB를 넘는 경우가 0건이다. 하루 201번째 요청은 100% 거부된다.
- **SC-005**: 원래 파일 이름이 저장되거나 화면에 보이는 경우가 0건이다.
- **SC-006**: 대체글이 없는 사진이 있는 글의 발행 성공률은 100%이고, 빈 대체글은 모두 꾸밈 이미지로 그려진다.
- **SC-007**: 다른 회원이 올린 사진 주소를 넣고 발행한 글에서 그 사진이 글에 연결되는 경우가 0건이고, 원래 주인의 글에서는 그대로 보인다.
- **SC-008**: 오프라인에서 넣은 사진은 연결 복구 후 100% 진짜 주소로 바뀌며, 임시 표시가 남은 글의 발행은 100% 거부된다.
- **SC-009**: 저장소 보호 검증 11가지가 로컬 고정 버전과 운영 저장소 두 곳에서 모두 통과한다 (운영은 배포 전).
- **SC-010**: 공개 주소를 바꾼 뒤 다시 렌더링해도 옛 주소로 쓴 우리 사진이 링크로 바뀌는 경우가 0건이다.
- **SC-011**: 1920px 또는 300프레임을 넘는 GIF는 100% 거부되고 파일이 지워진다. 허용 범위의 GIF는 움직임이 유지된다.
- **SC-012**: 정리 작업 뒤 24시간 넘은 미연결 사진과 7일 넘은 연결 해제 사진은 0장 남고, 사용 중인 프로필 사진은 0장 지워진다.
- **SC-013**: 글 목록 카드 9장의 썸네일 전송량은 약 0.4MB로, 원본을 쓸 때(약 3.6MB)의 약 1/9이다 (10 L-8).

## Assumptions

- 이 기능은 Tier B 공통 기능 C-IMG-1이다. 수치(1GB, 하루 200장, 1분 20장, 정리 기간)는 설정값으로 두고 기본값은 원문을 따른다.
- 사진 업로드는 임시저장과 분리된 즉시 업로드다 (01 결정 기록 2026-10-02 "사진 처리"). 자동 저장·수동 저장·발행 흐름 자체와 발행 때 카드 썸네일 지정(본문 첫 업로드 사진의 썸네일), 본문 렌더링·정화(우리 사진·남의 사진·외부 이미지 표시)는 → [specs/002-post-authoring](../002-post-authoring/spec.md)이 맡는다. 이 스펙은 업로드·검사·소유·저장소·정리·GIF·대체글을 맡는다.
- 프로필 사진(256×256 WebP, 소셜 가입 시 사진 복사, 프로필 사진 교체 순서, 남의 사진을 프로필로 지정하면 거부)은 같은 업로드 흐름을 쓰되 규칙은 → [specs/001-account-auth](../001-account-auth/spec.md)가 맡는다. 프로필 사진도 사용량에 포함된다.
- 글 카드의 썸네일 표시는 → [specs/005-post-reading](../005-post-reading/spec.md), 글 완전 삭제 때 사진 연결 해제는 → [specs/006-manage-delete](../006-manage-delete/spec.md), 탈퇴 회원 사진 정리는 → [specs/015-withdraw](../015-withdraw/spec.md), 공개 범위 정책은 → [specs/004-visibility-permission](../004-visibility-permission/spec.md)이 맡는다.
- 저장소 제품은 팀 결정(2026-10-06)대로 운영 NHN 제공 저장소, 로컬은 버전을 고정한 커뮤니티 포크다. 운영 저장소의 접속 방식·앱 전용 키·버킷 정책·교차 출처 설정 가능 여부와 백업 정책은 **배포 전 확인 대상**이며 아직 확인되지 않았다 (04 §6-1, 23 §2-1).
- CDN(CloudFront)과 지운 사진의 CDN 무효화 요청은 강성찬 개인 확장이다. 공통 기간에는 저장소 공개 주소를 그대로 쓴다 (23 §2-4, §6-3).
- 지운 사진이 이미 본 독자의 브라우저 캐시에 최대 1년 남는 것은 허용 한계로 둔다. "탈퇴 후 사진이 남지 않는다"는 우리 저장소(와 CDN) 기준이다 (23 §6-3).
- `FRIENDS` 공개 범위는 선택 구현이고 기본 비활성이다. 비활성인 동안 사진 접근은 "주소를 알면 보임"으로 충분하다.
- 저장소 요청 횟수 기록을 쓸 수 없는 장애 중에는 요청 횟수 제한(1분 20장, 하루 200장)이 통과된다 (02 §2-1 "요청 제한·중복 방지 카운터는 통과").
- 원문 간 차이: 23 §6-2·§2-4는 회원 테이블의 프로필 사진 컬럼(`member.profile_image_id`·`profile_image_url`)을 쓰지만 2026-10-07 회의에서 삭제되었으므로 51·13 §3-3 기준을 따른다. 23 §6-2의 "탈퇴 사진 최대 약 38일"은 2026-10-07 "탈퇴 회원 사진" 결정(다음 정리 때 삭제)으로 대체되었다. 23 §6-1 업로더 확인은 "제안"으로 적혀 있으나 2026-10-07 회의에서 채택되었다.

## Implementation Notes (for /speckit-plan)

원문의 기술 결정 요약이다. 위 절들은 이 내용을 몰라도 읽을 수 있게 썼다.

- **업로드 흐름** ([04 §4-1](../../docs/04-draft-and-image.md), [10 §6](../../docs/10-post-list.md)): `POST /api/images/presign {contentType, size, thumbSize}` → `image` 행 생성(`status = TEMP`) + Presigned PUT 2개(5분, **SigV4**, path-style) → 브라우저가 MinIO로 직접 PUT → `POST /api/images/{id}/complete`(`uploader_id ≠ 나`면 404, 존재·실제 크기·매직 바이트·해상도 검사, 썸네일 640px·1MB). 저장소 없는 환경용 `LocalImageStorage`는 `PUT /api/images/{id}/content`(같은 업로더 검사). 브라우저 압축은 캔버스로 다시 그려 EXIF 제거.
- **저장소 추상화** (04 §4-1): `ImageStorage { prepareUpload, inspect, publicUrl, delete }`, 구현 `S3ImageStorage`(AWS SDK for Java v2 `S3Client`·`S3Presigner`, `endpointOverride` + `forcePathStyle(true)`). 다른 도구로 테스트 URL을 만들 때는 `signature_version="s3v4"`.
- **저장소 제품** ([04 §6-1](../../docs/04-draft-and-image.md), [23 §2](../../docs/23-image.md)): MinIO. 운영 NHN 제공 MinIO, 로컬 `pgsty/silo:RELEASE.2026-09-16T00-00-00Z`(버전 고정, `latest` 금지, 클라이언트 `pgsty/mc`). 버킷 `blog` 하나, 사진은 `images/*`만. 앱 전용 키는 `s3:PutObject`·`GetObject`·`DeleteObject`만, 환경 변수로만. 익명 `GetObject`는 `images/*`만, 익명 `ListBucket` 금지. CORS는 우리 출처의 `PUT`·헤더 `Content-Type`만(MinIO 서버 설정 `MINIO_API_CORS_ALLOW_ORIGIN`). 관리 콘솔 비공개, 로컬도 9000 포트만.
- **저장소 검증 11가지** ([23 §2-3](../../docs/23-image.md)): `scripts/check-storage.sh`(로컬, 2026-10-06 PASS 11/FAIL 0), 운영은 `scripts/lib/presign_check.py`를 `S3_ENDPOINT`·`APP_KEY`·`APP_SECRET`·`BUCKET`·`SITE_ORIGIN`만 바꿔 실행(미실행, 배포 전 필수). 앱 통합 테스트는 Testcontainers로 같은 고정 이미지.
- **저장 키·주소** ([04 §4-2](../../docs/04-draft-and-image.md), [23 §2-4](../../docs/23-image.md)): 키 `images/{yyyy}/{MM}/{uuid}.{ext}`, 썸네일 `{uuid}_thumb.{ext}`. 주소 = `blog.image.public-base-url` + `/` + 키. 옛 주소 `blog.image.legacy-base-urls`. 판별·키 추출은 `ImageUrls.keyOf(url)` 하나(키 모양 `images/{yyyy}/{MM}/{uuid}(_thumb)?.{ext}`). 렌더링은 12 §2 ② AST 변환에서 `src`를 현재 공개 주소로. 작성자 사진 확인은 `SELECT storage_key FROM image WHERE storage_key = ANY(:keys) AND uploader_id = :author`(`uq_image_storage_key`). 캐시 `Cache-Control: public, max-age=31536000, immutable`. 공개 주소 변경 4단계 SQL: `UPDATE post SET thumbnail_url = :new || substr(thumbnail_url, length(:old) + 1) WHERE thumbnail_url LIKE :old || '/%'`, 3단계는 `RENDER_VERSION` 증가(12 §7-7).
- **요청 제한·용량** ([04 §4-2](../../docs/04-draft-and-image.md), [23 §3](../../docs/23-image.md)): 1분 20장은 Redis 카운터. 하루 장수 Redis `img:daily:{memberId}:{yyyyMMdd}` `INCR`, TTL 2일, presign에서 셈. 용량 설정 `blog.image.quota-bytes`(1GB), `blog.image.daily-limit`(200). presign 트랜잭션에서 `SELECT … FROM member WHERE id = :me FOR UPDATE` 후 `SELECT coalesce(sum(size_bytes + coalesce(thumb_size_bytes, 0)), 0) FROM image WHERE uploader_id = :me`(`ix_image_uploader`) → TEMP 행을 신고 크기로 INSERT. 오류 `409 STORAGE_QUOTA_EXCEEDED`, `429 DAILY_UPLOAD_LIMIT`. `GET /api/me/storage` → `{ usedBytes, quotaBytes, todayCount, dailyLimit }`. 회원 행에 사용량 컬럼을 두지 않는다.
- **오프라인 대기열** ([04 §4-3](../../docs/04-draft-and-image.md)): IndexedDB `pendingImages`에 Blob, 본문 `![업로드 대기](local:…)`, 화면은 `URL.createObjectURL`(CSP `img-src blob:`). 발행 시 `local:`이 있으면 `400`.
- **연결·정리** ([04 §4-4](../../docs/04-draft-and-image.md), [05 §7 ⑥](../../docs/05-publish.md)): `post_image` 동기화(`uploader_id = 글 작성자`만, `status = ATTACHED`, 빠진 사진 `detached_at`). 정리 배치는 매일 새벽 `@Scheduled` + ShedLock, `ix_image_cleanup_temp`(TEMP 24시간)·`ix_image_cleanup_detached`(7일). `purpose = PROFILE`, `status = ATTACHED`, `detached_at IS NULL`인 행은 제외(`uq_image_profile_current`). 저장소 삭제는 트랜잭션 밖, 성공 후 행 삭제. 탈퇴 정리는 13 §3-3 4번(order 40): `detached_at = now() - interval '7 days'`로 기록해 다음 배치가 지움.
- **GIF** ([23 §5](../../docs/23-image.md)): 서버 검사는 `ImageReader.getNumImages`로 머리말·프레임 수만. 본문 출력 `<a href="{원본.gif}" title="움직이는 이미지 재생" target="_blank" rel="noopener noreferrer nofollow ugc"><img src="{uuid}_thumb.webp" alt="…" loading="lazy" decoding="async"></a>`. 재생 스크립트 `/js/gif-play.js`(CSP `script-src 'self'`, `a[href$=".gif"] > img`), ▶ 표시는 CSS `a[href$=".gif"]::after`(class 없이, 정화 허용 목록 변경 없음).
- **CSP** ([02 §5](../../docs/02-architecture.md), [12 §8](../../docs/12-content-sanitize.md), 2026-10-07 H3): `connect-src 'self' {저장소 공개 주소}`, `img-src 'self' {저장소 공개 주소} data: blob:`. 저장소 주소는 `blog.image.public-base-url` 하나를 CSP·정화 허용 목록이 함께 씀.
- **스키마** ([51 `image`·`post_image`](../../docs/51-erd-unified.md)): `image(id, uploader_id FK RESTRICT, storage_key UQ, thumb_storage_key UQ, content_type CHECK 4종, size_bytes CHECK 1~10485760, thumb_size_bytes CHECK ≤1048576, width, height, status TEMP/ATTACHED, purpose POST/PROFILE, detached_at, created_at)`, `post_image(post_id, image_id)` 복합 PK, 양쪽 CASCADE. `image.original_name`은 삭제됨(2026-10-07). 회원 테이블은 사진을 가리키지 않는다.
- **장애** ([02 §2-1](../../docs/02-architecture.md)): Redis 장애 시 요청 제한 카운터는 통과(경고 로그).
