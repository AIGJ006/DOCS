## Clarifications

### Session 2026-10-08

- Q: 관리자가 글을 열어 본 것도 조회수에 셀까? → A: 세지 않는다. 조회 기록 요청에서 관리자면 기록 없이 같은 성공 응답(204)을 준다 (FR-024·FR-031) (민서 확정 2026-10-08)
- Q: "원래 접속 주소(IP)를 어디에도 남기지 않는다"의 범위는? → A: 조회수 기능이 만드는 기록(중복 판정 키·DB·조회수 로그)에만 해당한다. 서버 접속 로그와 로그인·재설정 요청 제한은 지금처럼 IP를 쓴다. SC-010을 이 범위로 좁힌다 (FR-034, SC-010) (민서 확정 2026-10-08)
- Q: 비회원 방문자 쿠키 안내를 개인정보 처리방침에 언제 넣을까? → A: 첫 공개 전 처리방침 첫 판에 넣는다(재동의 흐름을 일으키지 않음) (FR-023·FR-034) (민서 확정 2026-10-08)
- Q: 좋아요 요청 과다 오류 코드는? → A: 공통 `TOO_MANY_REQUESTS`(007 Q3과 같음) (FR-008) (민서 확정 2026-10-08)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 남의 글에 좋아요를 누르고 취소한다 (Priority: P1)

이메일 인증을 마친 회원이 읽을 수 있는 남의 발행 글에서 좋아요를 누르면 ♥와 숫자가 바로 바뀌고, 다시 누르면 취소된다. 버튼을 연타하거나 네트워크가 요청을 다시 보내도 결과는 사용자가 마지막으로 원한 상태 하나이고, 좋아요 수는 언제나 실제로 누른 사람 수와 같다.

**Why this priority**: 공통 Tier B 필수 기준 C-LIKE-1("1인 1글 1회, 다시 누르면 취소, 동시에 여러 번 눌러도 1건")의 핵심이며, 좋아요 수는 목록 카드와 트렌딩 점수의 재료라 정확성이 가장 중요하다.

**Independent Test**: 회원 A로 회원 B의 공개 글에 좋아요·취소를 각각 한 번, 그리고 동시에 20번씩 보내 보고, 화면 표시·응답의 좋아요 수·실제 누른 사람 수가 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원 A가 회원 B의 공개 발행 글을 보고 있고 좋아요를 누르지 않은 상태, **When** A가 좋아요를 누르면, **Then** 서버 응답을 기다리지 않고 ♡가 ♥로, 숫자가 +1로 바뀌고, 응답의 "좋아요 여부 = 예"와 최신 좋아요 수로 최종 숫자가 맞춰진다.
2. **Given** A가 이미 좋아요한 글, **When** A가 "좋아요 상태로" 요청을 다시 보내면, **Then** 성공으로 응답하고 좋아요 수는 바뀌지 않는다 (C-LIKE-1 기준 3).
3. **Given** A가 좋아요하지 않은 글, **When** 같은 "좋아요 상태로" 요청이 동시에 20번 도착하면, **Then** 좋아요는 1건만 생기고 좋아요 수는 1만 늘며 알림·트렌딩용 "좋아요됨" 사건도 1번만 생긴다 (C-LIKE-1 기준 1·5).
4. **Given** 같은 글에 같은 사람의 "좋아요"·"취소" 요청 20번씩이 동시에 섞여 들어오면, **When** 모두 처리된 뒤, **Then** 좋아요 수는 실제 남은 좋아요 건수와 같다 (C-LIKE-1 기준 2).
5. **Given** A가 버튼을 0.3초 안에 여러 번 연타하면, **When** 연타가 멈추면, **Then** 마지막 상태 하나만 서버로 보내고 최종 숫자는 서버 응답으로 맞춘다.
6. **Given** 좋아요 요청이 실패하면, **When** 응답이 오류로 돌아오면, **Then** 화면은 누르기 전 상태로 되돌아가고 "좋아요를 반영하지 못했어요"가 안내된다.
7. **Given** 회원 A가 이미 좋아요한 글을 상세 화면으로 처음 열면, **When** 화면이 그려질 때, **Then** ♥(눌림) 상태로 표시된다. 목록 카드에는 내가 눌렀는지 없이 수만 보인다.

### User Story 2 - 좋아요를 누를 수 없는 사람·글을 막고 안내한다 (Priority: P1)

비회원, 이메일 인증 전 회원, 탈퇴 유예 회원, 자기 글의 작성자, 볼 수 없는 글에 대한 좋아요 요청은 서버에서 거부되고 좋아요 수는 바뀌지 않는다. 화면에서는 비회원·인증 전 회원에게도 버튼이 보이되 누르면 로그인 또는 인증 안내가 나온다.

**Why this priority**: 인증 안 된 계정의 대량 좋아요, 자기 점수 올리기로 트렌딩이 조작되는 것을 막는 규칙이고, 볼 수 없는 글의 존재를 드러내지 않는 404 원칙(01 §3-3)과 직결된다.

**Independent Test**: 비회원·인증 전·탈퇴 유예·작성자 본인·일반 회원 각각으로 공개 글, 비공개 글, 휴지통 글, 숨긴 글에 좋아요를 요청해 응답 종류와 좋아요 수 불변을 확인한다.

**Acceptance Scenarios**:

1. **Given** 비회원, **When** 좋아요를 요청하면, **Then** 로그인 필요(401)로 거부되고 수는 그대로다. 화면에서는 버튼을 누르면 "로그인하고 좋아요를 눌러 보세요 [로그인]"이 보이고, 로그인 후 원래 글로 돌아오되 자동으로 좋아요가 눌리지 않는다 (K-2).
2. **Given** 이메일 인증 전 회원, **When** 좋아요를 요청하면, **Then** 계정 상태 거부(403, 이메일 미인증)와 "이메일 인증 후 누를 수 있어요" 안내가 나오고 수는 그대로다 (K-3, 42 P-6).
3. **Given** 작성자 본인, **When** 자기 글의 좋아요를 요청하면, **Then** 규칙 위반(400, 자기 글 좋아요 불가)으로 거부된다. 화면에는 버튼 대신 ♥와 개수만 보인다 (K-1, 42 P-9).
4. **Given** 회원, **When** 임시글·휴지통 글·비공개 글·관리자가 숨긴 글·탈퇴 유예 작성자의 글에 좋아요를 요청하면, **Then** 없는 글과 똑같이 404이고 수는 그대로다 (K-4, C-LIKE-1 기준 4).
5. **Given** 한 회원이 1분 동안 좋아요·취소를 합쳐 60번 요청한 상태, **When** 61번째를 보내면, **Then** 요청 과다(429)와 다시 시도할 수 있는 시간이 안내된다 (K-9, C-LIKE-1 기준 6).

### User Story 3 - 새로고침으로 부풀지 않는 조회수 (Priority: P2)

독자가 글 상세를 실제로 보면(화면에 보이는 상태로 1초 이상) 조회가 기록되고, 같은 방문자가 정해진 기간 안에 새로고침해도 정해진 횟수를 넘겨 세지 않는다. 작성자 본인, 봇·링크 미리보기, 미리 불러오기, 볼 수 없는 글은 세지 않는다. 조회수는 최대 1분 늦게 글 상세에 "조회 N"으로 보인다.

**Why this priority**: 공통 Tier B 기준 C-VIEW-1이며 트렌딩 점수의 재료다. 좋아요보다 정확도 요구는 낮지만(회계 값이 아님) 글 읽기를 절대 방해하지 않아야 한다.

**Independent Test**: 비회원 방문자 3명(그중 1명은 5번 새로고침)과 회원 1명(3번)이 각각 다른 글을 본 뒤 1분 반영을 기다려 조회수가 3과 1인지, 작성자 본인·봇 요청은 늘지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기본 설정(같은 방문자·같은 글 24시간에 1회), **When** 비회원 v1이 글 A를 5번 새로고침하고 v2·v3가 1번씩 보면, **Then** 1분 안에 글 A의 조회수는 3이 된다 (31 §9).
2. **Given** 같은 방문자가 같은 글에 동시에 50번 기록 요청을 보내면, **When** 처리된 뒤, **Then** 1번만 센다 (C-VIEW-1 기준 1).
3. **Given** 설정을 "30분에 5회"로 바꾼 운영, **When** 같은 방문자가 30분 안에 7번 보면, **Then** 5번만 센다. 기간이 지난 뒤 다시 보면 다시 센다.
4. **Given** 작성자 본인이 자기 글 상세를 열면, **When** 화면이 그려질 때, **Then** 조회 기록 요청 자체가 일어나지 않고 조회수는 늘지 않는다 (40 #7).
5. **Given** 글을 백그라운드 탭으로 열어 두면, **When** 사용자가 그 탭을 보고 1초가 지나면, **Then** 그때 한 번만 기록 요청을 보낸다.
6. **Given** 셌든 중복이라 안 셌든, **When** 기록 요청에 응답할 때, **Then** 두 경우의 응답이 똑같다 (C-VIEW-1 기준 6).
7. **Given** 조회 기록용 임시 저장소가 멈춘 상태, **When** 독자가 글 상세를 열면, **Then** 글 상세는 (로그인 정보를 읽지 못해도 비회원 기준으로) 정상으로 열리고 그동안의 조회만 빠진다 (C-VIEW-1 기준 3, H8).
8. **Given** 모아 둔 조회를 반영하던 도중 서버가 멈추면, **When** 다음 반영이 실행되면, **Then** 남은 조회가 사라지지 않고 반영되며 이미 반영한 글은 다시 더하지 않는다 (C-VIEW-1 기준 5).

### User Story 4 - 일별 조회수를 90일 보관한다 (Priority: P3)

시스템은 글마다 날짜(한국 시간)별 조회수 합계를 90일 동안 보관해 작성자 통계(개인 확장)와 트렌딩 점수식 변경에 대비한다. 누가 봤는지는 남기지 않는다.

**Why this priority**: 공통 화면에서 직접 쓰는 곳이 없고 통계·점수식 B 전환 대비용이라 가장 낮다.

**Independent Test**: 반영 뒤 일별 합계가 누적 조회수 증가분과 같은지, 91일 전·89일 전 행에 보관 정리를 실행해 91일 전만 지워지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 1분 반영이 실행되면, **When** 글 A·B의 조회가 반영될 때, **Then** 누적 조회수와 그날의 일별 합계가 같은 값만큼 늘어난다.
2. **Given** 자정 무렵에 생긴 조회, **When** 반영되면, **Then** 실제 조회가 일어난 날짜(한국 시간)의 일별 합계에 들어간다.
3. **Given** 91일 전·89일 전 일별 합계, **When** 매일 새벽 보관 정리가 실행되면, **Then** 91일 전 것만 삭제되고 누적 조회수는 그대로다 (C-VIEW-1 기준 8).
4. **Given** 글이 완전 삭제되면, **When** 삭제가 끝난 뒤, **Then** 그 글의 일별 합계도 함께 사라진다.

### Edge Cases

- 좋아요와 취소가 순서가 뒤바뀌어 도착하면? 상태 지정 방식이라 마지막으로 처리된 요청의 상태가 남고, 화면은 서버 응답의 수로 맞춘다.
- 좋아요한 글이 비공개·휴지통·관리자 숨김이 되면? 좋아요는 지우지 않고, 글을 볼 수 없는 사람에게는 수·버튼이 함께 안 보인다. 다시 공개·복구·숨김 해제하면 그대로 돌아온다 (06 V-7, 13 D-3, 43 §4-1).
- 좋아요를 누른 사람이 탈퇴를 신청하면? 유예 중에는 좋아요와 수가 그대로이고, 30일 뒤 익명 처리 때 그 사람의 좋아요가 지워지며 각 글의 수가 줄어든다 (→ specs/015-withdraw).
- 좋아요 수가 어떤 버그로 실제 건수와 어긋나면? 매일 새벽 보정이 고치고 경고 기록을 남긴다. 정상이라면 0건이다.
- 같은 사람이 같은 글에 좋아요 → 취소 → 좋아요를 반복하면? 사건은 실제로 바뀔 때마다 생기지만 작성자에게 가는 좋아요 알림은 1번뿐이다 (→ specs/011-notification).
- 좋아요 수 1만 이상은? "1.2만"처럼 소수 첫째 자리까지 내림으로 표시한다(12,999 → 1.2만).
- 비회원으로 글을 보다가 로그인해서 다시 보면? 방문자 구분이 달라져 1번 더 셀 수 있다. 드물어서 허용한다.
- 쿠키를 막은 비회원이 날짜를 넘겨 다시 보면? 비밀값이 매일 바뀌어 다른 방문자로 취급된다(추적 불가가 우선).
- 같은 방문자가 1분에 60번을 넘게 조회 기록을 보내면? 429로 거부한다.
- 반영 사이에 글이 완전 삭제되면? 그 글의 모아 둔 조회만 건너뛰고 나머지 글은 정상 반영한다.
- 반영 중 한 글을 확정한 직후·정리 직전에 서버가 멈추면? 그 글 하나만 1분치가 한 번 더 더해질 수 있다. 조회수는 회계 값이 아니라서 허용한다.
- 요청 제한용 임시 저장소가 멈추면? 좋아요·조회 요청 제한은 통과(경고 기록)되어 제한 없이 동작한다 (02 §2-1).
- 관리자가 신고 처리를 위해 글을 열면? 세지 않는다. 다른 경우와 같은 204를 준다 (FR-031).

## Requirements *(mandatory)*

### Functional Requirements

**좋아요 — 상태와 정확성**

- **FR-001**: 시스템은 한 회원이 한 글에 좋아요를 최대 1건만 남기도록 해야 하며, 같은 요청이 동시에 여러 번 와도 1건이어야 한다 (C-LIKE-1 기준 1).
- **FR-002**: 좋아요는 뒤집기(토글)가 아니라 "좋아요 상태로" / "취소 상태로"를 지정하는 두 가지 요청으로 바뀌어야 하며, 이미 그 상태인 요청도 성공으로 응답하고 수는 바꾸지 않아야 한다 (K-5, C-LIKE-1 기준 3).
- **FR-003**: 성공 응답은 지금 이 회원의 좋아요 여부와, 그 사이 다른 사람이 누른 것까지 반영한 최신 좋아요 수를 담아야 한다 (30 §3·§4).
- **FR-004**: 글의 좋아요 수는 좋아요가 실제로 새로 생기거나 실제로 지워진 경우에만 1씩 늘거나 줄어야 하며, 좋아요 기록과 수의 변경은 함께 반영되거나 함께 반영되지 않아야 한다. 좋아요·취소가 동시에 섞여도 수는 실제 건수와 같아야 한다 (K-6, C-LIKE-1 기준 2).
- **FR-005**: 시스템은 매일 새벽 한 번(여러 서버 중 한 곳에서만) 좋아요 수가 실제 건수와 다른 글을 찾아 고치고, 고친 건수가 0이 아니면 경고를 기록해야 한다. 정상 상태에서는 0건이어야 한다 (30 §4-1, C-LIKE-1 기준 7).

**좋아요 — 권한과 응답**

- **FR-006**: 좋아요는 그 사람이 지금 읽을 수 있는 발행 글에만 가능해야 한다. 임시글·휴지통 글·공개 범위상 볼 수 없는 글·관리자가 숨긴 글·탈퇴 유예 작성자의 글·없는 글은 모두 같은 404로 응답하고 수를 바꾸지 않아야 한다 (K-4, 42 §7; 읽기 판정 규칙은 → specs/004-visibility-permission).
- **FR-007**: 비회원의 좋아요·취소 요청은 로그인 필요(401)로 거부해야 한다 (K-2, 42 §7).
- **FR-008**: 이메일 인증 전 회원은 403 "이메일 미인증", 탈퇴 유예 회원은 403 "탈퇴 유예"로 거부해야 한다 (K-3, 42 P-5·P-6·P-12).
- **FR-009**: 자기 글에 대한 좋아요·취소 요청은 400 "자기 글 좋아요 불가"로 거부해야 한다 (2026-10-07 팀 확정, K-1, 42 P-9 — 30 원문의 403은 42 §4 원칙에 따라 400으로 맞춤).
- **FR-010**: 좋아요 요청의 판정은 ① 로그인 → ② 계정 상태(탈퇴 유예·이메일 미인증) → ③ 글을 읽을 수 있나(404) → ④ 자기 글인가(400) → ⑤ 요청 횟수(429) 순서로 하고, 처음 걸린 단계의 응답을 줘야 한다 (42 P-2·§3 — 30 §2의 "읽기 판정 먼저" 순서는 42 요청에 따라 변경).
- **FR-011**: 한 회원의 좋아요·취소 요청은 합쳐서 1분에 60번까지만 받아야 하며, 넘으면 429와 다시 시도할 수 있는 시간을 알려야 한다 (K-9, C-LIKE-1 기준 6).

**좋아요 — 사건 연결**

- **FR-012**: 시스템은 좋아요가 실제로 생긴 경우에만 "좋아요됨", 실제로 지워진 경우에만 "좋아요 취소됨" 사건을 변경이 확정된 뒤 한 번 남겨야 하며, 이미 그 상태였던 요청은 사건을 남기지 않아야 한다. 사건에는 글·작성자·누른 사람의 식별자와 시각만 담는다 (K-10, C-LIKE-1 기준 5; 알림 생성·중복 판정은 → specs/011-notification, 트렌딩 반영은 → specs/012-trending-search).

**좋아요 — 화면**

- **FR-013**: 글 상세의 좋아요 영역은 남의 글을 보는 회원에게 누를 수 있는 버튼으로, 작성자 본인에게는 버튼 없이 개수만, 비회원·이메일 인증 전 회원에게는 버튼으로 보여야 한다. 비회원이 누르면 "로그인하고 좋아요를 눌러 보세요 [로그인]", 인증 전 회원이 누르면 인증 안내가 나와야 한다 (K-1·K-2, 01 결정 H6).
- **FR-014**: 로그인 안내를 거쳐 로그인하면 원래 글로 돌아와야 하며, 돌아와서 좋아요를 자동으로 누르지 않아야 한다 (K-2).
- **FR-015**: 버튼을 누르면 서버 응답을 기다리지 않고 모양(♡/♥)과 숫자를 바로 바꾸고, 실패하면 되돌린 뒤 "좋아요를 반영하지 못했어요"를 안내해야 한다. 연타는 마지막 상태만 0.3초 뒤에 보내고, 최종 숫자는 서버 응답의 수로 맞춰야 한다 (K-7, 30 §5).
- **FR-016**: 좋아요 수와 조회수는 0~9,999는 천 단위 쉼표(`1,234`), 1만 이상은 소수 첫째 자리까지 내림한 "만" 단위(`1.2만`)로 표시해야 한다 (K-7, 31 §7).
- **FR-017**: 좋아요 버튼은 눌림 여부를 보조 기술에 알리고, 화면 낭독기 이름을 "좋아요 (N)" / "좋아요 취소 (N)"로 제공하며, 색만이 아니라 모양(♡/♥)으로 상태를 구분하고 키보드(Enter·Space)로 누를 수 있어야 한다 (30 §5).
- **FR-018**: 글 상세는 처음 열 때 "내가 눌렀는지"를 함께 보여야 하고, 목록 카드는 좋아요 수만 보여야 한다(내가 눌렀는지는 표시하지 않음) (K-8; 카드 구성은 → specs/005-post-reading).

**좋아요 — 다른 상태와의 관계**

- **FR-019**: 글이 비공개(또는 친구 공개)로 바뀌거나, 휴지통으로 가거나, 관리자에게 숨겨져도 좋아요와 좋아요 수는 지우지 않고 보존해야 하며, 그 글을 볼 수 없는 사람에게는 수와 버튼이 함께 보이지 않아야 한다. 다시 공개·복구·숨김 해제하면 그대로 돌아와야 한다 (30 §7, 06 V-7, 13 D-3, 43 §4-1).
- **FR-020**: 글의 수정·다시 발행은 좋아요와 수를 바꾸지 않아야 하고, 글이 완전 삭제되면 그 글의 좋아요도 함께 삭제되어야 한다 (30 §7, 05 §8, 13 D-5).
- **FR-021**: 좋아요를 누른 회원이 탈퇴 유예 중이면 좋아요를 그대로 두고, 탈퇴 30일 뒤 익명 처리 때 그 회원의 좋아요를 삭제하면서 해당 글들의 좋아요 수를 줄여야 한다 (30 §7, 13 §3-3 3번; 처리 순서는 → specs/015-withdraw).

**조회수 — 중복 판정과 제외**

- **FR-022**: 시스템은 같은 방문자의 같은 글 조회를 기간 안에 최대 정해진 횟수까지만 세야 한다. 기본값은 "24시간에 1회"이고, 기간과 횟수는 코드 수정 없이 설정값으로 바꿀 수 있어야 한다. 기간은 그 방문자가 그 글을 처음 본 순간부터 시작하고, 동시에 여러 요청이 와도 같은 결과여야 한다 (W-1, C-VIEW-1, C-VIEW-1 기준 1).
- **FR-023**: 방문자는 회원이면 계정(기기가 달라도 같은 사람), 비회원이면 첫 방문 때 발급하는 무작위 방문자 식별 쿠키(1년 유지), 쿠키를 막은 비회원이면 접속 주소와 브라우저 정보를 매일 0시(한국 시간)에 바뀌는 비밀값과 함께 되돌릴 수 없게 변환한 값으로 구분해야 한다. 비밀값은 하루만 보관해 날짜를 넘겨 같은 사람을 추적할 수 없어야 한다 (W-2, 31 §2-1).
- **FR-024**: 작성자 본인의 조회, 봇·링크 미리보기(브라우저 정보에 정해진 단어가 들어 있는 요청, 단어 목록은 설정으로 관리), 미리 불러오기 요청, 볼 수 없는 글의 조회는 세지 않아야 한다 (W-3, C-VIEW-1 기준 2).
- **FR-025**: 조회는 글 상세가 화면에 보이는 상태로 1초 이상 지났을 때 한 번만 기록 요청해야 하고, 백그라운드 탭은 사용자가 그 탭을 볼 때 센다. 기록 요청이 실패해도 다시 보내거나 화면에 표시하지 않아야 하며, 글 상세를 여는 것 자체로는 조회수를 세지 않아야 한다. 작성자 본인이 보는 상세에는 기록 요청이 없어야 한다 (W-4, 40 R-7·#7).
- **FR-026**: 조회 기록 요청은 비회원도 할 수 있어야 하고, 셌든 중복이라 안 셌든 항상 같은 성공 응답(본문 없음)을 줘야 한다. 볼 수 없는 글은 404, 같은 방문자가 1분에 60번을 넘으면 429여야 한다 (W-5, C-VIEW-1 기준 6).

**조회수 — 반영과 장애**

- **FR-027**: 모아 둔 조회는 최대 1분 안에 글의 누적 조회수와 그날의 일별 조회수에 함께 반영되어야 하며, 인기 글에 조회가 몰려도 글 상세 응답 속도에 영향을 주지 않아야 한다 (W-6, C-VIEW-1 기준 4).
- **FR-028**: 반영 도중 서버가 멈춰도 모아 둔 조회가 사라지지 않아야 하고, 다음 반영 때 남은 것만 처리해야 한다. 이미 반영한 글을 다시 더하지 않되, 확정 직후 멈춘 그 글 하나의 1분치 중복은 허용한다 (31 §5-2, C-VIEW-1 기준 5).
- **FR-029**: 조회 기록용 저장소에 연결할 수 없으면 기록을 건너뛰고 같은 성공 응답을 줘야 하며, 글 상세는 (로그인 정보를 읽지 못하면 비회원 기준으로) 정상으로 열려야 한다 (W-6, C-VIEW-1 기준 3, 01 결정 H8).
- **FR-030**: 조회수 반영은 글의 "수정 일자"를 바꾸지 않아야 한다 (31 §5-2).
- **FR-031**: 관리자의 조회는 세지 않아야 한다. 조회 기록 요청을 보낸 사람이 관리자면 기록·중복 판정 없이 다른 경우와 같은 성공 응답(204)을 준다. 신고 검토로 연 조회가 조회수·트렌딩에 섞이지 않게 하기 위함이다 (40 R-8, 42 "다른 담당자와 맞출 것", Clarifications 2026-10-08)

**조회수 — 일별 합계·화면·개인정보**

- **FR-032**: 시스템은 글마다 날짜(한국 시간)별 조회수 합계를 저장하고, 90일이 지난 날짜의 합계는 매일 새벽 삭제해야 한다. 누적 조회수는 계속 유지되고, 글이 완전 삭제되면 일별 합계도 함께 삭제되어야 한다 (W-7, C-VIEW-1 기준 8).
- **FR-033**: 조회수는 글 상세에만 "조회 N"(형식은 FR-016)으로 보이고 목록 카드에는 보이지 않아야 한다. 숫자에 마우스를 올리거나 누르면 "같은 사람은 하루에 한 번만 세요"를 보여 주고(중복 기준을 바꾸면 문구도 맞춤), 방금 본 내 조회를 화면에서 바로 +1하지 않아야 한다 (W-8, 31 §7).
- **FR-034**: 조회수 기능이 만드는 기록(중복 판정 키·데이터베이스·조회수 관련 로그)에는 원래 접속 주소(IP)를 남기지 않아야 하고, 방문자 구분 값도 로그에 남기지 않아야 한다. 서버 접속 로그와 로그인·재설정 요청 제한(보안용)의 IP 사용은 이 규칙의 범위 밖이다. 중복 판정 기록은 기간(기본 24시간)이 지나면 자동으로 사라져야 하며, 방문자 식별 쿠키는 첫 공개 전 개인정보 처리방침 첫 판에 "조회수 중복 방지용 무작위 식별자"로 안내해야 한다 (31 §8, C-VIEW-1 기준 7, Clarifications 2026-10-08).

### Key Entities *(include if feature involves data)*

- **좋아요**: 회원 한 명과 글 하나의 쌍(쌍마다 하나만 존재), 누른 시각. 누른 시각은 트렌딩 점수식을 "최근 반응" 방식으로 바꿀 때를 위해 남긴다.
- **글의 좋아요 수 / 조회수**: 글마다 미리 계산해 두는 합계. 좋아요 수는 실제 좋아요 건수와 항상 같아야 하고, 조회수는 누적 값이다. 목록·트렌딩이 그대로 읽는다.
- **일별 조회수**: 글·날짜(한국 시간)·그날 조회 합계(1 이상). 누가 봤는지는 담지 않는다. 90일 보관.
- **방문자 구분 값**: 회원 / 무작위 방문자 식별 쿠키 / 하루짜리 변환 값 중 하나. 중복 판정에만 쓰이고 기간이 지나면 사라진다.
- **좋아요 사건**: "좋아요됨"(글, 글 작성자, 누른 사람, 시각) / "좋아요 취소됨"(글, 글 작성자, 취소한 사람, 시각). 실제로 바뀐 경우에만 생긴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 회원이 같은 글에 좋아요 요청을 동시에 20번 보내면 좋아요는 정확히 1건이고 "좋아요됨" 사건도 1건이다.
- **SC-002**: 서로 다른 50명이 같은 글에 동시에 좋아요하면 좋아요 수는 50이고, 좋아요·취소를 동시에 섞어 보내는 시험을 3회 반복해도 매번 좋아요 수가 실제 건수와 100% 같다.
- **SC-003**: 정상 운영 상태에서 매일 새벽 보정이 고치는 글은 0건이다.
- **SC-004**: 비회원·인증 전·탈퇴 유예·작성자 본인·볼 수 없는 글에 대한 좋아요 요청은 100% 거부되고 그 전후 좋아요 수가 같다.
- **SC-005**: 사용자는 좋아요 버튼을 누른 즉시(서버 응답을 기다리지 않고) 바뀐 상태를 본다.
- **SC-006**: 같은 방문자가 기간 안에 몇 번을 새로고침하거나 동시에 50번 요청해도 설정한 횟수(기본 1번)를 넘겨 세지 않는다.
- **SC-007**: 실제로 본 조회는 1분 안에 글 상세의 조회수와 그날의 일별 합계에 반영된다.
- **SC-008**: 조회 기록용 저장소가 멈춘 동안에도 글 상세는 100% 정상으로 열린다.
- **SC-009**: 반영 도중 서버를 강제로 멈췄다 다시 실행해도 모아 둔 조회가 0건 유실되고, 남은 처리 대기 묶음이 0개가 된다.
- **SC-010**: 조회수 기능이 만드는 기록(중복 판정 키·데이터베이스·조회수 관련 로그) 어디에서도 원래 접속 주소가 0건 발견된다(서버 접속 로그·로그인 요청 제한 키는 범위 밖).
- **SC-011**: 보관 정리 뒤 90일이 지난 일별 합계는 0건 남는다.

## Assumptions

- 좋아요 누른 사람 목록, 내가 좋아요한 글 목록, 댓글 좋아요는 공통 범위가 아니라 개인 확장이다 (K-11, 30 §8).
- 조회수 중복 기준은 공통 원칙 7에 따라 설정값이다. 공통 기본값은 "24시간 1회"이고, 강성찬은 원래 안 "30분 5회"를 설정과 안내 문구만 바꿔 쓸 수 있다 (W-1, 31 §11).
- 좋아요 보정 대상은 처음에는 전체 글이며, 글이 많아지면 최근 7일 안에 좋아요가 바뀐 글로 줄인다 (30 §4-1).
- 2026-10-07 회의 H7로 화면은 React + REST로 정해져 30·31의 "JS 없는/SSR 팀원용 대체 경로"(폼 전송 좋아요, 서버가 상세 응답 때 조회 기록)는 공통 범위에서 빠졌다. 따라서 스크립트를 실행하지 않는 독자의 조회는 세지 않는다.
- 01 결정 H6(2026-10-07)으로 비회원·인증 전 회원에게도 좋아요 버튼을 보인다. 42 §11의 "회원·관리자에게만 버튼" 문장과 40 §7 #6은 이 결정으로 대체된 것으로 본다.
- 관리자가 남의 글에 좋아요하는 것은 일반 회원과 같다 (42 §7).
- 정지 회원은 로그인할 수 없어 비회원과 같게 취급되며(42 P-7), 남아 있는 세션으로 쓰기를 시도하면 403 "정지 계정"으로 거부된다 (01 결정 H7).
- 알림 생성·묶기·중복 판정(같은 사람·같은 글 좋아요 알림 1번)은 → specs/011-notification, 트렌딩 점수식(좋아요·조회 누적 수 사용, 일별 조회는 점수식 B 전환 대비)은 → specs/012-trending-search, 읽기 가능 판정과 404 정책은 → specs/004-visibility-permission, 글 상세의 버튼·조회 표시 위치는 → specs/005-post-reading, 관리자 숨김은 → specs/014-report-hide, 탈퇴 정리 순서는 → specs/015-withdraw에 의존한다.
- 작성자에게 내 글 관리 화면에서 조회수를 보여 주는 것은 → specs/006-manage-delete 범위다 (41 M-8).
- 이메일 인증 여부·로그인·로그인 후 돌아오기는 → specs/001-account-auth를 따른다.

## Implementation Notes (for /speckit-plan)

원문의 기술 결정 요약. 이 절 밖의 본문에는 구현 용어를 쓰지 않았다.

- **스키마** ([51 §2](../../docs/51-erd-unified.md)): `post_like(post_id, member_id, created_at)` 복합 PK, `post_id` FK CASCADE·`member_id` FK RESTRICT, `ix_post_like_member (member_id, created_at DESC)`. `post.like_count`(INT)·`post.view_count`(BIGINT), `ck_post_counts`(음수 금지). `post_view_daily(post_id, view_date, views)` PK `(post_id, view_date)`, CASCADE, `ck_post_view_daily_views (views > 0)`, `ix_post_view_daily_date (view_date, post_id) INCLUDE (views)`. 스키마 변경 없음 (30 "ERD 변경 제안", 31 §6, 03 E-6·E-7·E-11·E-24).
- **좋아요 API** ([30 §3](../../docs/30-like.md), [02 §5-1](../../docs/02-architecture.md)): `PUT`/`DELETE /api/posts/{postId}/like` → `200 { "liked", "likeCount" }`; 401 `LOGIN_REQUIRED`, 403 `EMAIL_NOT_VERIFIED`/`ACCOUNT_WITHDRAWN`, 400 `CANNOT_LIKE_OWN_POST`([42 P-9](../../docs/42-permission-matrix.md); 30은 403), 404 `NOT_FOUND`, 429 `TOO_MANY_REQUESTS` + `Retry-After`. 오류 본문은 O8 공통 형식.
- **좋아요 처리** ([30 §4](../../docs/30-like.md)): `WITH ins AS (INSERT … ON CONFLICT DO NOTHING RETURNING post_id) UPDATE post SET like_count = like_count + 1 …`, 취소는 `WITH del AS (DELETE … RETURNING post_id) UPDATE … - 1`. 응답의 `likeCount`는 같은 트랜잭션에서 `SELECT like_count`. 동시성 검증 결과 30 §4-2 (PostgreSQL 18).
- **보정 배치** ([30 §4-1](../../docs/30-like.md)): `LEFT JOIN post_like … GROUP BY` 후 `like_count <> n`인 행만 `UPDATE … RETURNING`, ShedLock, 0건 아니면 WARN 로그.
- **권한 판정** ([42 §3](../../docs/42-permission-matrix.md), [02 §4-2](../../docs/02-architecture.md)): `PostAccessPolicy.canRead` + `status = PUBLISHED`; 공용 조건 `deleted_at IS NULL AND hidden_at IS NULL AND 작성자 withdrawn_at IS NULL`(01 H1).
- **요청 제한** ([30 §6](../../docs/30-like.md)): Redis 카운터 `rate:like:{memberId}` 60/분. Redis 장애 시 통과 + 경고 로그 ([02 §2-1](../../docs/02-architecture.md), H8).
- **이벤트** ([20 §3-3](../../docs/20-domain-events.md), [30 §6](../../docs/30-like.md)): `PostLiked(postId, postAuthorId, memberId, likedAt)`, `PostUnliked(postId, postAuthorId, memberId, unlikedAt)` — 20(2026-10-06)의 필드명을 따른다(30의 `likerId`/`authorId`, `PostUnliked{postId, likerId}`와 다름). Service에서 `ins`/`del` 결과로 판단해 발행, `@TransactionalEventListener(AFTER_COMMIT)` 구독. 모듈 `interaction/LikeService`, `ViewCountService` ([02 §3](../../docs/02-architecture.md)).
- **글 상세 연동** ([40 §2·§4·§6](../../docs/40-post-detail.md)): "내가 눌렀는지"는 상세 조회 때 `EXISTS`(PK) 1번. 조회 기록은 React 화면의 005 `useViewBeacon` 훅이 보낸다(2026-10-07 H7로 서버 화면 스크립트 `/js/post-view.js`는 쓰지 않음). 상세 응답 `Cache-Control: private, no-cache` (R-9).
- **조회 기록 API** ([31 §4](../../docs/31-view-count.md)): `POST /api/posts/{postId}/views` → 항상 `204`, 404, 429(방문자 키 60/분). `fetch(..., { keepalive: true })` + `X-XSRF-TOKEN`(001 공통 CSRF 헤더), `visibilitychange`로 1초 타이머.
- **방문자 키** ([31 §2-1](../../docs/31-view-count.md)): `m:{memberId}` / `v:{vid}` (쿠키 `vid`: UUID, 1년, `HttpOnly`, `Secure`, `SameSite=Lax`) / `h:{SHA-256(IP + User-Agent + 오늘의 비밀값)}`. IP는 02 §5 신뢰 프록시 규칙(H4)의 값.
- **제외 판정** ([31 §3](../../docs/31-view-count.md)): UA에 `bot`·`crawler`·`spider`·`preview`·`facebookexternalhit`·`Slackbot`·`kakaotalk-scrap`·`Discordbot`·`HeadlessChrome`(설정 파일), `Purpose: prefetch`/`Sec-Purpose: prefetch` 헤더.
- **설정값** ([31 §2-2](../../docs/31-view-count.md)): `blog.view.dedupe-window`(기본 `24h`), `blog.view.max-per-window`(기본 `1`).
- **Redis 집계** ([31 §5-1](../../docs/31-view-count.md)): Lua로 `INCR view:seen:{postId}:{visitorKey}` + 첫 회 `EXPIRE` + 한도 이내면 `HINCRBY view:pending:{yyyyMMdd(KST)} {postId} 1`. Redis 연결 불가 시 건너뛰고 204.
- **DB 반영** ([31 §5-2](../../docs/31-view-count.md)): 1분마다 ShedLock, `SCAN view:pending:*` → 남은 `…:processing:…` 키 먼저 → `RENAME` → 글마다 한 트랜잭션으로 `UPDATE post SET view_count = view_count + :n`(`updated_at` 변경 없음) + `INSERT … ON CONFLICT (post_id, view_date) DO UPDATE` → 커밋 후 `HDEL`. FK 오류(완전 삭제된 글)는 그 글만 건너뜀. 검증 결과 31 §9 (Redis 7 + PostgreSQL 18).
- **보관 배치** ([31 §6](../../docs/31-view-count.md)): 매일 새벽 `view_date < 오늘 - 90일` 삭제.
- **탈퇴** ([44 §4](../../docs/44-withdraw.md), [13 §3-3](../../docs/13-delete-withdraw.md)): `LikeWithdrawalPurgeStep` order 30(좋아요 삭제 + `like_count` 감소). 조회수는 정리 단계 없음.
- **Redis 장애 정책** ([02 §2-1](../../docs/02-architecture.md), 01 H8): 요청 제한 통과, 조회 기록 건너뜀, 세션 조회 실패는 비로그인 처리.
