## User Scenarios & Testing *(mandatory)*

### User Story 1 - 잃게 되는 것을 확인하고 탈퇴 신청하기 (Priority: P1)

회원이 설정 맨 아래 [회원 탈퇴]로 들어가, 한 화면에서 탈퇴하면 무엇이 사라지는지(글 수·댓글 수·받은 좋아요 수, 다시 쓸 수 없는 블로그 주소)를 숫자로 확인하고 체크한 뒤, 본인 확인(이메일 가입은 비밀번호, 소셜 가입은 "탈퇴" 입력)을 거쳐 탈퇴를 신청한다. 신청 즉시 모든 기기에서 로그아웃되고 블로그와 글은 다른 사람에게 보이지 않는다.

**Why this priority**: 탈퇴 기능의 출발점이다. 실수로 탈퇴하지 않도록 하는 안내·확인과, 신청 즉시 콘텐츠가 가려지는 효과가 함께 있어야 의미가 있다.

**Independent Test**: 글 24개·남의 글 댓글 18개·받은 좋아요 126개인 회원으로 탈퇴 화면을 열어 숫자가 맞는지, 체크·본인 확인 없이는 버튼이 비활성이고 서버도 거부하는지, 신청 후 다른 기기 세션이 끊기고 블로그가 404인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원이 탈퇴 화면을 열었을 때, **When** 안내를 보면, **Then** 블로그 주소와 글 수(휴지통 포함), 남의 글에 쓴 댓글 수, 복구 기한(신청 시각 + 30일), 30일 뒤 지워지는 받은 좋아요 수, "블로그 주소는 다른 사람도, 나도 다시 쓸 수 없어요"가 보인다 (W-3).
2. **Given** 확인 체크나 본인 확인을 하지 않았을 때, **When** [탈퇴하기]를 누르려 하면, **Then** 버튼이 비활성이고, 요청을 직접 보내도 서버가 거부한다 (44 완료 기준 1).
3. **Given** 이메일 가입 회원이 비밀번호를 5번 연속 틀렸을 때, **When** 다시 탈퇴를 시도하면, **Then** 15분 동안 시도할 수 없다 (44 완료 기준 2, W-8).
4. **Given** 소셜 가입 회원이 "탈퇴"가 아닌 글자를 입력했을 때, **When** [탈퇴하기]를 누르면, **Then** 확인 문구 불일치로 거부된다.
5. **Given** 관리자 권한이 있는 회원, **When** 탈퇴를 신청하면, **Then** "관리자 권한을 해제한 뒤 탈퇴할 수 있어요"로 거부된다 (44 완료 기준 6, W-6).
6. **Given** 탈퇴를 신청했을 때, **When** 다른 기기에서 요청하면, **Then** 로그인 상태가 아니고, 완료 화면에 복구 기한이 보이며, 이메일이 있는 계정에는 탈퇴 접수 메일이 간다 (44 완료 기준 3, 13 §5 탈퇴 1, W-5).
7. **Given** 탈퇴 신청 직후, **When** 다른 사람이 그 블로그·글을 열거나 홈·검색·피드를 보면, **Then** 블로그·글은 404이고 어떤 목록에도 없으며, 남의 글에 쓴 댓글은 "탈퇴한 사용자의 댓글이에요"로 보인다 (13 §3-1).

### User Story 2 - 유예 기간 안에 복구하기 (Priority: P1)

탈퇴를 신청한 회원이 30일 안에 로그인하면 복구 화면만 보이고, [복구하기]를 누르면 블로그·글·댓글이 탈퇴 전과 똑같이 돌아온다. 로그인만으로는 복구되지 않는다.

**Why this priority**: 30일 유예의 존재 이유이며, 세션 탈취 등 본인이 하지 않은 탈퇴를 되돌리는 안전장치다. 신청(US1)과 함께 있어야 데이터 정책(13 D-6)이 성립한다.

**Independent Test**: 탈퇴 유예 회원으로 로그인해 어떤 주소로 가도 복구 화면만 보이는지, [복구하기] 후 블로그·글·댓글·좋아요 수·팔로워 수가 탈퇴 전과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 탈퇴 유예 회원, **When** 로그인하면, **Then** "탈퇴 신청한 계정이에요 / {기한}까지 복구할 수 있어요 ({N}일 남음)"과 [로그아웃]·[복구하기]만 보인다 (44 §3).
2. **Given** 복구 화면 상태, **When** 다른 주소로 가거나 다른 기능을 요청하면, **Then** 복구 화면으로 돌아오고 요청은 "탈퇴 유예 계정" 이유로 거부된다 (44 완료 기준 4, 42 P-12).
3. **Given** 복구 화면, **When** [복구하기]를 누르면, **Then** 계정이 활동 상태로 돌아오고 블로그·글·댓글이 탈퇴 전과 같으며, 홈으로 이동해 "다시 오신 걸 환영해요"가 보이고 복구 완료 메일이 간다 (44 완료 기준 5, 13 §5 탈퇴 2).
4. **Given** 복구 화면, **When** [로그아웃]을 누르면, **Then** 로그아웃만 되고 유예는 계속된다.
5. **Given** 유예 회원이 비밀번호를 잊었을 때, **When** 로그인 화면에서 [비밀번호 찾기]를 쓰면, **Then** 재설정할 수 있다 (13 §3-2).
6. **Given** 유예 중인 계정의 이메일로, **When** 새로 가입하려 하면, **Then** "탈퇴 신청한 계정이 있어요. 로그인하면 복구할 수 있어요"가 보인다 (13 §3-2, 회의 P2 A안).

### User Story 3 - 30일 뒤 개인 정보 정리 (Priority: P2)

유예 30일이 지나면 시스템이 그 회원의 글·사진·댓글·좋아요·로그인 수단·관계·알림을 정리하고, 회원 기록은 블로그 주소만 남긴 익명 껍데기로 바꾼다. 회원 한 명의 정리는 전부 성공하거나 전부 취소된다.

**Why this priority**: 개인 정보를 실제로 지우는 데이터 정책(13 §3-3, 확정)이지만 사용자가 직접 조작하는 흐름은 아니다.

**Independent Test**: 글·댓글(답글 있음/없음)·좋아요·사진·팔로우·친구·알림·신고를 가진 회원을 유예 30일이 지난 상태로 만들고 정리를 실행해, 13 §5 "회원 탈퇴 데이터" 기준 1~6과 44 완료 기준 7~9를 확인한다. 정리 중 한 단계를 일부러 실패시켜 모든 변경이 취소되는지도 확인한다.

**Acceptance Scenarios**:

1. **Given** 유예 30일이 지난 회원, **When** 정리가 실행되면, **Then** 이메일·닉네임·소개·최근 활동 일자가 남지 않고, 블로그 주소는 남아 다른 사람이 쓸 수 없다 (13 §5 탈퇴 3, 44 완료 기준 9).
2. **Given** 그 회원이 남의 글에 쓴 댓글 중 답글이 달린 것과 없는 것, **When** 정리 후 보면, **Then** 답글이 달린 댓글만 "탈퇴한 사용자의 댓글이에요"로 자리가 남고 나머지는 사라지며, 각 글의 댓글 수·좋아요 수가 실제 남은 수와 같다 (13 §5 탈퇴 4, 44 완료 기준 7).
3. **Given** 정리 중 한 단계가 실패할 때, **When** 결과를 보면, **Then** 그 회원의 정리는 앞 단계까지 모두 취소되고 다음 날 다시 시도된다 (44 완료 기준 8).
4. **Given** 그 회원의 콘텐츠에 대기 중 신고가 있었을 때, **When** 정리 후 보면, **Then** 신고는 "대상 없음"으로 닫히고, 그 회원이 쓴 신고의 설명은 비어 있으며, 동의·정지 이력 기록은 남아 있다 (13 §5 탈퇴 6).
5. **Given** 그 회원이 올린 사진, **When** 정리 후 다음 사진 정리 작업이 돌면, **Then** 사진이 저장소에 남지 않는다 (13 §5 탈퇴 3, 2026-10-07 "탈퇴 회원 사진").
6. **Given** 정리 후, **When** 누군가 옛 블로그 주소를 열면, **Then** 404이고, 남은 댓글의 작성자는 "탈퇴한 사용자"와 회색 기본 아이콘으로 보인다 (13 §3-4).

### User Story 4 - 같은 이메일로 다시 가입하기 (Priority: P3)

정리가 끝난 뒤 같은 이메일(또는 같은 소셜 계정)로 가입하면 새 계정이 만들어진다. 옛 블로그 주소는 예약되어 있어 다른 주소가 된다.

**Why this priority**: 로그인 수단 삭제(13 D-11)의 결과로 자연히 성립하며 별도 화면이 거의 없다.

**Independent Test**: 정리가 끝난 회원의 이메일로 가입해 새 계정이 만들어지고 블로그 주소가 `옛주소_2` 형태가 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 익명 처리가 끝난 회원의 이메일, **When** 그 이메일로 가입하면, **Then** 새 계정이 만들어진다 (13 §5 탈퇴 5).
2. **Given** 옛 주소가 `kim755030`이었을 때, **When** 같은 이메일로 다시 가입하면, **Then** 주소는 `kim755030_2`처럼 다른 값이 된다 (13 §3-4, → specs/001-account-auth).
3. **Given** 옛 닉네임, **When** 익명 처리 직후 다른 사람이 그 닉네임을 쓰려 하면, **Then** 쓸 수 있다 (D-8, 09 N-11).

### Edge Cases

- 이메일 인증 전 회원도 탈퇴할 수 있다 (42 §9).
- 정지된 회원은 로그인할 수 없으므로 정지 기간에는 탈퇴 화면에 들어갈 수 없다 (42 §9). 정지 중 탈퇴를 원할 때의 경로는 FR-008의 미결 사항이다.
- 탈퇴 유예 중인 회원은 정지할 수 없다 (13 §3-2, → specs/014-report-hide).
- 유예 중 그 회원에게 새 알림이 만들어지지 않고, 그 회원의 행동으로도 알림이 생기지 않는다. 이미 있는 알림에서 그 회원은 "탈퇴한 사용자"로 보인다 (25 §8, → specs/011-notification).
- 유예 중 그 회원이 누른 좋아요는 그대로 남아 반응 수가 유지되고, 그 회원의 댓글은 행이 남아 댓글 수에 계속 포함된다 (13 §3-2, 21 CM-11).
- 유예 중 그 회원은 다른 사람의 팔로워·팔로잉 목록과 수에서 빠지고, 복구하면 돌아온다 (24 F-6).
- 유예 중 그 회원 콘텐츠의 대기 신고는 그대로 대기한다. 익명 처리 때 닫힌 사건의 스냅샷은 그로부터 30일 뒤 비워지므로 탈퇴 신청부터 최대 약 60일 남는다 (2026-10-07 결정).
- 복구 기한(신청 + 30일)이 지났지만 그날의 정리 작업이 아직 돌지 않은 사이에 로그인하는 경우, 원문에 따로 규정이 없다. 계정이 아직 유예 상태이므로 복구 화면 규칙(FR-014)을 그대로 따른다고 본다 (Assumptions).
- 브라우저에 남은 임시 글 데이터는 탈퇴 완료 시 로그아웃과 같이 지운다 (44 §2, 07 §7).
- 이메일이 없는 소셜 계정에는 탈퇴 접수·복구 메일을 보내지 않는다 (W-5 "이메일이 있는 계정").
- 탈퇴 회원 사진은 브라우저 캐시를 제외한 우리 저장소 기준으로 지워진다 (23 §6-3).

## Requirements *(mandatory)*

### Functional Requirements

**탈퇴 신청 화면 (44 §1·§2, 13 §3-1)**

- **FR-001**: System MUST 설정 화면 맨 아래에 [회원 탈퇴]를 두고 탈퇴 화면으로 연결해야 한다 (W-1, 11 §2).
- **FR-002**: System MUST 한 화면 안에 ① 안내·확인 체크 → ② 본인 확인 → [탈퇴하기]를 두고, ①을 체크하고 ②를 채워야만 [탈퇴하기]가 활성화되며, 서버도 확인 없는 요청을 거부해야 한다 (W-2, 44 완료 기준 1).
- **FR-003**: System MUST 화면을 열 때 계산한 숫자로 다음을 안내해야 한다: 블로그 주소와 내 글 수(휴지통 포함 전체)가 바로 보이지 않게 된다는 것, 남의 글에 쓴 댓글 수가 "탈퇴한 사용자의 댓글이에요"로 가려진다는 것, 복구 기한(신청 시각 + 30일, 날짜·시각)까지 로그인하면 복구할 수 있다는 것, 30일 뒤 글·사진·받은 좋아요(합계 수)가 완전히 삭제되고 되돌릴 수 없으며 답글이 달린 댓글은 내용 없이 자리만 남는다는 것, 블로그 주소는 다른 사람도 나도 다시 쓸 수 없다는 것 (W-3, 13 §3-1).
- **FR-004**: System MUST 탈퇴 사유를 묻지 않고 저장하지도 않아야 한다 (W-4).
- **FR-005**: System MUST 본인 확인을 이메일 가입 회원은 현재 비밀번호로, 소셜 가입 회원은 "탈퇴" 직접 입력으로 받아야 한다. 비밀번호가 틀리거나 문구가 다르면 거부한다 (13 §3-1, 44 §2).
- **FR-006**: System MUST 탈퇴 본인 확인에서 비밀번호를 5번 연속 틀리면 15분 동안 탈퇴 시도를 막아야 한다 (비밀번호 변경과 같은 규칙) (W-8, 11 §6-2, 44 완료 기준 2).
- **FR-007**: System MUST [탈퇴하기] 버튼이 기본 선택(포커스) 상태가 아니게 해서 Enter로 바로 눌리지 않게 해야 한다 (44 §2).
- **FR-008**: System MUST 관리자 권한이 있는 회원의 탈퇴를 "관리자 권한을 해제한 뒤 탈퇴할 수 있어요"로 거부하고(W-6), 이메일 인증 전 회원의 탈퇴는 허용해야 한다(42 §9). 정지 중인 회원의 탈퇴 요청 경로와 영구 정지 계정의 개인정보 보유 기간은 [NEEDS CLARIFICATION: 13 §3-2가 "미정 (검증 M11, 43 §6과 함께 정한다)"으로 남겼다. 정지 회원은 로그인할 수 없어(42 P-7) 탈퇴 화면에 들어갈 수 없고, 영구 정지 계정은 탈퇴 없이 개인정보가 무기한 남는다]

**신청 즉시 효과 (13 §3-1·§3-2, 44 §2)**

- **FR-009**: System MUST 탈퇴 신청 즉시 계정을 탈퇴 유예 상태로 바꾸고 신청 시각을 기록하며, 그 회원의 모든 기기 로그인을 즉시 끊어야 한다 (13 §3-1, 44 완료 기준 3, 13 §5 탈퇴 1).
- **FR-010**: System MUST 유예 중 그 회원의 블로그와 글 전부를 없는 것과 같이 404로 다루고 모든 목록·검색·피드·트렌딩·태그·글 수에서 빼야 한다. 글 데이터는 그대로 둔다 (13 §3-2, 06 R-2a, → specs/004-visibility-permission).
- **FR-011**: System MUST 유예 중 그 회원의 댓글을 지우지 않고 화면에서만 "탈퇴한 사용자의 댓글이에요"(작성자 "탈퇴한 사용자")로 가리고, 글의 댓글 수에는 계속 포함해야 한다 (13 §3-2, 21 §11·CM-11, → specs/007-comment).
- **FR-012**: System MUST 유예 중 그 회원이 누른 좋아요를 그대로 두고, 그 회원을 다른 사람의 팔로워·팔로잉 목록과 수에서 빼야 한다 (13 §3-2, 24 F-6).
- **FR-013**: System MUST 유예 중 그 회원의 닉네임과 블로그 주소를 묶어 두어 다른 사람이 쓸 수 없게 해야 한다 (13 §3-2, D-8).
- **FR-014**: System MUST 유예 중 그 회원에게 새 알림을 만들지 않고 그 회원의 행동으로도 알림을 만들지 않아야 한다 (44 §2, 25 §8, → specs/011-notification).
- **FR-015**: System MUST 신청이 끝나면 로그아웃된 상태로 완료 화면("탈퇴 신청이 완료됐어요 / {기한}까지 로그인하면 복구할 수 있어요 / 그동안 블로그와 글은 다른 사람에게 보이지 않아요" + [홈으로])을 보여주고, 브라우저에 남은 임시 글 데이터를 지워야 한다 (44 §2).
- **FR-016**: System MUST 이메일이 있는 계정에 탈퇴 접수 메일(복구 기한 안내)을 보내야 한다 (W-5).

**유예 중 로그인·복구 (44 §3, 13 §3-2, 42 P-12)**

- **FR-017**: System MUST 유예 회원이 로그인하면 항상 복구 화면("탈퇴 신청한 계정이에요 / {기한}까지 복구할 수 있어요 ({N}일 남음) / 복구하면 블로그·글·댓글이 모두 원래대로 돌아와요" + [로그아웃]·[복구하기])만 보여주고, 다른 주소로 가면 복구 화면으로 돌려보내며, 그 밖의 요청은 탈퇴 유예 계정 이유(403)로 거부해야 한다 (44 §3, 42 P-12, 44 완료 기준 4).
- **FR-018**: System MUST 로그인만으로는 복구하지 않고, 사용자가 [복구하기]를 눌러야 복구해야 한다 (W-9).
- **FR-019**: System MUST [복구하기] 시 계정을 활동 상태로 되돌리고 신청 시각을 지워, 블로그·글·댓글·좋아요·팔로우 노출이 탈퇴 전과 같아지게 해야 하며, 홈으로 보내 "다시 오신 걸 환영해요"를 보여주고 이메일이 있는 계정에 복구 완료 메일을 보내야 한다 (44 §3, W-5, 44 완료 기준 5, 13 §5 탈퇴 2).
- **FR-020**: Users MUST be able to 복구 화면에서 [로그아웃]만 할 수 있어야 하며, 이때 유예는 계속된다 (44 §3).
- **FR-021**: System MUST 유예 회원의 비밀번호 재설정을 허용해야 한다 (13 §3-2).
- **FR-022**: System MUST 유예 중인 계정과 같은 이메일로 가입하려 하면 "탈퇴 신청한 계정이 있어요. 로그인하면 복구할 수 있어요"를 보여주어야 한다. 이메일만으로 탈퇴 신청 여부가 드러나는 것은 감수한다 (13 §3-2, 44 결정 기록 회의 P2 A안).

**30일 뒤 익명 처리 (13 §3-3, 44 §4)**

- **FR-023**: System MUST 매일 한 번(여러 서버 중 한 곳에서만), 탈퇴 신청 후 30일이 지났고 아직 익명 처리되지 않은 회원을 찾아 정리해야 한다 (13 §3-3 배치).
- **FR-024**: System MUST 회원 한 명의 정리를 하나의 단위로 처리해, 모든 단계가 성공하거나 하나라도 실패하면 그 회원의 모든 변경을 취소하고 다음 날 다시 시도해야 한다 (44 완료 기준 7·8, 13 §3-3).
- **FR-025**: System MUST 다음 순서로 정리해야 한다 (13 §3-3, 44 §4):
  1. 내 글 전부(휴지통 포함)를 글 완전 삭제 규칙대로 지운다. 그 글과 그 글 댓글의 대기 신고는 "대상 없음"으로 닫히고, 남이 내 글에 쓴 댓글·좋아요·관련 알림도 함께 지워진다 (→ specs/006-manage-delete).
  2. 남의 글에 쓴 내 댓글: 답글이 달린 댓글은 내용을 비우고 "탈퇴한 사용자의 댓글이에요" 자리로 남기고, 답글이 없는 댓글은 지우며, 해당 글의 댓글 수를 줄인다 (D-7, → specs/007-comment).
  3. 내가 누른 좋아요를 지우고 해당 글의 좋아요 수를 줄인다 (→ specs/009-like-view).
  4. 내가 올린 사진 전부(현재 프로필 사진 포함)를 연결 해제해 다음 사진 정리 때 파일까지 지워지게 한다 (→ specs/003-image-upload).
  5. 로그인 수단을 지워 같은 이메일·소셜 계정이 풀리게 한다 (D-11).
  6. 친구 관계(요청 중·수락 모두, 어느 쪽이든)를 지운다. 친구 맺기는 공통이라 항상 실행한다 (2026-10-07 회의 M1, C-FRIEND-1).
  7. 팔로우 관계를 양방향 모두 지운다 (24 §6, → specs/010-follow-feed).
  8. 알림: 내가 받은 알림을 지우고, 남의 묶음 알림에서 나를 빼 다시 계산하며(0명이면 삭제), 내가 행동한 하나짜리 알림을 지운다. 글·댓글 단계 다음에 실행한다 (25 §8, → specs/011-notification).
  9. 신고: 내 콘텐츠의 대기 사건을 "대상 없음"으로 닫고(처리 시각 기록, 처리 관리자 없음), 내가 쓴 신고의 설명을 비운다(사유는 유지) (13 §3-3 6-3, → specs/014-report-hide).
  10. 회원 기록 익명화: 닉네임·소개·닉네임 변경 시각·최근 활동 시각을 비우고 익명 처리 시각을 기록한다. 블로그 주소는 그대로 둔다. 회원 기록 익명화는 마지막 단계다 (13 §3-3 7, D-9, D-10, C-ACT-1).
  11. 정리가 확정된 뒤 그 회원의 로그인 세션·토큰·실패 횟수·요청 횟수 기록을 지운다 (13 §3-3 8).
- **FR-026**: System MUST 정리 후 각 글의 댓글 수·좋아요 수가 실제로 남은 댓글·좋아요 수와 같아야 한다 (13 §5 탈퇴 4, 44 완료 기준 7).
- **FR-027**: System MUST 정리 후 회원 기록에 블로그 주소 외 개인 정보(이메일·닉네임·소개·사진·최근 활동 일자)를 남기지 않아야 하며, 사진은 다음 사진 정리 작업 뒤 저장소에 남지 않아야 한다 (13 §5 탈퇴 3, 44 완료 기준 9).
- **FR-028**: System MUST 정리 후에도 동의 기록(이용약관·개인정보 처리방침·AI 동의, 버전·일자)과 정지 이력은 지우지 않아야 한다 (D-10, 13 §5 탈퇴 6, 07 §3-1, 2026-10-07 회의 E6).
- **FR-029**: System MUST 정리 단계 순서를 지켜, 새 정리 단계가 추가되어도 기존 단계의 순서가 바뀌지 않게 해야 한다 (44 §4).

**익명 처리 후 (13 §3-4, D-8, D-9, D-11)**

- **FR-030**: System MUST 익명 처리된 회원의 옛 블로그 주소를 영구히 예약해, 그 주소를 열면 404이고 다른 사람도 본인도 다시 쓸 수 없게 해야 한다 (D-9, 08 §6).
- **FR-031**: System MUST 익명 처리 즉시 그 닉네임을 해제해 다른 사람이 쓸 수 있게 해야 한다 (D-8, 09 N-11, C-AUTH-2).
- **FR-032**: System MUST 남아 있는 댓글의 작성자를 "탈퇴한 사용자", 내용을 "탈퇴한 사용자의 댓글이에요", 프로필을 회색 기본 아이콘으로 보여주어야 한다 (13 §3-4).
- **FR-033**: System MUST 같은 이메일·소셜 계정으로 다시 가입하면 새 계정을 만들고, 옛 주소는 예약 중이므로 다른 주소(예: `옛주소_2`)를 주어야 한다 (D-11, 13 §3-4, 13 §5 탈퇴 5).

### Key Entities *(include if feature involves data)*

- **회원**: 상태(활동 / 정지 / 탈퇴 유예), 탈퇴 신청 시각(유예 기한 계산), 익명 처리 시각, 블로그 주소(영구 보존), 닉네임·소개·최근 활동 시각(익명 처리 때 비움), 역할(관리자는 탈퇴 불가). 탈퇴 유예 상태와 신청 시각은 항상 함께 있다.
- **로그인 수단**: 이메일·소셜 계정과 회원의 연결. 익명 처리 때 지워져 같은 이메일로 새 가입이 가능해진다.
- **동의 기록·정지 이력**: 익명 처리 뒤에도 남는다(분쟁 증빙, 재가입 악용 확인).
- **정리 단계**: 기능 영역별로 회원 한 명의 데이터를 지우는 처리. 정해진 순서로 한 단위 안에서 실행된다.
- **연관 데이터**: 글·댓글·좋아요·사진·친구·팔로우·알림·신고 — 각 기능 spec이 소유하고, 이 기능은 유예 중 노출 규칙과 30일 뒤 정리 순서를 정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 탈퇴 신청 직후 그 회원의 기존 세션으로 보낸 요청이 로그인 상태로 처리되는 경우가 0건이고, 그 회원의 블로그·글이 다른 사람에게 보이는 경우가 0건이다.
- **SC-002**: 유예 중 복구하면 블로그·글·댓글·좋아요 수·팔로워 수가 탈퇴 전과 100% 같다.
- **SC-003**: 30일 뒤 정리에서 일부 단계만 반영된 회원이 0명이다 (전부 성공 또는 전부 취소).
- **SC-004**: 정리 후 댓글 수·좋아요 수가 실제 남은 행 수와 다른 글이 0개다.
- **SC-005**: 정리 후 익명 회원 기록에서 블로그 주소 외 개인 정보가 발견되는 경우가 0건이고, 사진은 탈퇴 신청 후 30일 + 사진 정리 1회 안에 저장소에서 사라진다.
- **SC-006**: 탈퇴한 회원의 블로그 주소가 다른 계정에 다시 배정되는 경우가 0건이다.
- **SC-007**: 확인 체크·본인 확인 없이 탈퇴가 처리된 경우가 0건이고, 관리자 계정의 탈퇴가 0건이다.

## Assumptions

- **화면·기능은 Tier C, 데이터 정책은 확정**이다 (01 §2-3 "회원 탈퇴": 30일 유예 → 익명 처리, 13 §3). 44 원문은 "초안 (항목 확인 중)" 상태이며, 2026-10-07 회의로 바뀐 부분(동의·정지 이력 유지, 신고 분리, 사진 정리 시점, 세션 쿠키)은 13·51을 따랐다.
- 30일 정리의 각 단계 세부 규칙은 해당 기능 spec이 소유한다: 글 완전 삭제(specs/006-manage-delete), 댓글(specs/007-comment), 좋아요(specs/009-like-view), 사진(specs/003-image-upload), 팔로우(specs/010-follow-feed), 알림(specs/011-notification), 신고(specs/014-report-hide), 로그인 수단·친구·최근 활동·주소 예약(specs/001-account-auth). 조회수는 정리할 개인 데이터가 없다(31).
- 공용 노출 조건(작성자 탈퇴 신청 시 제외)은 specs/004-visibility-permission이 정의하므로 각 목록이 따로 처리하지 않는다 (44 맞출 것).
- 복구 기한이 지났지만 정리 작업이 아직 그 회원을 처리하지 않은 짧은 사이에는 계정이 여전히 유예 상태이므로 복구 화면 규칙을 그대로 따른다고 본다(원문에 별도 규정 없음).
- 관리자 권한을 해제하는 방법은 원문에 없어 범위 밖으로 둔다.
- 탈퇴 본인 확인의 비밀번호 실패 횟수는 비밀번호 변경(11 §6-2)과 같은 규칙이며, 같은 횟수를 공유하는지는 구현에서 정한다.
- **개인 확장(범위 밖)**: 탈퇴 전 글 내보내기(W-7), 가입 중복·탈퇴 여부를 메일로만 알리는 방식(회의 P2 B안).
- 유예 30일 정리는 사용자에게 보이는 이벤트를 만들지 않는다 (20 §3-6).

## Implementation Notes (for /speckit-plan)

- 화면 주소: `/settings/withdraw`, 완료 `/withdrawn`, 복구 `/account/restore` ([44 §2·§3](../../docs/44-withdraw.md)).
- API: `POST /api/me/withdraw { password?, confirmText? }` → 실패 `400 CURRENT_PASSWORD_MISMATCH`(5회 잠금), `400 CONFIRM_TEXT_MISMATCH`, `409 ADMIN_CANNOT_WITHDRAW`. `POST /api/me/restore`. 유예 회원의 다른 요청은 `403 ACCOUNT_WITHDRAWN`([42 P-12](../../docs/42-permission-matrix.md)). 44 §3의 "SSR 302"는 2026-10-07 회의 H7(React + REST)로 React가 403을 받아 복구 화면으로 보내는 방식으로 읽는다.
- 상태 전이: 신청 `status = WITHDRAWN`, `withdrawn_at = now()`, Spring Session Redis 세션 전부 삭제 → 커밋 후 `MemberWithdrawn(memberId, withdrawnAt)`. 복구 `status = ACTIVE`, `withdrawn_at = null` → 커밋 후 `MemberRestored(memberId, restoredAt)` ([20 §3-6](../../docs/20-domain-events.md)). 30일 뒤 처리는 이벤트 없음(`MemberPurged` 없음). 글 삭제의 `PostPurged`는 post 모듈 규칙.
- 스키마([13 §4](../../docs/13-delete-withdraw.md), [51](../../docs/51-erd-unified.md)): `member.withdrawn_at`, `member.deleted_at`(익명 처리 일자), `ck_member_withdrawn`, `ck_member_deleted`, `ck_member_nickname_null`, `ix_member_withdraw_purge`, `uq_member_nickname`(NULL 무시 → 즉시 해제). 44 ERD 변경 없음.
- 정리 작업: `WithdrawPurgeJob`(매일 새벽, ShedLock), 대상 `status = 'WITHDRAWN' AND deleted_at IS NULL AND withdrawn_at < now() - 30일`, 회원 1명 `@Transactional`. 모듈마다 `WithdrawalPurgeStep { int order(); void purge(long memberId); }`를 `order()` 순으로 실행 ([44 §4](../../docs/44-withdraw.md)): 10 Post(공통 post) / 20 Comment(강성찬) / 30 Like(김민서) / 40 Image(강성찬, [23 §6-2](../../docs/23-image.md)) / 50 AuthIdentity(공통 account) / 60 Friendship(항상 실행, M1) / 65 Follow / 70 Notification(25 §8 ①②③, DELETE와 UPDATE 분리) / 80 Report(나민서) / 90 Member(공통 account) / 커밋 후 Redis 키 삭제. `order`는 10 단위, 새 단계는 사이 값.
- 13 §3-3 SQL: 사진 `UPDATE image SET detached_at = now() - interval '7 days' WHERE uploader_id = :me AND (...)`(다음 정리 배치가 즉시 삭제, 2026-10-07 "탈퇴 회원 사진"), 신고 `UPDATE report_case SET status='CLOSED_NO_TARGET', handled_at=now(), handled_by=NULL WHERE target_author_id=:me AND status='PENDING'` + `UPDATE report SET detail = NULL WHERE reporter_id = :me`, 회원 `UPDATE member SET nickname=NULL, bio=NULL, nickname_changed_at=NULL, last_active_at=NULL, deleted_at=now()`.
- 44 §4 order 90의 "`ai_consent_at`·`suspended_until`·`suspended_reason` null"은 통합 V1에서 해당 컬럼이 `member_agreement`·`member_suspension`으로 옮겨졌고(E2·E3), 익명 처리 때 두 표의 행은 남긴다(E6, 13 §3-3 7, 07 §3-1) → 지우지 않는다.
