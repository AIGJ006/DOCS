## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이메일로 가입하고 인증한 뒤 로그인·로그아웃한다 (Priority: P1)

방문자가 이메일·블로그 주소·비밀번호·닉네임을 입력하고 필수 약관 두 개에 동의해 계정을 만든다. 받은 인증 메일의 링크를 누르면 글쓰기 등 쓰기 기능을 쓸 수 있다. 로그인 상태는 14일 유지되고, 로그아웃하면 서버의 로그인 상태와 그 사용자의 브라우저 임시 데이터가 지워진다. (C-AUTH-1)

**Why this priority**: 모든 쓰기 기능(글·댓글·사진·좋아요·신고)의 전제다. 이 흐름 하나만 있어도 회원 기반 서비스가 동작한다.

**Independent Test**: 새 이메일로 가입 → 인증 전 글쓰기 시도(거부 확인) → 인증 링크 클릭 → 글쓰기 허용 확인 → 로그아웃 → 쓰기 요청 거부 확인으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 가입한 적 없는 이메일, **When** 규칙에 맞는 입력과 필수 동의 2개로 가입하면, **Then** 계정이 하나 생기고 인증 전 상태가 되며 24시간 유효한 인증 메일이 발송되고, 이용약관·개인정보 처리방침 동의가 버전·시각과 함께 기록된다.
2. **Given** 같은 이메일로 이미 이메일 가입한 계정, **When** 같은 이메일(대소문자·앞뒤 공백만 다름 포함)로 다시 이메일 가입하면, **Then** 새 계정은 생기지 않고 "이미 가입된 이메일이에요. [로그인] [비밀번호 찾기]"가 보인다. (C-AUTH-1 #1)
3. **Given** 인증 전 회원이 로그인한 상태, **When** 글쓰기·댓글·사진 업로드·좋아요·신고를 요청하면, **Then** 계정 상태 거부(403)와 "인증 메일 다시 보내기" 안내를 받고 아무것도 바뀌지 않는다. (C-AUTH-1 #3, 42 P-6)
4. **Given** 이미 한 번 사용했거나 24시간이 지난 인증 링크, **When** 그 링크를 열면, **Then** "링크가 만료됐어요. [인증 메일 다시 보내기]"가 보이고 인증되지 않는다. (C-AUTH-1 #8)
5. **Given** 1분 안에 인증 메일을 이미 재발송한 회원, **When** 다시 재발송을 요청하면, **Then** 거부되고, 새 메일이 발송되면 이전 링크는 무효가 된다.
6. **Given** 로그인한 회원, **When** 로그아웃한 뒤 그 브라우저로 쓰기 요청을 보내면, **Then** 로그인 필요(401)로 거부되고 그 사용자의 브라우저 임시 글 데이터·백업은 이미 지워져 있다. (C-AUTH-1 #2)
7. **Given** 8자 미만·16자 초과이거나 영문·숫자·특수문자 중 하나라도 없는 비밀번호, **When** 가입하려 하면, **Then** 가입되지 않고 입력 중에 규칙별 충족 여부가 글자와 ✓로 표시된다. (C-AUTH-1 #4)

### User Story 2 - Google·GitHub 계정으로 가입·로그인한다 (Priority: P1)

방문자가 [Google로 계속하기] 또는 [GitHub로 계속하기]를 누른다. 처음이면 가입 마무리 화면에서 닉네임·블로그 주소·약관 동의를 마친 뒤에야 계정이 생기고, 원하면 소셜 프로필 사진이 우리 저장소로 복사된다. 이미 연결된 소셜 계정이면 바로 로그인된다. (C-AUTH-1)

**Why this priority**: 세 팀원의 공통 로그인 수단(이메일 + Google + GitHub)이며, 개발자 사용자 다수가 소셜 로그인을 쓴다.

**Independent Test**: 테스트용 소셜 계정으로 첫 로그인 → 마무리 화면 → 계정 생성 → 로그아웃 → 같은 소셜 계정으로 다시 로그인했을 때 같은 계정인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 처음 쓰는 Google 계정, **When** 소셜 인증을 마치면, **Then** 계정은 아직 생기지 않고 가입 마무리 화면(닉네임 미리 채움, `go-` 고정 접두어 + 수정 가능한 본문, 약관 동의, "프로필 사진 사용" 기본 체크)이 전체 페이지로 열린다.
2. **Given** 마무리 화면에서 10분 넘게 머문 경우, **When** 가입 완료를 누르면, **Then** 보관하던 소셜 인증 정보가 만료되어 계정이 만들어지지 않는다.
3. **Given** 이미 가입한 GitHub 계정(그 사이 GitHub 쪽 이메일·로그인 이름이 바뀜), **When** 다시 GitHub로 로그인하면, **Then** 새 계정이 아니라 기존 계정으로 로그인된다.
4. **Given** 같은 이메일로 이메일 가입한 계정이 있는 사람, **When** 그 이메일의 Google 계정으로 처음 로그인해 마무리하면, **Then** 별도 계정이 하나 더 생긴다(자동 합치기·계정 연결 없음). (L-1)
5. **Given** "프로필 사진 사용"을 켠 채 가입 완료, **When** 브라우저가 5초 안에 소셜 사진을 받지 못하면, **Then** 가입은 성공하고 기본 이미지가 쓰이며 "소셜 사진을 가져오지 못했어요. 설정에서 직접 올릴 수 있어요"가 안내된다.
6. **Given** 소셜 사진을 가져와 가입한 회원, **When** 그 회원의 프로필 사진 정보를 확인하면, **Then** 우리 저장소에 복사된 256×256 사진이 연결되어 있고 소셜 서비스의 사진 주소는 어디에도 저장되어 있지 않다. (C-AUTH-2 #6)

### User Story 3 - 가입할 때 블로그 주소와 닉네임을 정한다 (Priority: P1)

가입자는 이메일에서 미리 채워진 블로그 주소를 가입할 때 한 번만 고칠 수 있고, 2~10자 닉네임을 정한다. 주소는 가입 후 바꿀 수 없고 탈퇴 후에도 다시 쓰이지 않는다. (C-AUTH-2, C-BLOG-1의 주소 규칙)

**Why this priority**: `/@주소`는 블로그·글 주소의 바탕이고 바꿀 수 없으므로 가입 시점에 올바르게 정해져야 한다.

**Independent Test**: 08 §3 예시 이메일들로 미리 채우기 결과를 비교하고, 09 §2~§7 예시 닉네임들로 허용·거부를 확인한다.

**Acceptance Scenarios**:

1. **Given** `kim755030@naver.com` 이메일 가입, `kim755030@gmail.com` Google 가입, `kim755030@naver.com` GitHub 가입, **When** 차례로 가입하면, **Then** 주소가 `kim755030` / `go-kim755030` / `gi-kim755030`으로 겹치지 않는다. (08 #1)
2. **Given** `Kim.Min-Seo+blog@naver.com`, **When** 이메일 가입 화면에 입력하면, **Then** 주소 칸이 `kim_min_seo`로 채워지고 대문자와 `-`가 없다. (08 #2)
3. **Given** 사용자가 주소 칸을 직접 고친 뒤, **When** 이메일을 다시 바꾸면, **Then** 주소 칸은 더 이상 자동으로 바뀌지 않는다.
4. **Given** 두 사람이 같은 주소로 동시에 가입, **When** 둘 다 가입 버튼을 누르면, **Then** 한 명만 그 주소를 갖고, 늦은 쪽에는 "방금 다른 분이 이 주소를 사용했어요. `…_2`는 어떠세요?"가 보인다. (08 #3)
5. **Given** 본문이 예약어(`admin`)인 주소 또는 `go-admin`, **When** 가입하면, **Then** 거부된다. (08 #5)
6. **Given** 가입한 회원, **When** 어떤 경로로든 블로그 주소 변경을 시도하면, **Then** 바뀌지 않고 설정 화면에서는 읽기 전용으로 보인다. (08 #4)
7. **Given** `/@Kim755030`, **When** 접속하면, **Then** `/@kim755030`으로 영구 이동(301)한다. (08 #6)
8. **Given** 닉네임 `ㅋㅋ`, `김 민서`, `12345`, `관리자김`, `admin123`, `시1발`, `sh1t`, **When** 가입·변경에 쓰면, **Then** 모두 거부되고, 금칙어 거부 문구는 어떤 단어에 걸렸는지 알려주지 않는다. `시발점`은 허용된다. (09 #1·#4·#5·#7)
9. **Given** 자음·모음이 분리된(NFD) 형태로 붙여넣은 `김민서`, **When** 저장하면, **Then** 정상 닉네임으로 저장된다. (09 #2)
10. **Given** `Kim`이 이미 있음, **When** `kim`을 쓰면, **Then** 중복으로 거부되고, 같은 닉네임을 동시에 요청해도 한 명만 성공한다. (09 #3)

### User Story 4 - 비밀번호를 찾고 바꾼다 (Priority: P2)

이메일 가입 회원은 비밀번호를 잊으면 메일 링크로 재설정하고, 로그인한 상태에서는 현재 비밀번호를 확인한 뒤 바꾼다. 어느 쪽이든 다른 기기의 로그인은 끊긴다. 소셜 계정에는 비밀번호가 없다. (C-AUTH-1, C-AUTH-2)

**Why this priority**: 계정 복구 수단이 없으면 이메일 가입자가 계정을 잃는다. 다만 가입·로그인보다 빈도는 낮다.

**Independent Test**: 가입된·가입되지 않은 이메일로 비밀번호 찾기를 요청해 화면 문구가 같은지 확인하고, 재설정 후 다른 브라우저의 로그인이 끊기는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가입된 이메일과 가입되지 않은 이메일, **When** 각각 비밀번호 찾기를 요청하면, **Then** 화면에는 똑같이 "가입된 이메일이면 안내 메일을 보냈어요"가 보인다. (C-AUTH-1 #7)
2. **Given** 그 이메일로 Google 계정만 있는 사람, **When** 비밀번호 찾기를 요청하면, **Then** 재설정 링크 없이 "이 이메일은 Google로 가입되어 비밀번호가 없어요" 안내 메일만 그 이메일로 간다.
3. **Given** 두 기기에서 로그인한 이메일 가입 회원, **When** 30분 안에 재설정 링크로 새 비밀번호를 저장하면, **Then** 그 계정의 모든 로그인 상태가 끊기고 링크는 다시 쓸 수 없다. (C-AUTH-1 #5·#8)
4. **Given** 로그인한 이메일 가입 회원, **When** 현재 비밀번호를 맞게 입력하고 규칙에 맞는 새 비밀번호로 바꾸면, **Then** 다른 기기는 로그아웃되고 지금 기기는 로그인이 유지되며 "비밀번호가 변경됐어요. 본인이 아니라면 [비밀번호 재설정]" 알림 메일이 간다. (C-AUTH-2 #7)
5. **Given** 소셜 계정 회원, **When** 설정 화면을 열거나 비밀번호 변경을 요청하면, **Then** 버튼이 보이지 않고 요청은 거부된다. (C-AUTH-2 #7)
6. **Given** 로그인한 상태에서 현재 비밀번호를 5회 연속 틀림, **When** 6번째로 시도하면, **Then** 15분 동안 거부된다.

### User Story 5 - 로그인 보안: 실패 제한·정지 계정·약관 재동의 (Priority: P2)

비밀번호 추측, 정지 회원의 계속된 활동, 바뀐 약관에 대한 미동의, 위조한 IP 헤더를 막는다. (C-AUTH-1 #6·#9·#10·#11)

**Why this priority**: 계정 보안과 운영 정책의 집행 수단이다. 가입·로그인 흐름 위에 덧붙는다.

**Independent Test**: 같은 계정으로 5회 틀린 뒤 맞는 비밀번호로 로그인 시도, 정지 처리 후 남은 로그인으로 쓰기 시도, 약관 버전 올린 뒤 로그인을 각각 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 계정으로 5회 연속 로그인 실패, **When** 15분 안에 맞는 비밀번호로 로그인하면, **Then** "잠시 후 다시 시도해 주세요(약 15분)"로 거부된다. (C-AUTH-1 #6)
2. **Given** 틀린 이메일 또는 틀린 비밀번호, **When** 로그인하면, **Then** 어느 쪽이든 "이메일 또는 비밀번호가 올바르지 않아요"만 보인다. (C-AUTH-1 #7)
3. **Given** 정지 기간 중인 계정, **When** 맞는 비밀번호로 로그인하면, **Then** 로그인이 거부되고 "정지된 계정이에요 (~기한). 사유: …"(기한이 없으면 영구)가 보인다. (C-AUTH-1 #10)
4. **Given** 정지 기한이 지난 계정, **When** 로그인하면, **Then** 정지가 자동 해제·기록되고 정상 로그인된다.
5. **Given** 정지되기 전부터 남아 있던 로그인 상태, **When** 쓰기 요청을 보내면, **Then** 계정 상태 거부(403, 정지 계정)로 거부된다. (C-AUTH-1 #10, H7)
6. **Given** 이용약관 버전이 바뀐 뒤, **When** 예전 버전에 동의한 회원이 로그인하면, **Then** 재동의 화면으로 가고 동의하기 전에는 다른 화면으로 넘어가지 않는다. (C-AUTH-1 #11)
7. **Given** 신뢰 프록시가 아닌 곳에서 IP 전달 헤더를 위조한 요청, **When** IP 기준 제한(로그인 1분 20회 등)을 넘기려 하면, **Then** 위조 헤더는 무시되어 제한을 우회할 수 없다. (C-AUTH-1 #9)
8. **Given** 로그인 후 이동할 주소로 외부 사이트 주소가 주어짐, **When** 로그인에 성공하면, **Then** 외부 사이트로 이동하지 않는다(사이트 안 상대 경로만 허용).

### User Story 6 - 프로필과 계정 설정을 고친다 (Priority: P2)

회원은 설정 화면에서 닉네임·소개·프로필 사진을 한 번에 저장하고, 새 글 기본 공개 범위와 최근 활동 공개 여부를 바꾼다. 블로그 주소와 이메일은 바꿀 수 없다. (C-AUTH-2)

**Why this priority**: 블로그 정체성을 꾸미는 기능이지만, 가입 직후 기본값으로도 서비스를 쓸 수 있다.

**Independent Test**: 닉네임·소개·사진을 함께 저장해 반영을 확인하고, 그중 하나를 규칙 위반으로 보내 아무것도 바뀌지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 회원, **When** 닉네임·소개·사진을 바꿔 [저장]하면, **Then** 모두 반영되고 목록·글 상세·댓글의 작성자 표시에도 바로 반영된다.
2. **Given** 올바른 닉네임과 201자 소개, **When** 함께 저장하면, **Then** 어떤 값도 바뀌지 않고 "소개는 200자까지 쓸 수 있어요"를 포함해 실패한 칸이 모두 표시된다. (C-AUTH-2 #2)
3. **Given** `<script>`가 든 소개, **When** 저장 후 블로그 상단에서 보면, **Then** 실행되지 않고 글자로 보인다. (C-AUTH-2 #3)
4. **Given** 닉네임을 바꾼 지 30일이 안 됨, **When** 설정 화면을 열면, **Then** 닉네임 칸은 비활성화되고 "다음 변경 가능일"이 보이며, 닉네임 변경을 강제로 보내면 거부(409)되고 같은 요청의 다른 칸도 저장되지 않는다. (09 #6)
5. **Given** 남이 올린 사진·글용 사진·256×256이 아닌 사진, **When** 프로필 사진으로 연결하려 하면, **Then** 연결되지 않는다. (C-AUTH-2 #4)
6. **Given** 프로필 사진을 새 사진으로 바꿈, **When** 7일이 지나면, **Then** 이전 사진은 지워지고 현재 사진은 정리 작업이 지우지 않는다. (C-AUTH-2 #5)
7. **Given** 다른 회원 ID를 요청에 넣어 프로필 수정을 시도, **When** 저장하면, **Then** 그 값은 무시되고 로그인한 본인 프로필만 대상이 된다. (C-AUTH-2 #1, C-OWN-1)

### User Story 7 - 친구를 맺는다 (Priority: P3)

회원은 다른 회원의 블로그에서 친구 요청을 보내고, 받은 사람이 수락하면 서로 친구가 된다. 거절·취소·끊기는 상대에게 알리지 않는다. (C-FRIEND-1)

**Why this priority**: 공통 Tier A지만, 친구 관계의 공통 용도는 최근 활동 표시(User Story 8)이고 친구 공개 범위는 선택 구현이다.

**Independent Test**: 회원 두 명으로 요청 → 수락 → 친구 목록 확인 → 끊기를 확인한다.

**Acceptance Scenarios**:

1. **Given** 친구가 아닌 A와 B, **When** A가 B의 블로그에서 [친구 요청]을 누르고 B가 받은 요청 목록에서 [수락]하면, **Then** 두 사람은 서로 친구가 된다.
2. **Given** A가 B에게 요청 중, **When** B가 A에게 친구 요청을 보내면, **Then** 별도 요청이 생기지 않고 바로 수락되어 친구가 된다.
3. **Given** A와 B가 동시에 서로 요청, **When** 둘 다 처리되면, **Then** 두 사람 사이의 관계는 하나뿐이다.
4. **Given** B가 A의 요청을 거절, **When** A가 확인하면, **Then** A는 거절 사실을 알림 등으로 받지 않는다.
5. **Given** 회원 A, **When** 자기 자신에게 친구 요청하면, **Then** 거부된다.
6. **Given** A의 친구 목록, **When** 다른 회원이 보려 하면, **Then** 볼 수 없다(본인만).

### User Story 8 - 직전 로그인과 친구의 최근 활동을 본다 (Priority: P3)

회원은 계정 화면에서 이번 로그인 바로 전의 로그인 일자·방식을 보고 계정 도용을 알아챈다. 친구끼리는 서로의 최근 활동을 "오늘·어제·N일 전·1주 이상"으로만 본다. (C-ACT-1)

**Why this priority**: 2026-10-07 회의에서 공통으로 추가된 보조 기능이며, 친구 맺기(User Story 7)에 의존한다.

**Independent Test**: 두 번 로그인한 뒤 계정 화면의 표시를 확인하고, 친구·비친구·요청 중 회원으로 같은 회원의 최근 활동 노출을 비교한다.

**Acceptance Scenarios**:

1. **Given** 10월 6일에 로그인한 적이 있는 회원, **When** 10월 7일에 다시 로그인해 계정 화면을 보면, **Then** "직전 로그인: 2026.10.06 …, 로그인 방식"이 보인다(방금 한 로그인이 아님). (C-AUTH-2 #8)
2. **Given** 처음 로그인한 회원, **When** 계정 화면을 보면, **Then** "첫 로그인"이 보인다.
3. **Given** A와 B가 친구(수락)이고 둘 다 공개 켬, **When** A가 B의 블로그·프로필을 보면, **Then** B의 최근 활동이 "오늘/어제/N일 전(2~6일)/1주 이상" 중 하나로 보이고 정확한 시각은 보이지 않는다.
4. **Given** 비회원, 친구가 아닌 회원, 요청 중(수락 전)인 회원, **When** B의 최근 활동을 조회하면, **Then** 화면과 응답 어디에도 최근 활동 값이 없다.
5. **Given** A가 최근 활동 공개를 끔, **When** A가 친구 B의 최근 활동을 보면, **Then** A에게도 B의 것이 보이지 않고, B에게도 A의 것이 보이지 않는다. (C-AUTH-2 #9, 06 #9)
6. **Given** A와 B가 친구를 끊음, **When** 서로의 블로그를 보면, **Then** 그 순간부터 최근 활동이 보이지 않는다.

### Edge Cases

- 인증 메일 재발송 하루 10번을 넘기면? → 그날은 더 보낼 수 없다. 새 메일이 나가면 이전 링크는 무효다.
- 이메일 가입 시 블로그 주소 미리 채우기 결과가 3자 미만(`ab@…`, 영문이 없는 이메일)이면? → `user_` + 6자리 난수로 채운다(소셜은 접두어 포함, 예: `go-user_483920`).
- 블로그 주소가 예약어이거나 이미 있으면? → `_2`, `_3` … 중 비어 있는 첫 번호를 붙여 미리 채운다.
- 소셜 이름이 닉네임 규칙에 안 맞거나(`A`), 이미 쓰이는 닉네임이면? → 닉네임 칸을 빈칸으로 두고 "닉네임을 입력해 주세요".
- GitHub에 인증된 대표 이메일이 없으면? → 마무리 화면에서 이메일을 받아 이메일 가입과 같은 방식으로 인증한다.
- 같은 닉네임으로 다시 저장하면? → 아무것도 바뀌지 않고 30일 제한도 시작되지 않는다. 대소문자만 바꾸면(`kim` → `Kim`) 변경으로 보며 자기 자신은 중복 검사에서 제외한다.
- 가입 직후 닉네임을 바꾸면? → 가입 때 정한 닉네임은 변경으로 세지 않으므로 바로 한 번 바꿀 수 있다.
- 로그인 정보를 보관하는 저장소에 장애가 나면? → 로그인 정보를 읽지 못한 요청은 비로그인으로 처리해 글 읽기는 계속되고 로그인이 필요한 요청은 401, 새 로그인과 인증·재설정 링크 확인은 "잠시 후 다시 시도해 주세요"로 거부, 실패 횟수·재발송 제한은 장애 동안 적용되지 않고, 최근 활동 갱신은 건너뛴다. (H8)
- 정지 회원이 비밀번호를 잊었다면? → 비밀번호 재설정(로그인 전 기능)은 할 수 있다. 정지 기간에는 프로필 수정·비밀번호 변경·탈퇴는 할 수 없다. (42 §9)
- 탈퇴 유예 중인 회원이 로그인하거나 같은 이메일로 다시 가입하려 하면? → 복구 화면·복구 안내로 처리한다 (→ specs/015-withdraw).
- 소셜 사진 서버에 사진이 없으면? → Google·GitHub가 주는 기본 사진(이름 첫 글자·기본 무늬)을 그대로 가져온다. 체크를 끄면 우리 기본 이미지다.
- 프로필 사진만 올리고 [저장]을 누르지 않으면? → 연결되지 않고 24시간 뒤 정리된다.
- 최근 활동 값이 아직 없으면(활동 기록 전)? → 표시하지 않는다.
- 친구 요청 중(PENDING)인 상대는? → 친구가 아니므로 최근 활동을 볼 수 없다.

## Requirements *(mandatory)*

### Functional Requirements

**계정과 로그인 수단**

- **FR-001**: System MUST 이메일 가입·로그인, Google 로그인, GitHub 로그인 세 가지 로그인 수단을 제공해야 한다. 네이버 등 다른 수단은 이번 범위에서 제외한다. (C-AUTH-1, L-5)
- **FR-002**: System MUST 계정 하나에 로그인 수단 하나만 두고, 같은 로그인 수단(같은 이메일 가입, 같은 소셜 계정)으로는 동시에 요청해도 계정이 두 개 생기지 않게 해야 한다. 이메일이 같아도 로그인 수단이 다르면 별도 계정이며, 자동 합치기·계정 연결 기능은 두지 않는다. (C-AUTH-1 #1, L-1)
- **FR-003**: System MUST 이메일 가입 계정은 소문자로 바꾸고 앞뒤 공백을 지운 이메일로, 소셜 계정은 소셜 서비스의 고유 사용자 ID로 식별해야 한다. 소셜 쪽 이메일이나 로그인 이름이 바뀌어도 같은 계정으로 로그인된다. (07 §2·§5)

**이메일 가입과 인증**

- **FR-004**: 이메일 가입은 이메일(일반 형식, 최대 254자)·블로그 주소·비밀번호·비밀번호 확인·닉네임·필수 동의 2개(이용약관, 개인정보 처리방침)를 받아야 한다. 이미 이메일 가입된 주소면 "이미 가입된 이메일이에요. [로그인] [비밀번호 찾기]"를 보여야 한다. (07 §3)
- **FR-005**: System MUST 이메일 가입 직후 계정을 인증 전 상태로 만들고, 24시간 유효·한 번만 쓸 수 있는 인증 링크를 메일로 보내야 한다. 링크를 열면 인증이 기록되고 "인증이 완료됐어요", 만료·사용된 링크면 "링크가 만료됐어요. [인증 메일 다시 보내기]"를 보여야 한다. (L-2, C-AUTH-1 #8)
- **FR-006**: System MUST 인증 메일 재발송을 회원당 1분에 1번, 하루 10번으로 제한하고, 새 메일을 보내면 이전 링크를 무효로 해야 한다. (L-10)
- **FR-007**: System MUST 인증 전 회원의 글쓰기(새 글·저장·발행·공개 범위 변경 포함)·댓글·사진 업로드·좋아요·신고 요청을 계정 상태 거부(403, 이메일 미인증)와 "인증 메일 다시 보내기" 안내로 거부해야 한다. 인증 전 회원도 로그인, 닉네임·소개 수정, 비밀번호 변경, 새 글 기본 공개 범위 변경, 탈퇴, 자기 글·댓글 삭제·복구는 할 수 있다. (C-AUTH-1 #3, L-2, 42 P-6·§5-2·§9)
- **FR-008**: System MUST 소셜 가입 계정을 가입 시각에 인증된 것으로 처리해야 한다. Google은 인증된 이메일만 받고, GitHub은 인증된 대표 이메일을 받으며 없으면 가입 마무리 화면에서 이메일을 입력받아 FR-005와 같은 방식으로 인증한다. (07 §5)
- **FR-009**: 운영 환경의 인증·재설정·알림 메일은 [NEEDS CLARIFICATION: 배포 환경의 메일 발송 수단 미정 — 07 L-9 "개발은 로컬 메일 확인 도구, 배포 방식은 환경 확인 후 결정". 발송 수단에 따라 메일 도달·발송 한도가 달라진다]으로 발송해야 한다.

**약관·처리방침 동의**

- **FR-010**: System MUST 이메일 가입과 소셜 가입 마무리 모두에서 이용약관·개인정보 처리방침 동의를 필수로 받고, 계정 생성과 같은 처리 안에서 동의 종류·동의한 버전·시각을 기록해야 한다. 동의 기록 없이 계정이 생기면 안 된다. (L-8, 07 §3-1)
- **FR-011**: 이용약관·개인정보 처리방침 화면은 각각 시행일과 버전을 표시하고 가입 화면·소셜 가입 마무리 화면·설정 화면에서 열 수 있어야 한다. 개인정보 처리방침에는 "친구에게 최근 활동 시점 표시"를 명시해야 한다. (07 §3-1, H9)
- **FR-012**: System MUST 로그인할 때 회원이 동의한 이용약관·처리방침 버전이 현재 버전과 다르면 재동의 화면으로 보내고, 동의하기 전에는 다른 화면으로 넘어가지 못하게 해야 한다. 재동의하면 버전·시각을 갱신한다. (C-AUTH-1 #11, H9)

**비밀번호**

- **FR-013**: System MUST 가입·재설정·변경 때 비밀번호를 8~16자, 영문 대소문자 1개 이상·숫자 1개 이상·특수문자 1개 이상으로 검사해야 한다. 쓸 수 있는 문자는 영문·숫자·지정 특수문자(`` ! @ # $ % ^ & * ( ) - _ = + [ ] { } ; : ' " , . < > / ? \ | ` ~ ``)뿐이며(공백·한글 불가), 이메일 `@` 앞부분이 들어간 비밀번호와 흔한 비밀번호 목록(`Password1!`, `Qwer1234!` 등)은 거부한다. 안내 문구에 "최대 16자"를 분명히 적는다. (L-3, 07 §4, C-AUTH-1 #4)
- **FR-014**: 비밀번호 입력 화면은 입력하는 동안 규칙별 충족 여부를 글자와 ✓로 표시해야 한다(색만으로 표시하지 않음). (07 §4)
- **FR-015**: System MUST 비밀번호 원문을 저장하거나 로그에 남기지 않아야 하며, 인증·재설정 링크 값도 로그에 남기지 않아야 한다. (07 §4·§6)

**블로그 주소 (08)**

- **FR-016**: 블로그 주소는 `[접두어-]본문` 형식이어야 한다. 접두어는 이메일 가입은 없음, Google은 `go-`, GitHub은 `gi-`이고 가입 수단과 일치해야 한다. 본문은 영문 소문자·숫자·`_` 3~36자이며 처음과 끝은 영문 소문자나 숫자다(전체 최대 39자). (08 §2, H-1·H-2·H-3)
- **FR-017**: System MUST 이메일로 블로그 주소를 미리 채울 때 다음 순서를 따라야 한다: ① `@` 앞부분 ② `+` 뒤 버림 ③ 소문자 ④ `.`·`-`를 `_`로 ⑤ 영문 소문자·숫자·`_` 외 문자 제거 ⑥ 연속 `_`는 하나로, 처음·끝 `_` 제거 ⑦ 30자로 자름(끝이 `_`면 제거) ⑧ 3자 미만이면 `user_` + 6자리 난수 ⑨ 가입 수단 접두어 ⑩ 예약어이거나 이미 있으면 `_2`, `_3` … 중 비어 있는 첫 번호. (08 §3, H-5)
- **FR-018**: 가입자는 미리 채워진 주소를 가입할 때 한 번 직접 고칠 수 있어야 한다. 이메일 가입 화면은 이메일 입력에 따라 주소를 자동으로 채우되 사용자가 주소 칸을 직접 고치면 이후 자동으로 바꾸지 않는다. 소셜 가입 마무리 화면은 접두어를 고칠 수 없는 고정 글자로 보이고 본문만 고치게 한다. 대문자 입력은 소문자로 바꿔 보이고, 한글 자판 상태여도 영문으로 입력되며, `-`는 입력할 수 없다. "이메일 앞부분으로 미리 채웠어요. 이메일을 드러내고 싶지 않으면 바꿔 주세요."와 "블로그 주소는 가입 후 바꿀 수 없어요" 안내를 보인다. (H-4, 08 §4)
- **FR-019**: System MUST 접두어를 뺀 본문이 예약어 목록(`admin administrator root system official support help about terms privacy api login logout signup settings me write search tag tags notifications manage static assets images mail www blog user users null undefined devlog teamblog` + [NEEDS CLARIFICATION: 서비스 이름 미확정 — 08 §5·09 §5 "서비스 이름이 확정되면 추가". 확정 전까지 어떤 이름을 예약어로 막을지])와 같거나, 닉네임과 같은 금칙어 필터(FR-025)에 걸리는 주소를 거부해야 한다. (08 §4-2·§5)
- **FR-020**: 주소 입력이 0.5초 멈추면 사용 가능 여부를 확인해 보여야 한다. 이 확인은 사용 중 여부·거부 이유·대안 주소만 알려주고, 같은 IP에서 1분에 30번으로 제한된다. 최종 판정은 가입 요청 때 System이 다시 한다. 같은 주소로 동시에 가입하면 한 명만 성공하고, 늦은 쪽에는 "방금 다른 분이 이 주소를 사용했어요. `{대안}`는 어떠세요?"를 보인다. (08 §4-2, 08 #3)
- **FR-021**: System MUST 가입 후 블로그 주소를 어떤 경로로도 바꿀 수 없게 하고(설정 화면에서는 읽기 전용), 대문자가 섞인 주소 접속은 소문자 주소로 영구 리다이렉트(301), 없는 주소는 404로 응답해야 한다. 탈퇴한 계정의 주소는 다시 쓸 수 없다(→ specs/015-withdraw). 화면에는 `@주소`로 표시한다. (C-AUTH-2, 08 §6, 08 #4·#6)

**닉네임 (09)**

- **FR-022**: System MUST 닉네임을 검사하기 전에 앞뒤 공백을 지우고 유니코드 NFC로 정규화하며, 정규화한 값을 저장해야 한다. 형식은 완성형 한글(`가`~`힣`)·영문·숫자 2~10자이고 한글이나 영문이 1자 이상 있어야 한다. 자음·모음만, 공백, 특수문자, 이모지, 숫자만으로 된 닉네임은 거부한다. (09 §2, N-1·N-2·N-3, 09 #1·#2)
- **FR-023**: System MUST 닉네임을 정리 → 형식 → 글자 포함 → 예약어 → 금칙어 → 중복 순서로 검사하고, 단계별로 "한글·영문·숫자로 2~10자까지 쓸 수 있어요 (공백·특수문자 불가)" / "한글이나 영문을 1자 이상 넣어 주세요" / "사용할 수 없는 닉네임이에요" / "사용할 수 없는 단어가 들어 있어요" / "이미 사용 중인 닉네임이에요"를 돌려줘야 한다. 가입(이메일·소셜)과 프로필 수정은 같은 검사를 쓰고, 화면 검사는 안내용이며 System이 요청을 받을 때 다시 검사한다. (09 §3)
- **FR-024**: System MUST 예약어(`관리자 운영자 운영진 운영팀 고객센터 공식 매니저 스태프 admin administrator official staff manager system root`, 서비스 이름은 FR-019와 같이 미정)가 대소문자 무시·금칙어와 같은 변형 4가지 기준으로 **포함만 되어도** 닉네임을 거부해야 한다. (N-6, 09 §5, 09 #5)
- **FR-025**: System MUST 금칙어 검사에서 입력을 소문자로 바꾼 뒤 ① 그대로 ② 숫자 제거 ③ 숫자→영문 치환(0→o, 1→i, 3→e, 4→a, 5→s, 7→t) ④ 1→l 네 가지 변형 중 하나라도 금칙어를 포함하면 거부하고, 각 변형에서 예외 단어(`시발점`, `시발역` 등)는 먼저 지워야 한다. 거부 문구는 어떤 단어에 걸렸는지 알려주지 않는다. 같은 필터를 블로그 주소와 소개에도 적용한다(소개는 예약어 검사 제외). (N-5, 09 §4, R-3, 09 #4·#7)
- **FR-026**: System MUST 닉네임 중복을 대소문자 무시로 판정하고(`Kim` = `kim`, 화면에는 입력한 대로 표시), 같은 닉네임을 동시에 요청해도 한 명만 성공시켜야 하며, 진 쪽에는 "방금 다른 분이 이 닉네임을 사용했어요"를 보여야 한다. 사용 가능 확인은 입력이 0.5초 멈추면 하고 같은 IP에서 1분에 30번으로 제한한다. (N-4, 09 §6, 09 #3)
- **FR-027**: 이메일 가입은 닉네임을 직접 입력받아야 한다. 소셜 가입 마무리 화면은 소셜 이름에서 허용되지 않는 문자를 지우고 10자로 잘라 미리 채우되, 결과가 FR-023 검사를 통과하지 못하면 빈칸으로 두고 "닉네임을 입력해 주세요"를 보인다. (N-10, 09 §7)
- **FR-028**: System MUST 닉네임 변경을 본인만 하게 하고, 바꾼 뒤 30일 동안 다시 바꿀 수 없게 해야 한다(화면에 "다음 변경 가능일" 표시·입력칸 비활성화, 요청은 상태 충돌(409)로 거부). 가입 때 정한 닉네임은 변경으로 세지 않고, 같은 닉네임으로 다시 저장하면 아무것도 바뀌지 않으며 제한도 시작되지 않는다. 대소문자만 바꾸는 것은 변경으로 보고 중복 검사에서 자기 자신은 제외한다. 이전 닉네임은 즉시 다른 사람이 쓸 수 있다. (N-7·N-8, 09 §8, 09 #6)
- **FR-029**: 닉네임은 글 카드에서는 닉네임만, 글 상세 작성자 영역·댓글·블로그 상단에서는 `닉네임 @블로그주소`로 표시해야 한다. 탈퇴한 사람의 표시는 → specs/015-withdraw. (N-9, 09 §9)

**소셜 로그인**

- **FR-030**: System MUST 소셜 로그인 요청과 돌아온 응답이 같은 로그인 흐름인지 확인하고, 연결된 계정이 있으면 로그인시키고, 처음이면 가입 마무리 화면(닉네임·블로그 주소·약관 동의)을 반드시 거치게 해야 한다. 마무리 전에는 계정을 만들지 않고 소셜 인증 정보는 10분만 보관한다. (07 §5)
- **FR-031**: 소셜 가입 마무리 화면의 "프로필 사진 사용"(기본 체크)이 켜져 있으면, 계정 생성 직후 브라우저가 소셜 사진을 5초 제한으로 받아 가운데를 정사각형으로 잘라 256×256으로 바꾸고 서비스 저장소에 복사해 프로필 사진으로 연결해야 한다. System은 Google·GitHub 사진 서버 두 곳의 HTTPS 주소만 화면에 넘기고, 외부 사진 주소를 직접 요청하거나 저장하지 않는다. 실패하면 가입은 그대로 성공하고 기본 이미지와 "소셜 사진을 가져오지 못했어요. 설정에서 직접 올릴 수 있어요"를 보인다. 복사는 가입 때 한 번뿐이다. (R-6, 11 §4-2, C-AUTH-2 #6)
- **FR-032**: System MUST 소셜 사진 서버를 불러오는 것을 소셜 가입 마무리 화면에서만 허용해야 하며, 이 화면은 소셜 로그인 복귀 때 전체 페이지로 열고 가입을 마치면 전체 페이지 이동으로 나가야 한다. 다른 화면은 외부 사진 서버를 불러올 수 없다. (H3, 2026-10-07 "소셜 가입 마무리 화면")
- **FR-033**: 소셜로 처음 로그인했을 때 같은 이메일로 다른 로그인 수단의 계정이 이미 있으면 [NEEDS CLARIFICATION: 07 §10 F-1 미결 — 가입 마무리 화면에 "이 이메일로 이메일 가입한 계정이 이미 있어요. [기존 계정으로 로그인] [새 계정 만들기]" 안내를 보일지, 안내 없이 바로 새 계정 마무리로 갈지].

**로그인 유지와 보안**

- **FR-034**: System MUST 로그인 상태를 마지막 활동 시점부터 14일 유지하고, 로그인할 때마다 로그인 식별값을 새로 발급하며, 상태를 바꾸는 모든 요청에 요청 위조 방지 확인을 적용해야 한다. 여러 서버로 늘려도 로그인은 유지된다. (L-6, 07 §6)
- **FR-035**: System MUST 같은 계정의 연속 5회 로그인 실패 시 15분 동안 그 계정의 로그인을 막고("잠시 후 다시 시도해 주세요(약 15분)"), 같은 IP의 로그인 시도를 1분에 20회로 제한해야 한다. (L-7, C-AUTH-1 #6)
- **FR-036**: System MUST 로그인 실패 시 "이메일 또는 비밀번호가 올바르지 않아요"만 보이고, 어느 쪽이 틀렸는지나 가입 여부를 알려주지 않아야 한다. (07 §6, C-AUTH-1 #7)
- **FR-037**: System MUST 사용자 IP를 신뢰 프록시(로드 밸런서) 내부 대역에서 온 요청에 한해서만 전달 헤더의 가장 오른쪽 신뢰 밖 주소로 정하고, 그 밖의 출처가 보낸 전달 헤더는 무시해야 한다. HTTPS 여부 판단도 같은 신뢰 규칙을 따른다. 이 문서의 모든 "같은 IP" 제한은 이 값을 쓴다. (H4, C-AUTH-1 #9)
- **FR-038**: System MUST 정지 상태 계정의 로그인을 비밀번호가 맞아도 거부하고 "정지된 계정이에요 (~기한). 사유: …"(기한이 없으면 영구)를 보여야 한다. 열린 정지의 종료 시각이 지났으면 해제를 기록하고 정상 상태로 바꾼 뒤 로그인시킨다. 정지되는 순간 그 회원의 모든 로그인 상태를 끊고, 그래도 남은 로그인 상태의 쓰기 요청은 계정 상태 거부(403, 정지 계정)로 거부한다. 정지를 거는 기능은 → specs/014-report-hide. (07 §6, 42 P-7, H7, C-AUTH-1 #10)
- **FR-039**: System MUST 로그인 후 원래 보던 페이지로 보내되 사이트 안의 상대 경로만 허용해야 한다. 로그인이 필요한 요청을 비로그인 상태로 보내면 401로 거부하고 화면은 로그인 화면으로 안내한다. (07 §6, 42 §3 ①)
- **FR-040**: System MUST 로그인 정보 저장소에 장애가 나면 로그인 정보를 읽지 못한 요청을 비로그인으로 처리해 글 읽기를 계속하고(로그인이 필요한 요청은 401), 새 로그인과 인증·재설정 링크 확인은 "잠시 후 다시 시도해 주세요"로 거부하며, 실패 횟수·재발송·요청 횟수 제한은 통과시키고, 최근 활동 갱신은 건너뛰어야 한다. (H8, 07 §6, 02 §2-1)

**로그아웃**

- **FR-041**: System MUST 로그아웃 때 서버의 로그인 상태를 삭제하고, 그 사용자의 브라우저 임시 글 데이터·백업을 전부 지우고(→ specs/002-post-authoring), 홈으로 이동시켜야 한다. 테마 설정은 지우지 않는다(→ specs/016-dark-mode). 비밀번호 재설정 때는 모든 기기 로그아웃이 자동으로 실행된다. (07 §7, C-AUTH-1 #2)

**비밀번호 재설정·변경**

- **FR-042**: System MUST 비밀번호 찾기 요청에 화면으로는 항상 "가입된 이메일이면 안내 메일을 보냈어요"만 보이고, 메일은 그 이메일 주인에게만 보내야 한다. 메일 내용: 이메일 가입 계정이 있으면 30분 유효·한 번만 쓸 수 있는 재설정 링크, 같은 이메일의 Google·GitHub 계정도 있으면 "그 계정은 Google로 로그인하세요" 같은 안내 추가, 소셜 계정만 있으면 "이 이메일은 Google로 가입되어 비밀번호가 없어요" 안내만. (L-4, 07 §4-1, C-AUTH-1 #7·#8)
- **FR-043**: System MUST 비밀번호 찾기 요청을 같은 이메일 1분 1번·하루 10번, 같은 IP 1시간 20번으로 제한해야 한다. (07 §4-1)
- **FR-044**: System MUST 재설정으로 새 비밀번호를 저장하면 그 계정의 모든 로그인 상태를 끊어야 한다. 정지 회원과 탈퇴 유예 회원도 재설정할 수 있다. (C-AUTH-1 #5, 42 §9, 13 §3-2)
- **FR-045**: 이메일 가입 회원은 로그인한 상태에서 현재 비밀번호를 확인한 뒤 비밀번호를 바꿀 수 있어야 한다. 새 비밀번호는 FR-013 규칙을 따르고 현재와 같으면 거부한다. 현재 비밀번호를 5회 연속 틀리면 15분 잠근다. 바꾸면 다른 기기의 로그인은 모두 끊고 지금 기기는 유지(식별값 새로 발급)하며 "비밀번호가 변경됐어요. 본인이 아니라면 [비밀번호 재설정]" 알림 메일을 보낸다. 소셜 계정에는 버튼을 보이지 않고 요청도 거부한다. (R-10, 11 §6-2, C-AUTH-2 #7)

**프로필·계정 설정 (11)**

- **FR-046**: 설정 화면은 로그인한 사람만 열 수 있어야 하며(비회원은 로그인 화면으로), 프로필(사진, 닉네임, 소개, 블로그 주소 읽기 전용)·계정(이메일 읽기 전용, 로그인 수단, 직전 로그인, 비밀번호 변경(이메일 가입만), 새 글 기본 공개 범위, 최근 활동 공개, 약관·처리방침 보기)·회원 탈퇴(→ specs/015-withdraw) 영역을 가져야 한다. (11 §2)
- **FR-047**: System MUST 프로필·설정 수정 대상을 로그인한 본인으로만 정하고, 요청에 담긴 다른 회원 식별값은 무시해야 한다. 이메일은 바꿀 수 없다. (C-AUTH-2 #1, C-OWN-1, R-9, 11 §5)
- **FR-048**: System MUST 소개를 0~200자 글자로만 받아야 한다: HTML·Markdown으로 해석하지 않고 화면에 글자 그대로(이스케이프) 표시, 줄바꿈 최대 4줄, 연속 빈 줄은 하나로, 이모지 허용, 주소 자동 링크 없음, 앞뒤 공백 제거·NFC 정규화, 금칙어 필터 적용. 실패 문구는 "소개는 200자까지 쓸 수 있어요" / "소개는 4줄까지 쓸 수 있어요" / "사용할 수 없는 단어가 들어 있어요". (R-1·R-2·R-3, 11 §3, C-AUTH-2 #3)
- **FR-049**: 회원은 jpg·png·gif·webp 10MB 이하 파일을 골라 브라우저에서 정사각형으로 자르고(위치 조정·확대·축소) 256×256 사진(위치 정보 등 메타데이터 제거, GIF는 첫 장면)으로 올린 뒤 [저장]을 눌러 프로필 사진으로 연결할 수 있어야 한다. System은 형식·실제 내용·정확히 256×256·1MB 이하를 다시 검사하고, 본인이 올린 프로필 용도의 삭제되지 않은 사진만 연결한다(아니면 400으로 거부). 인증 전 회원은 사진을 올릴 수 없다. 업로드 절차·요청 제한은 → specs/003-image-upload. (R-4, 11 §4-1·§5, C-AUTH-2 #4)
- **FR-050**: System MUST 회원당 연결된 프로필 사진을 하나로 유지하고, 사진을 바꾸거나 [기본 이미지로]를 누르면 이전 사진의 연결을 끊어 7일 뒤 지워지게 하며, 연결된 프로필 사진은 정리 작업이 지우지 않게 해야 한다. 같은 회원의 동시 저장은 차례로 처리한다. 올리기만 하고 저장하지 않은 사진은 24시간 뒤 정리된다. (R-7, 11 §4-4, C-AUTH-2 #5)
- **FR-051**: 프로필 사진이 없으면 닉네임 첫 글자(영문은 대문자)가 든 원형 아이콘을 보여야 한다. 배경색은 블로그 주소로 정한 8가지 색 중 하나로 사람마다 항상 같고, 라이트·다크 모두 글자와 명도 대비 4.5:1 이상이며, 파일로 저장하지 않고 화면에서 그린다. (R-5, 11 §4-3)
- **FR-052**: System MUST 프로필 변경을 [저장] 한 번으로 반영하고(바꾸려는 칸만 전송), 닉네임·소개·사진 중 하나라도 검사에 실패하면 아무것도 저장하지 않고 실패한 칸을 모두 돌려줘야 한다. 닉네임 30일 제한 중에도 닉네임 변경이 없는 요청의 다른 칸은 저장되지만, 같은 요청에 닉네임 변경이 있으면 전체가 실패한다. 동시 수정은 나중에 저장한 쪽이 반영되고, 저장 즉시 목록·글 상세·댓글의 작성자 표시에 반영된다. (R-8, 11 §5, C-AUTH-2 #2)
- **FR-053**: 회원은 설정에서 새 글 기본 공개 범위를 전체 공개 / 나만 보기(친구 공개 규격 적용자는 친구 공개 추가) 중에서 본인만 바꿀 수 있어야 하며, 기본값은 전체 공개다. 새 글에 적용하는 규칙은 → specs/002-post-authoring, 공개 범위 규칙은 → specs/004-visibility-permission. (V-4, 11 §6-3)

**친구 맺기 (C-FRIEND-1)**

- **FR-054**: 회원은 다른 회원의 블로그에서 [친구 요청]을 보낼 수 있어야 한다. 자기 자신에게는 보낼 수 없고, 이미 친구거나 요청 중이면 아무것도 바뀌지 않으며, 상대가 이미 나에게 보낸 요청이 있으면 바로 수락된다. 두 회원 사이의 관계는 동시에 서로 요청해도 하나만 생긴다. (V-2, 06 §6-1·§6-2)
- **FR-055**: 회원은 설정의 "받은 친구 요청" 목록에서 [수락] / [거절]할 수 있어야 한다. 거절·요청 취소·친구 끊기는 관계를 지우고 상대에게 알리지 않는다. (06 §6-2)
- **FR-056**: System MUST 친구 목록을 본인에게만 보여야 한다. 친구를 끊으면 그 순간부터 서로의 최근 활동이 보이지 않는다. 친구 공개 글 접근은 → specs/004-visibility-permission, 친구 알림(선택 기능, 기본 비활성)은 → specs/011-notification, 탈퇴 시 친구 관계 삭제는 → specs/015-withdraw. (06 §6-2, M1)

**직전 로그인·최근 활동 (C-ACT-1)**

- **FR-057**: System MUST 로그인에 성공할 때마다 그 계정의 마지막 로그인 일자를 갱신하되, 갱신하기 전 값과 로그인 방식을 그 로그인 상태에 담아 두어야 한다. (07 §6, 2026-10-07 "마지막 로그인 일자"·"직전 로그인 표시")
- **FR-058**: 계정 화면은 본인에게만 "직전 로그인: 일자, 로그인 방식"(이번 로그인 바로 전 로그인)을 보여야 하며, 이전 로그인이 없으면 "첫 로그인"으로 표시한다. (R-11, 11 §6-4, C-AUTH-2 #8)
- **FR-059**: System MUST 로그인한 요청이 오면 회원의 최근 활동 일자를 한 시간에 한 번 정도만 갱신해야 한다. (07 §6, 06 §6-4)
- **FR-060**: System MUST 최근 활동을 보는 사람과 대상이 수락된 친구이고, 두 사람 모두 최근 활동 공개를 켰고, 대상의 최근 활동 값이 있을 때만 "오늘" / "어제" / "N일 전"(2~6일) / "1주 이상" 중 하나로 보여야 한다. 정확한 시각은 보이지 않으며, 그 밖의 경우(비회원·친구 아님·요청 중·한쪽이라도 끔·값 없음)에는 화면과 응답 어디에도 넣지 않는다. (R-12, 06 §6-4, C-AUTH-2 #9, 06 #9)
- **FR-061**: 회원은 설정의 "최근 활동을 친구에게 보이기"(기본 켬)를 끌 수 있어야 하며, 끄면 친구에게 내 최근 활동이 보이지 않고 나도 친구의 최근 활동을 볼 수 없다. 탈퇴 익명 처리 때 최근 활동 값은 비워진다(→ specs/015-withdraw). (R-12, 11 §6-4)

### Key Entities *(include if feature involves data)*

- **회원(Member)**: 블로그 주인이자 계정. 블로그 주소(변경 불가·재사용 불가), 닉네임·닉네임 변경 일자, 소개, 권한(일반·관리자), 회원 상태(정상·정지·탈퇴 유예), 새 글 기본 공개 범위, 최근 활동 일자·최근 활동 공개 여부, 가입·탈퇴 신청·익명 처리 일자. 프로필 사진은 회원이 직접 가리키지 않고 "그 회원이 올린 프로필 용도의 연결된 사진 하나"로 판별한다.
- **로그인 수단(Auth Identity)**: 회원당 정확히 하나. 로그인 방식(이메일·Google·GitHub), 방식 안에서 유일한 식별값(이메일 가입은 소문자 이메일, 소셜은 고유 ID), 이메일, 비밀번호 해시(이메일 가입만), 이메일 인증 일자, 마지막 로그인 일자.
- **회원 동의(Member Agreement)**: 회원·동의 종류(이용약관·개인정보 처리방침·AI)마다 하나. 동의한 버전과 일자. 재동의 때 갱신되고 탈퇴 익명 처리 뒤에도 남는다. (AI 동의는 → specs/013-ai-tag-suggest)
- **회원 정지 이력(Member Suspension)**: 이 기능은 읽기만 한다. 사유, 시작·종료(없으면 영구)·해제 일자. 로그인 때 만료된 열린 정지를 해제한다. (생성은 → specs/014-report-hide)
- **친구 관계(Friendship)**: 두 회원 쌍마다 하나. 요청한 회원, 상태(요청 중·친구), 요청·수락 일자.
- **프로필 사진(Image, 프로필 용도)**: 올린 회원, 256×256, 연결 상태·연결 해제 일자. 회원당 연결된 것 하나.
- **일회성 링크(인증·재설정)**: 인증 24시간, 재설정 30분, 한 번만 사용. 영구 보관하지 않는다.
- **로그인 상태**: 14일(마지막 활동 기준), 직전 로그인 일자·방식을 담는다. 정지·탈퇴·비밀번호 변경·재설정 때 삭제된다.

## Assumptions

- 범위: C-AUTH-1(로그인·로그아웃), C-AUTH-2(프로필 수정), C-FRIEND-1(친구 맺기), C-ACT-1(직전 로그인·최근 활동)은 모두 Tier A 공통 필수다. 개인 블로그 페이지(C-BLOG-1)의 목록·화면은 → specs/005-post-reading, 공개 범위·권한 매트릭스는 → specs/004-visibility-permission, 정지 부여는 → specs/014-report-hide, 탈퇴·복구·익명 처리는 → specs/015-withdraw, 사진 업로드 절차는 → specs/003-image-upload에서 다룬다.
- 개인 확장(공통 범위 아님): 설정 화면의 "모든 기기에서 로그아웃" 버튼, 이전 닉네임을 일정 기간 묶어 두기, 소개의 외부 링크 칸(김민서). 계정 연결 기능은 두지 않는다(L-1).
- Tier C·나중 단계: 금칙어·예약어 운영자 관리 화면(그 전까지는 설정 파일), 운영자 계정의 예약어 닉네임 허용.
- 선택 구현: 친구 공개(`FRIENDS`) 공개 범위와 친구 요청·수락 알림은 기본 비활성이다. 친구 맺기 자체는 모두 구현한다(2026-10-07 M1).
- 금칙어 목록은 공개된 한국어·영어 비속어 목록을 팀이 검토해 쓰고, 변형 표기를 목록에 함께 넣는다(09 §4-1). 목록 내용 자체는 이 spec의 범위 밖이다.
- 친구 요청에 이메일 인증이 필요한지는 원문(42 권한 매트릭스)에 없다. 기본값으로 팔로우(42 §10-1, 인증 불필요)와 같이 로그인만 요구한다고 가정하며, 친구 요청 횟수 제한도 원문에 없어 두지 않는다.
- 최근 활동의 "오늘/어제" 날짜 경계는 서비스 기준 시간대(한국 시간)를 따른다고 가정한다.
- 원문 간 충돌 처리: ① 정지 계정 — 42 P-5·P-7(2026-10-03)은 "로그인 단계에서만 막힘"이었으나 2026-10-07 회의 H7을 따라 남은 로그인 상태의 쓰기 요청도 계정 상태 거부(403, 정지 계정)로 거부한다. ② 51 §4는 "마지막 로그인"을 보여 준다고 적었으나 01 C-ACT-1과 2026-10-07 "직전 로그인 표시" 결정(07 §6, 11 §6-4)을 따라 **갱신 전 값(직전 로그인)**을 보여 준다. ③ 20 §3-7은 친구 요청·수락 이벤트를 "친구 공개 규격 적용자만"으로 적었으나 2026-10-07 M1로 친구 맺기는 공통이 되었다(알림만 선택). ④ 42의 "SSR 화면" 문구는 2026-10-07 Q2·H7(React + REST)로 "화면이 로그인 화면으로 안내"로 읽는다.

원문의 기술 결정 요약. 스키마 기준은 통합 V1([51](../../docs/51-erd-unified.md) / `erd/V1__common_schema.sql`).

- **테이블·컬럼** ([51 §2·§3](../../docs/51-erd-unified.md), [07 §8](../../docs/07-auth.md), [11 §7](../../docs/11-profile.md))
  - `member`: `handle` varchar(39) UNIQUE + `ck_member_handle` `^((go|gi)-)?[a-z0-9][a-z0-9_]{1,34}[a-z0-9]$`, `nickname` varchar(10) + `ck_member_nickname` + `uq_member_nickname ON member (lower(nickname))`, `nickname_changed_at`, `bio` varchar(200) + `ck_member_bio`, `role`(USER/ADMIN), `status`(ACTIVE/SUSPENDED/WITHDRAWN), `default_visibility`(기본 PUBLIC, CHECK PUBLIC/PRIVATE), `withdrawn_at`, `last_active_at`, `last_active_visible boolean NOT NULL DEFAULT true`, `deleted_at`. 회원 → 사진 컬럼 없음(`profile_image_id`·`profile_image_url` 삭제, 2026-10-07).
  - `auth_identity`: `provider`(LOCAL/GOOGLE/GITHUB), `provider_user_id`, `email`, `password_hash`(BCrypt, LOCAL만 `ck_auth_password`), `email_verified_at`, `last_login_at`. `uq_auth_identity (provider, provider_user_id)`, `uq_auth_identity_member (member_id)`, `ck_auth_local_email`(LOCAL은 소문자 이메일 = `provider_user_id`), `ix_auth_identity_email`(재설정 메일의 같은 이메일 계정 안내).
  - `member_agreement(member_id, type, version, agreed_at)`, PK `(member_id, type)`, type TERMS/PRIVACY/AI, 가입 트랜잭션에서 TERMS·PRIVACY 행 INSERT ([07 §3-1](../../docs/07-auth.md)).
  - `member_suspension`(reason, started_at, ends_at, lifted_at, lifted_by): 로그인 때 `lifted_at IS NULL AND ends_at < now()`면 `lifted_at` 기록 + `status = ACTIVE` ([07 §6](../../docs/07-auth.md)).
  - `friendship(member_a_id < member_b_id, requested_by, status PENDING/ACCEPTED, created_at, accepted_at)`, `ck_friendship_order`, `ix_friendship_b`. 맞요청은 `ON CONFLICT`로 수락 처리. 친구 판정은 `LEAST/GREATEST`로 한 행 조회 ([06 §6-1·§6-3](../../docs/06-visibility.md)).
  - 프로필 사진: `image.purpose = 'PROFILE'`, 현재 사진 = `uploader_id = 회원 AND purpose='PROFILE' AND status='ATTACHED' AND detached_at IS NULL`, `uq_image_profile_current` 부분 UNIQUE. 연결 트랜잭션: `member FOR UPDATE` → 이전 사진 `detached_at = now()` → 새 사진 `ATTACHED`(떼기 → 붙이기 순서) ([11 §4-4](../../docs/11-profile.md)). 작성자 사진은 `image` LEFT JOIN + `ImageStorage.publicUrl(COALESCE(thumb_storage_key, storage_key))`.
- **Redis** ([07 §3·§4-1·§6](../../docs/07-auth.md), [02 §2-1](../../docs/02-architecture.md)): 인증 토큰 `auth:verify:{토큰}` = memberId TTL 24h(32바이트 난수 URL-safe), 재발송 카운터 `auth:verify-resend:{memberId}:{yyyyMMdd}`, 재설정 `auth:reset:{토큰}` TTL 30m, 실패 횟수·IP 카운터, 최근 활동 갱신 간격 조절. 세션은 Spring Session Data Redis(14일), 세션 속성 `previousLoginAt`·`provider`. Redis 장애 정책은 02 §2-1 표.
- **보안 설정** ([07 §6](../../docs/07-auth.md), [02 §5](../../docs/02-architecture.md)): Spring Security 폼 로그인 + OAuth2 Client(Google `sub`, GitHub 숫자 ID, `state` 검증, GitHub `user:email` 권한, Google `email_verified = true`), 세션 쿠키 `HttpOnly`·`Secure`·`SameSite=Lax`, CSRF 토큰 헤더(저장 방식은 M17), 로그인 시 세션 ID 재발급, `server.forward-headers-strategy` + 신뢰 대역(NHN LB 내부 대역은 배포 담당 확인), `X-Forwarded-Proto`. 공통 코드는 JWT를 쓰지 않으며, 개인 서비스에서 JWT를 쓰려면 Refresh 토큰 Redis 저장·교체 + 토큰 버전 확인을 갖춘다(H7). 소셜 가입 마무리 화면만 CSP `img-src`에 `https://lh3.googleusercontent.com https://avatars.githubusercontent.com` 추가([12 §8](../../docs/12-content-sanitize.md)).
- **소셜 사진** ([11 §4-2](../../docs/11-profile.md)): Google `picture` + `=s256-c`, GitHub `avatar_url` + `&s=256`, `crossOrigin="anonymous"`, 5초 제한, presign `{purpose: PROFILE}` → 업로드 → complete → `PATCH /api/me/profile {profileImageId}`.
