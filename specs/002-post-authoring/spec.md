## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 글을 쓰고 발행한다 (Priority: P1)

인증된 회원이 [새 글]을 눌러 제목과 Markdown 본문을 쓰고, 발행 설정에서 태그와 공개 범위를 골라 발행한다. 전체 공개로 발행한 글은 `/@주소/posts/{번호}`에서 누구나 읽는다. (C-POST-1, C-POST-3)

**Why this priority**: 블로그의 핵심 가치 그 자체다. 이 흐름만 있어도 글을 쓰고 읽게 할 수 있다.

**Independent Test**: 회원으로 새 글 → 제목·본문 입력 → 발행 → 비로그인 브라우저로 글 주소 조회(읽기 성공)로 단독 검증한다.

**Acceptance Scenarios**:

1. **Given** 인증된 회원(기본 공개 범위 = 나만 보기), **When** [새 글]을 누르면, **Then** 서버에 그 회원의 임시글이 바로 하나 생기고 공개 범위 초기값은 나만 보기다. (C-POST-4 #7)
2. **Given** 제목·본문을 채운 임시글, **When** 전체 공개로 발행하면, **Then** 응답의 글 주소로 이동하고 비로그인 사용자도 그 주소에서 글을 읽을 수 있다. (C-POST-3 #1)
3. **Given** 제목이 비었거나, 본문이 공백뿐이거나, 업로드가 끝나지 않은 사진이 본문에 있는 임시글, **When** 발행하면, **Then** 실패한 항목이 모두 입력칸 옆에 표시되고 글은 임시글로 남는다. (C-POST-3 #6)
4. **Given** 나만 보기로 발행한 글, **When** 나중에 전체 공개로 바꾸면, **Then** 목록에서 처음 공개한 시점의 위치에 나온다. (C-POST-3 #7)
5. **Given** 다른 회원의 글 번호, **When** 그 글을 저장·발행하려 하면, **Then** 404로 거부되고 글 내용·상태·편집 버전·수정 일자가 그대로다. (C-POST-3 #5, C-OWN-1)
6. **Given** 본문에 다른 회원이 올린 우리 저장소 사진 주소, **When** 발행하면, **Then** 그 사진은 내 글에 연결되지 않고 링크로 보이며 원래 주인의 글에서는 그대로 보인다. (C-POST-3 #9)

### User Story 2 - 본문의 스크립트는 실행되지 않는다 (Priority: P1)

작성자가 무엇을 쓰든 독자 화면에서 스크립트가 실행되지 않는다. 직접 쓴 HTML은 글자로 보이고, 외부 링크는 안전하게 새 탭으로 열리며, 외부 이미지는 링크로 바뀐다. (C-POST-1)

**Why this priority**: 공개 글에 스크립트가 들어가면 모든 독자가 피해를 본다. 발행과 동시에 갖춰야 한다.

**Independent Test**: 12 §9-1의 공격 문자열 32개를 각각 본문·제목에 넣고 발행한 뒤, 결과에 실행 가능한 스크립트가 없고 브라우저에서 알림창이 뜨지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`가 든 본문, **When** 발행 후 글을 열면, **Then** 그 문자열이 글자로 보이고 알림창이 뜨지 않는다. (C-POST-1 #1·#2)
2. **Given** `[클릭](javascript:alert(1))`, `JaVaScRiPt:`, `&#106;avascript:`, `%6A…`, 참조형 `[x]: javascript:…` 링크, **When** 발행하면, **Then** 위험한 링크는 제거되거나 무해한 주소가 된다.
3. **Given** 외부 사이트 링크, **When** 독자가 누르면, **Then** 새 탭으로 열리고 원래 탭을 조작할 수 없으며 검색 순위 효과가 없다(noopener noreferrer nofollow ugc). (C-POST-1 #4)
4. **Given** 외부 이미지 주소와 내가 올린 사진(옛 공개 주소로 쓰임), **When** 발행하면, **Then** 외부 이미지는 "[이미지] 대체글" 링크로, 내 사진은 지금 공개 주소의 이미지로 보인다. (C-POST-1 #4)
5. **Given** `#`~`######` 제목·표·체크리스트·코드 블록이 든 본문, **When** 발행하면, **Then** 의도대로 보이고 본문에 1단계 제목은 없다. (C-POST-1 #3)
6. **Given** 같은 본문, **When** 에디터 미리보기와 발행 결과를 비교하면, **Then** 같다. (C-POST-1 #5)
7. **Given** 인용 25단계로 중첩된 본문, **When** 발행하면, **Then** "글 구조가 너무 복잡해요 (목록·인용은 20단계까지)"로 거부된다. 15단계는 허용된다. (C-POST-1 #6)

### User Story 3 - 쓰다 만 글을 잃지 않고 이어 쓴다 (Priority: P1)

작성자가 타이핑하면 이 기기에 1초 단위로, 서버에 30초 이내로 자동 저장된다. 네트워크가 끊겨도 이 기기에 계속 저장되고 연결되면 동기화된다. 나중에 임시글을 다시 열어 이어 쓴다. (C-POST-2)

**Why this priority**: "저장했다고 믿은 글이 사라지는" 일은 신뢰를 잃게 한다. 긴 글을 쓰는 블로그에 필수다.

**Independent Test**: 글을 쓰다 네트워크를 끊고 계속 입력 → 상태 표시 확인 → 네트워크 복구 후 동기화 확인 → 다른 기기에서 임시글을 열어 같은 내용 확인.

**Acceptance Scenarios**:

1. **Given** 에디터에서 입력 중, **When** 입력이 1초 멈추면, **Then** 이 기기에 저장되고 "● 이 기기에 저장됨 (동기화 대기)"가 보이며, 3초 더 멈추면(계속 입력 중이면 최대 30초마다) 서버에 저장되어 "✓ 저장됨 14:03"이 된다.
2. **Given** 오프라인 상태, **When** 계속 입력하면, **Then** "⚠ 오프라인 — 이 기기에 저장 중, 연결되면 자동 동기화"가 보이고, 연결되면 자동으로 서버에 저장된다.
3. **Given** 서버에 저장된 임시글, **When** 서버 쪽 임시 보관 시간(24시간)이 지난 뒤 다른 기기에서 다시 열면, **Then** 마지막 저장 내용으로 이어 쓸 수 있다. (C-POST-2)
4. **Given** 서버로 아직 못 보낸 내용이 있음, **When** 페이지를 떠나려 하면, **Then** 확인창이 뜬다.
5. **Given** 이 기기에 미전송 내용이 있고 그 출발 버전이 서버 버전과 같음, **When** 에디터를 다시 열면, **Then** 충돌로 보지 않고 "이 기기에 저장되지 않은 변경을 불러왔어요" 안내 후 이어 편집한다.
6. **Given** 작성자가 [저장]을 누름, **When** 저장이 끝나면, **Then** 즉시 영구 저장되어 서버 쪽 임시 보관분이 사라져도 남아 있다. (D-3)
7. **Given** 공용 PC에서 쓰던 회원, **When** 로그아웃하면, **Then** 그 회원의 이 기기 작업 내용·백업이 모두 지워진다. (C-AUTH-1 #2)

### User Story 4 - 발행한 글을 고쳐 다시 발행한다 (Priority: P2)

작성자가 발행한 글을 고치는 동안 독자는 마지막 발행본을 본다. 다시 발행하면 내용이 바뀌고 "수정됨" 표시가 붙지만 주소·발행일·목록 위치·반응 수는 그대로다. 고치던 내용을 버리면 발행본으로 돌아간다. (C-POST-3)

**Why this priority**: 발행 후 오타 수정은 흔하지만, 최초 발행 흐름이 먼저 있어야 의미가 있다.

**Independent Test**: 발행 글을 열어 고치고 저장 → 비로그인으로 조회(옛 내용) → 다시 발행 → 비로그인 조회(새 내용, 주소·날짜·반응 수 동일).

**Acceptance Scenarios**:

1. **Given** 발행된 글을 작성자가 고쳐 자동·수동 저장함, **When** 독자가 그 글을 보면, **Then** 마지막 발행본이 보인다. (C-POST-3 #3)
2. **Given** 고친 작업본, **When** 다시 발행하면, **Then** 내용이 반영되고 주소·최초 발행 일자·최초 공개 일자·조회수·좋아요·댓글은 그대로이며 글에 "수정됨 · 10월 3일"이 붙는다. (C-POST-3 #2)
3. **Given** 수정 중인 글, **When** 작성자가 [변경 취소]하면, **Then** 작업본이 버려지고 독자가 보던 발행본은 그대로다.
4. **Given** 발행한 글을 다시 열 때 작업본이 있음, **When** 에디터를 열면, **Then** 작업본을 불러온다(없으면 발행본).
5. **Given** 발행한 글, **When** 임시글로 되돌리려 하면, **Then** 그런 기능은 없고 내리고 싶으면 나만 보기로 바꾼다. (P-1)

### User Story 5 - 여러 탭·기기에서 같은 글을 고쳐도 몰래 덮어쓰지 않는다 (Priority: P2)

같은 글을 두 곳에서 고치면 저장 충돌을 감지하고, 두 내용을 나란히 보여 차이를 강조한 뒤 작성자가 고르게 한다. (2026-10-02 "여러 탭·기기 편집 충돌")

**Why this priority**: 데이터 손실 방지 장치지만 단일 탭 사용에서는 드물게 일어난다.

**Independent Test**: 같은 글을 탭 두 개에서 열고 A 탭에서 저장한 뒤 B 탭에서 입력해 배너와 비교 창의 세 가지 선택을 각각 확인한다.

**Acceptance Scenarios**:

1. **Given** 탭 A가 먼저 저장한 글, **When** 탭 B의 자동 저장이 충돌하면, **Then** 탭 B의 편집은 막히지 않고 서버 전송만 멈추며 "⚠ 다른 탭이나 기기에서 이 글이 수정되었어요(14:03). 지금 내용은 이 기기에만 저장되고 있어요. [비교하기]" 배너가 보인다.
2. **Given** 충돌 배너 상태, **When** [비교하기]·[저장]·[발행] 중 하나를 누르면, **Then** 저장된 내용과 편집 중인 내용을 나란히 보여 주는 비교 창이 열리고 삭제 부분은 빨간 배경과 `−`, 추가 부분은 초록 배경과 `+`로 표시된다.
3. **Given** 비교 창, **When** [편집 중인 내용으로 저장]을 누르면, **Then** "14:03에 저장된 내용이 지금 편집 중인 내용으로 바뀌어요. 정말 저장할까요?" 확인 후에만 덮어쓴다.
4. **Given** 비교 창, **When** [저장된 내용 불러오기]를 누르면, **Then** 에디터가 서버 내용으로 바뀌고 편집 중이던 내용은 이 기기에 7일 동안 백업된다는 안내가 보인다.
5. **Given** 비교 창, **When** [새 임시글로 따로 저장]을 누르면, **Then** 편집 중인 내용으로 새 임시글이 생기고 원래 글은 서버 내용 그대로다.

### User Story 6 - [발행]을 여러 번 눌러도 한 번만 발행된다 (Priority: P2)

버튼 연타나 네트워크 재전송이 있어도 글은 한 번만 발행되고, 이미 성공한 발행에 충돌 창이 뜨지 않는다. (C-POST-3 "연달아 눌러도 한 번만 발행")

**Why this priority**: 공통 완료 기준이지만 발행 기능 위에 덧붙는 보호 장치다.

**Independent Test**: 같은 발행 요청 키로 동시 20건을 보내 편집 버전이 1만 증가하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** [발행]을 누름, **When** 응답을 받기 전, **Then** 버튼이 비활성화되고 "발행 중…"이 보인다.
2. **Given** 같은 발행 요청 키로 동시 20건, **When** 모두 처리되면, **Then** 발행은 한 번만 일어나고(편집 버전 +1) 나머지는 같은 결과를 받거나 "처리 중"을 받아 1초 뒤 같은 키로 재시도한다. (C-POST-3 #4)
3. **Given** 이미 쓴 발행 요청 키, **When** 다른 내용으로 같은 키를 다시 보내면, **Then** 거부된다(422).

### User Story 7 - 정화 규칙이 바뀌면 기존 글도 새 규칙을 따르고, 빈 임시글은 정리된다 (Priority: P3)

운영자가 렌더링·정화 규칙을 바꾸면 기존 발행 글이 새 규칙으로 다시 렌더링된다. 아무 내용 없이 버려진 임시글은 하루 뒤 정리된다. (C-POST-1 #8, 2026-10-02 "빈 임시글 정리")

**Why this priority**: 운영·유지보수 기능으로, 사용자 흐름이 갖춰진 뒤 필요하다.

**Independent Test**: 렌더링 규칙 버전을 올리고 다시 렌더링 작업을 실행해 이전 버전 글이 0건인지 확인하고, 24시간 지난 빈 임시글이 정리 작업 뒤 사라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 렌더링 규칙 버전이 올라감, **When** 다시 렌더링 작업이 끝나면, **Then** 모든 발행 글이 새 규칙으로 보이고 "수정됨" 일자·편집 버전은 바뀌지 않는다. (C-POST-1 #8)
2. **Given** 만든 지·마지막 수정 후 24시간이 지났고 제목·본문이 비었으며 서버 쪽 임시 보관분도 없는 임시글, **When** 매일 새벽 정리 작업이 돌면, **Then** 휴지통을 거치지 않고 완전히 삭제된다.

### Edge Cases

- 발행 처리 중에 다른 탭의 자동 저장이 들어오면? → 발행 확정 뒤 서버 쪽 임시 보관분을 지울 때, 발행 때 확인한 버전보다 새 버전이면 지우지 않는다.
- 발행 처리 저장이 실패하면? → 서버 쪽 임시 보관분은 지우지 않는다(지우는 일은 성공 확정 뒤에만). 발행 요청 키도 풀려 같은 키로 다시 시도할 수 있다.
- 서버 쪽 임시 보관소가 재시작되면? → 최대 약 1초 분량 손실, 이 기기에 남아 있으면 그것도 복구된다.
- 서버 쪽 임시 보관소에 연결할 수 없으면? → 자동 저장이 영구 저장소에 바로 저장하도록 전환하고 버전 확인은 영구 저장소 기준으로 한다(손실 없음). 발행 연타 방지는 행 잠금·버전 확인으로 막는다.
- 서버 쪽 임시 보관소 메모리가 부족하면? → 자동 저장분을 밀어내지 않고 쓰기가 실패하며, 내용은 이 기기에 남아 재시도된다.
- 이 기기 데이터가 지워지면? → 서버에 30초 이내 내용이 있다(최대 30초 손실).
- 업로드에 실패한 사진이 본문에 있으면? → 임시 표시로 본문에 남고 화면에는 정상으로 보이며 자동 저장은 계속된다. 발행은 거부된다. 연결되면 자동 재시도해 진짜 주소로 바꾼다(→ specs/003-image-upload).
- 휴지통에 있는 글을 저장·발행·변경 취소하려 하면? → 작성자라도 404 (→ specs/006-manage-delete).
- 인증 전 회원이 [새 글]·저장·발행을 하면? → 403 (→ specs/001-account-auth).
- 같은 내용으로 다시 발행하면? → 다시 발행으로 처리되어 "수정됨" 일자가 기록된다(원문은 다시 발행할 때마다 기록).
- 공개 범위만 바꾸면? → 다시 발행이 아니므로 "수정됨" 일자·작업본·편집 버전이 그대로다(→ specs/004-visibility-permission).
- 요약 대상 글자가 없는 글(코드만 있는 글)이면? → 요약이 비어 있다.
- 썸네일이 없는 옛 사진이 첫 사진이면? → 원본 주소로 대체한다.
- 제목에 방향 뒤집기 문자(U+202E)·폭 0 문자가 있거나 NFD 한글이면? → 제거·NFC 정규화 후 검사한다.

## Requirements *(mandatory)*

### Functional Requirements

**글 만들기와 입력 규칙**

- **FR-001**: System MUST [새 글]을 누르는 즉시 그 회원 소유의 임시글을 만들고(편집 버전 0), 공개 범위 초기값을 회원의 새 글 기본 공개 범위로 정해야 한다. 비회원은 401, 인증 전·탈퇴 유예 회원은 403으로 거부한다. (04 §2-5, V-4, C-POST-4 #7, 42 §5-2)
- **FR-002**: System MUST 본문을 작성자가 쓴 Markdown 원문 그대로 저장해야 하며, 브라우저가 만든 HTML은 받지 않는다. 에디터 종류는 자유지만 Markdown으로 내보내야 하며 Markdown에 없는 서식(글자 색·가운데 정렬 등)은 저장되지 않는다. (C-POST-1, 12 §2)
- **FR-003**: System MUST CommonMark + GFM 문법(표·취소선·체크리스트·주소 자동 링크)을 지원해야 한다. 각주·수식·Mermaid·임베드는 공통 범위에서 제외한다. (S-1, S-7)
- **FR-004**: System MUST 글 제목을 NFC로 정규화하고 보이지 않는 글자(U+200B~U+200F, U+2060~U+2069, U+FEFF)·방향 제어 문자(U+202A~U+202E)·제어 문자를 지운 뒤 앞뒤 공백을 제거해 1~100자를 검사해야 한다. 제목은 글자로만 다루고 화면에 이스케이프해 표시한다. (S-10, 12 §7-4)
- **FR-005**: System MUST 본문을 최대 100,000자로 제한해야 한다(발행본·작업본 모두). (P-6)

**임시저장·자동 저장 (C-POST-2)**

- **FR-006**: 자동 저장 대상은 제목과 본문뿐이어야 한다. 태그는 발행할 때 확정한다(→ specs/008-tag). (2026-10-02 "자동 저장 범위")
- **FR-007**: System MUST 자동 저장을 3단계로 해야 한다: ① 입력이 1초 멈추면 이 기기에 저장 ② 바뀐 내용이 있을 때만 입력이 3초 멈추면, 계속 입력 중이면 최대 30초마다, 그리고 탭이 가려지거나 페이지를 떠날 때 서버로 전송 ③ 서버에 모인 내용을 1분마다 영구 저장. 이 수치는 초기 설정값이다. (C-POST-2, 04 §2·§2-1)
- **FR-008**: System MUST 임시글의 원본을 영구 저장소에 두어, 서버 쪽 임시 보관(24시간, 저장할 때마다 연장) 만료와 상관없이 임시글을 다시 열어 이어 쓸 수 있게 해야 한다. (D-1, C-POST-2)
- **FR-009**: System MUST 작성자가 누른 수동 저장과 발행을 즉시 영구 저장소에 반영해야 한다. (D-3)
- **FR-010**: 브라우저는 탭 하나에서 서버 저장 요청을 한 번에 하나만 보내고 응답 뒤에 다음 요청을 보내야 한다. 실패하면 2초 → 4초 → 8초 … 최대 60초 간격에 무작위 지연을 섞어 재시도하고, 그동안 내용은 이 기기에 남는다. (04 §2-2)
- **FR-011**: System MUST 자동 저장을 사용자당 5초에 1번, 요청 크기 1MB로 제한하고, 넘으면 다시 시도할 시점과 함께 요청 과다(429) 또는 너무 큼(413)으로 응답해야 한다. (04 §2-1)
- **FR-012**: 서버로 못 보낸 내용이 있는데 페이지를 떠나려 하면 확인창을 띄워야 한다. (04 §2-2)
- **FR-013**: 에디터는 저장 상태를 색만이 아니라 글자로 "✓ 저장됨 14:03" / "● 이 기기에 저장됨 (동기화 대기)" / "⚠ 오프라인 — 이 기기에 저장 중, 연결되면 자동 동기화" / "⚠ 다른 곳에서 수정됨 — 이 기기에만 저장 중 [비교하기]"로 보여야 한다. (04 §2-2)
- **FR-014**: 이 기기에 저장한 작업 내용은 회원별로 구분하고 로그인 정보는 담지 않아야 하며, 발행에 성공하거나 미전송 내용 없이 에디터를 떠날 때 지운다. 로그아웃할 때는 그 회원의 작업 내용과 백업을 전부 지운다. (04 §2-2, 2026-10-02 "공용 PC", C-AUTH-1 #2)
- **FR-015**: System MUST 임시글의 저장 내용은 글 자체에, 발행한 글의 저장 내용은 독자에게 보이지 않는 별도 작업본에 반영해, 수정 중에도 독자에게는 마지막 발행본이 보이게 해야 한다. (2026-10-02 Q9, C-POST-3 #3)
- **FR-016**: System MUST 늦게 도착한 옛 편집 버전의 내용이 더 새 버전을 덮어쓰지 않게 해야 한다. (04 §2-4, §5)
- **FR-017**: System MUST 임시글·작업본을 저장할 때는 렌더링하지 않고, 렌더링은 발행할 때 한 번만 해야 한다. (04 §2-4, 12 §2)
- **FR-018**: System MUST 서버 쪽 임시 보관소에 연결할 수 없으면 자동 저장을 영구 저장소에 바로 쓰도록 전환하고 버전 확인도 영구 저장소 기준으로 해야 한다. 임시 보관소는 재시작 시 손실이 약 1초 이내이고, 메모리가 부족해도 자동 저장분을 밀어내지 않아야 한다. (04 §2-6, 02 §2)
- **FR-019**: System MUST 남의 글·없는 글에 대한 자동 저장·수동 저장을 404로 거부하고 글을 바꾸지 않아야 한다. (04 §2-3, C-OWN-1)

**편집 충돌 (2026-10-02 결정)**

- **FR-020**: System MUST 자동 저장·수동 저장·발행 요청에 내용이 출발한 편집 버전을 받아, 현재 버전과 같을 때만 받아들이고 버전을 1 올려야 한다. 다르면 저장하지 않고 충돌(409)로 응답하며 서버의 제목·본문·버전·저장 시각을 함께 돌려준다. 서버는 어느 쪽 내용도 몰래 덮어쓰지 않는다. (04 §2-3·§2-7, 05 §5)
- **FR-021**: 자동 저장이 충돌하면 편집을 막지 않고(입력 중에 창을 띄우지 않음) 서버 전송만 멈춘 채 이 기기 저장을 계속하며 "⚠ 다른 탭이나 기기에서 이 글이 수정되었어요(14:03). 지금 내용은 이 기기에만 저장되고 있어요. [비교하기]" 배너를 보여야 한다. [비교하기]·수동 저장·발행을 누르면 비교 창을 연다. (04 §2-7)
- **FR-022**: 에디터를 열 때 이 기기에 미전송 내용이 있으면, 그 출발 버전이 서버 버전과 같을 때는 충돌로 보지 않고 "이 기기에 저장되지 않은 변경을 불러왔어요" 안내 후 이어 편집하고, 다르면 바로 비교 창을 띄워야 한다. (04 §2-7)
- **FR-023**: 비교 창은 줄 단위로 비교하고 바뀐 줄 안은 단어 단위로 강조해야 하며(제목이 다르면 제목도), 지운 부분은 빨간 배경 + `−`, 추가한 부분은 초록 배경 + `+`로 색과 기호를 함께 쓴다. 넓은 화면은 좌우 나란히, 모바일은 위아래로 합친 보기이고, 긴 글은 [이전 차이]·[다음 차이] 버튼과 바뀌지 않은 긴 구간 접기를 제공한다. (04 §2-7)
- **FR-024**: 비교 창은 결과를 이름에 담은 버튼을 제공해야 한다: [편집 중인 내용으로 저장](확인 문구 "…저장된 내용이 지금 편집 중인 내용으로 바뀌어요. 정말 저장할까요?"에 동의할 때만 덮어씀), [저장된 내용 불러오기](편집 중이던 내용은 이 기기에 7일 백업, 안내만), [새 임시글로 따로 저장](편집 중인 내용으로 새 임시글을 만들고 원래 글은 서버 내용 그대로), 닫기(계속 편집, 전송 멈춤·배너 유지). (04 §2-7, 2026-10-02 "여러 탭·기기 편집 충돌")

**사진과 본문 (→ specs/003-image-upload)**

- **FR-025**: System MUST 사진 데이터를 본문이나 자동 저장 내용에 넣지 않고, 올리는 즉시 따로 저장해 본문에는 사진 주소만 남겨야 한다. 업로드가 끝나지 않은 사진은 본문에 임시 표시로 남고 자동 저장은 그대로 진행한다. (D-4, 04 §4-3)

**발행 (C-POST-3)**

- **FR-026**: System MUST 발행 때 다음을 검사하고, 실패하면 실패한 항목을 모두 담아 400으로 거부하며 글 상태를 바꾸지 않아야 한다: 제목 필수(FR-004 정리 후 1~100자), 본문 필수(앞뒤 공백 제거 후 1자 이상, 최대 100,000자), 태그 0~10개(최대 개수는 설정값, 정규화·형식은 → specs/008-tag), 공개 범위 전체 공개/나만 보기(값 추가는 → specs/004-visibility-permission), 업로드가 끝나지 않은 사진 없음. 화면은 각 입력칸 옆에 이유를 표시한다. (05 §4, P-5, C-POST-3 #6)
- **FR-027**: System MUST 발행할 때 목록용 요약을 만들어야 한다: 정화된 결과에서 코드 블록·이미지·표·수식을 통째로 빼고, 제목·문단·목록의 글자(인라인 코드·링크는 글자로)만 꺼내 줄바꿈·연속 공백을 공백 하나로 바꾼 뒤 앞 200자(단어 중간이면 그 단어 앞에서)로 자른다. (05 §4, 10 §2-1)
- **FR-028**: System MUST 발행할 때 본문에 나오는 첫 번째 "작성자가 올린 사진"의 640px 썸네일을 글 썸네일로 지정해야 한다. 썸네일이 없는 옛 사진은 원본 주소로 대체한다. (05 §4, 10 §6)
- **FR-029**: System MUST 발행할 때 본문의 우리 저장소 사진 중 작성자가 올린 사진만 그 글에 연결하고 본문에서 빠진 사진은 연결을 해제해야 한다. 수동 저장과 1분 DB 반영 때도 같은 규칙으로 연결한다(→ specs/003-image-upload FR-022). 다른 회원이 올린 사진은 연결하지 않고 링크로 둔다. (05 §7 ⑥, 2026-10-07 "남이 올린 사진", C-POST-3 #9)
- **FR-030**: System MUST 발행의 소유 확인·버전 확인·태그 확정·사진 연결·발행본 반영·작업본 삭제를 하나의 단위로 모두 성공하거나 모두 실패하게 처리해야 한다. 서버 쪽 임시 보관분은 성공이 확정된 뒤에만 지우며, 발행 때 확인한 버전보다 새 버전이 들어와 있으면 지우지 않는다. 렌더링은 이 단위에 들어가기 전에 끝낸다. (05 §7, J-5)
- **FR-031**: System MUST 최초 발행 때 글을 발행 상태로 바꾸고 최초 발행 일자를 기록해야 한다. 최초 공개 일자는 글이 처음으로 "발행 + 전체 공개"가 되는 순간에만 기록하고, 이후 공개 범위를 껐다 켜도 처음 값을 유지한다. (P-3, 05 §3, C-POST-3 #7)
- **FR-032**: System MUST 다시 발행할 때 주소(`/@주소/posts/{번호}`)·최초 발행 일자·최초 공개 일자·조회수·좋아요·댓글을 유지하고, 재발행 일자를 매번 기록해 글 상세에 "수정됨 · 날짜"로 보이게 해야 한다. 재발행 일자는 다시 발행할 때만 바뀌고 자동 저장 반영·공개 범위 변경으로는 바뀌지 않는다. 공개 범위는 다시 발행하면서 바꿀 수 있다. (P-2, 05 §8, C-POST-3 #2)
- **FR-033**: System MUST 발행한 글을 임시글로 되돌리는 기능을 두지 않아야 한다. 내리려면 나만 보기로 바꾼다. 발행 이력·되돌리기는 공통에서 남기지 않는다. (P-1, 05 §8)
- **FR-034**: 글 상태는 임시글 / 발행됨 / 수정 중(작업본 있음) 세 가지로 구분되어야 하며, 임시글은 작성자 외에게 404다. 발행한 글을 다시 열면 작업본이 있으면 작업본을, 없으면 발행본을 에디터로 불러온다. "수정 중" 표시 화면은 → specs/006-manage-delete, specs/005-post-reading. (05 §2, 04 §2-5)
- **FR-035**: 작성자는 수정 중인 글의 [변경 취소]로 작업본과 서버 쪽 임시 보관분을 버릴 수 있어야 하며, 독자가 보던 발행본은 그대로다. (04 §2-5)
- **FR-036**: System MUST 저장·발행·변경 취소를 작성자에게만 허용해야 한다. 남의 글·없는 글·휴지통 글은 404이고 글이 바뀌지 않는다. 관리자도 남의 글 내용을 수정할 수 없다(숨김만, → specs/014-report-hide). 비회원 401, 인증 전·탈퇴 유예 회원 403. (05 §8, 42 §3·§4·§5-2, C-POST-3 #5, C-OWN-1)
- **FR-037**: System MUST [발행]을 연달아 누르거나 요청이 재전송되어도 한 번만 발행해야 한다: 화면은 누르는 즉시 버튼을 비활성화하고 "발행 중…"을 보이며, 발행 시도마다 새 요청 키를 붙인다. 같은 키가 처리 중이면 "처리 중"(409)으로 응답해 브라우저가 1초 뒤 같은 키로 재시도하고, 끝난 키면 저장된 응답을 그대로 돌려주며(10분 보관), 같은 키에 다른 내용이면 422로 거부하고, 실패하면 키를 풀어 다시 시도할 수 있게 한다. 키 보관소에 장애가 나도 행 잠금과 버전 확인으로 중복 발행을 막는다. (P-4, 05 §6, C-POST-3 #4)
- **FR-038**: System MUST 발행에 성공하면 글 주소·최초 발행 일자·최초 공개 일자·재발행 일자·새 편집 버전을 돌려주고, 화면은 그 주소로 이동해야 한다. (05 §5)
- **FR-039**: System MUST 최초 발행·다시 발행·처음 공개된 사실을 다른 기능(알림·검색 색인·sitemap 등)이 이어받을 수 있게 발행이 확정된 뒤 알려야 하며, 그 기능들의 실패가 발행을 실패시키지 않아야 한다(→ specs/011-notification, specs/012-trending-search). (05 §7 ⑩, 20 §3-1, 01 §3-5)

**본문 렌더링·정화 (C-POST-1)**

- **FR-040**: System MUST 본문에 직접 쓴 HTML을 전부 글자로 보이게 하고(예: `<b>`가 글자로 보임), 그와 별개로 렌더링 결과를 허용 목록 기반으로 한 번 더 정화해야 한다(이중 방어). 정화는 서버에서만, 하나의 렌더러로만 한다. (S-2, 12 §2, C-POST-1 #2)
- **FR-041**: System MUST 렌더링 결과에 허용 목록의 요소·속성만 남기고 나머지(스크립트·스타일·iframe·폼·svg 등 요소, 이벤트·스타일 속성 등)는 전부 제거해야 한다. 허용 목록은 문단·줄바꿈·구분선·인용·제목(2~6단계)·굵게·기울임·취소선·목록·번호 목록·읽기 전용 체크박스·인라인 코드·코드 블록·표·링크·이미지와 각 요소의 제한된 속성이다. (S-4, 12 §4)
- **FR-042**: System MUST 본문 제목을 한 단계씩 낮춰(`#` → 2단계 … `######` → 6단계) 본문에 1단계 제목이 없게 하고, 제목 앵커 이름에 `h-` 접두어를 붙이며 같은 이름은 `-1`, `-2`로 구분해야 한다. (S-9, 12 §3·§7-3, C-POST-1 #3)
- **FR-043**: System MUST 링크 주소를 `http`·`https`·`mailto`·`/`로 시작하는 상대 경로만 허용하고, 그 외(`javascript:`·`data:`·`vbscript:` 등)는 대소문자 섞기·문자 참조·퍼센트 인코딩·앞 공백·참조형 링크로 숨겨도 제거해야 한다. 외부 링크는 새 탭 + `noopener noreferrer nofollow ugc`, 우리 사이트 링크는 같은 탭·관계 표시 없음이다. (S-5, 12 §5, C-POST-1 #4)
- **FR-044**: System MUST 우리 저장소 사진 중 글 작성자가 올린 사진만 이미지로 보여 주되 주소를 지금의 공개 주소로 바꿔 써야 하고(옛 공개 주소로 쓴 사진 포함, 지연 로딩), 외부 이미지와 다른 회원이 올린 우리 저장소 사진은 "[이미지] 대체글" 링크(외부 링크 규칙, 대체글이 없으면 주소)로 바꿔야 한다. 원문은 바꾸지 않는다. 미리보기는 로그인한 본인, 다시 렌더링은 글 작성자를 기준으로 판단한다. (S-6, 12 §6, C-POST-1 #4)
- **FR-045**: System MUST 체크리스트를 항상 읽기 전용으로, 코드 블록 내용은 이스케이프해 보여야 하며, 코드 강조는 브라우저에서 하되 강조가 실패해도 코드는 읽혀야 한다. 임베드(iframe)는 공통에서 제외한다. (S-7, S-8, 12 §3)
- **FR-046**: System MUST 목록·인용 중첩이 20단계를 넘거나 렌더링이 1초를 넘으면 "글 구조가 너무 복잡해요 (목록·인용은 20단계까지)"로 거부해(400) 발행하지 않아야 한다. (S-14, 12 §7-5, C-POST-1 #6)
- **FR-047**: 작성자는 서버 렌더러와 같은 결과의 미리보기를 볼 수 있어야 한다. 입력이 0.5초 멈추면 요청하고, 로그인이 필요하며, 사용자당 1분에 60번으로 제한한다. 에디터 자체 미리보기는 참고용이고 최종 결과는 서버 렌더러가 기준이다. (S-11, 12 §7-6, C-POST-1 #5)
- **FR-048**: System MUST 렌더링 결과를 발행 때 한 번 만들어 저장하고 조회 때는 그대로 쓰며, 결과마다 렌더링 규칙 버전을 기록해야 한다. 렌더링·정화 규칙이 바뀌어 버전이 오르면 이전 버전으로 렌더링된 발행 글을 100개씩 다시 렌더링해 본문 결과·요약을 갱신하되 재발행 일자·편집 버전은 바꾸지 않는다. (S-12, 12 §7-7, C-POST-1 #8)
- **FR-049**: System MUST 모든 응답에 2차 방어 보안 정책을 붙여야 한다: 스크립트는 우리 사이트 파일만(인라인 금지), 이미지는 우리 사이트·사진 저장소 공개 주소·내장 데이터·기기 안 임시 사진만, 네트워크 연결은 우리 사이트·사진 저장소 공개 주소만, 플러그인 객체 금지, 다른 사이트가 우리 페이지를 프레임에 넣는 것 금지, 기준 주소 변경 금지, 폼 전송은 우리 사이트만, 응답 형식 추측 금지, 다른 사이트로 주소 전체를 넘기지 않음. 사진 저장소 공개 주소는 정화 허용 목록과 같은 설정값 하나를 쓴다. 소셜 가입 마무리 화면의 예외는 → specs/001-account-auth. (S-13, 12 §8, H3, C-POST-1 #7)

**빈 임시글 정리**

- **FR-050**: System MUST 매일 새벽 한 번, 임시글이고 제목·본문이 모두 비었으며 만든 지와 마지막 수정 후 모두 24시간이 지났고 서버 쪽 임시 보관분도 없는 글을 휴지통을 거치지 않고 완전 삭제해야 한다. 이 삭제는 다른 기능에 알리지 않는다. 사용자가 직접 지운 빈 임시글의 즉시 삭제는 → specs/006-manage-delete. (04 §2-5, 2026-10-02 "빈 임시글 정리", 20 §3-1)

### Key Entities *(include if feature involves data)*

- **글(Post)**: 작성자, 상태(임시·발행), 제목, 본문 원문(Markdown, 최대 100,000자), 렌더링·정화된 본문, 요약(200자), 썸네일 주소, 공개 범위, 편집 버전, 렌더링 규칙 버전, 최초 발행·최초 공개·재발행·생성·수정 일자, 반응 수(조회·좋아요·댓글, 이 기능은 유지만 함). 삭제·숨김 일자는 다른 기능 소관.
- **작업본(Post Draft)**: 발행한 글 하나에 0~1개. 고치는 중인 제목·본문과 편집 버전, 수정 시작·마지막 저장 일자. 다시 발행·변경 취소 때 사라지고 글이 완전 삭제되면 함께 사라진다.
- **서버 쪽 자동 저장 보관분**: 글마다 소유자·제목·본문·편집 버전·저장 시각. 24시간(저장마다 연장), 1분마다 영구 반영된다.
- **기기 안 작업 내용**: 회원·글마다 제목·본문·출발 편집 버전·미전송 여부·업로드 대기 사진·갱신 시각. 비교 창의 백업은 7일.
- **글-사진 연결**: 글과 작성자가 올린 사진의 연결. 발행 때 동기화한다(사진 자체는 → specs/003-image-upload).
- **발행 요청 키**: 회원·키마다 요청 내용 요약과 처리 상태 또는 응답, 10분 보관.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 네트워크가 끊긴 동안 쓴 내용의 손실은 0이고, 이 기기 데이터가 지워져도 손실은 최대 30초 분량이다.
- **SC-002**: 같은 발행 요청 키로 동시 20건을 보내면 발행은 정확히 1번 일어난다(편집 버전 +1).
- **SC-003**: 12 §9-1의 공격 문자열 32개 모두에 대해 발행 결과에 실행 가능한 스크립트가 0개이고, 브라우저 종단 간 시험에서 알림창이 0번 뜬다.
- **SC-004**: 같은 본문의 미리보기 결과와 발행 결과가 100% 같다.
- **SC-005**: 다시 발행 전후로 주소·최초 발행 일자·최초 공개 일자·조회수·좋아요·댓글 값의 변화는 0이다.
- **SC-006**: 수정 중인 글을 독자가 조회했을 때 마지막 발행본이 아닌 내용이 보이는 경우는 0건이다.
- **SC-007**: 편집 충돌 상황에서 작성자의 확인 없이 한쪽 내용이 덮어써진 경우는 0건이다.
- **SC-008**: 남의 글에 대한 저장·발행·변경 취소 요청 성공은 0건이고, 요청 전후 글의 내용·상태·편집 버전·수정 일자가 같다.
- **SC-009**: 100,000자 본문도 렌더링 제한 시간(1초) 안에 발행된다.
- **SC-010**: 렌더링 규칙 버전을 올리고 다시 렌더링 작업이 끝난 뒤 이전 버전으로 남은 발행 글은 0건이다.

## Assumptions

- 범위: Tier A 공통 C-POST-1(글 작성·본문 정화), C-POST-2(임시저장·자동 저장), C-POST-3(발행·수정). 공개 범위 값과 변경 규칙은 → specs/004-visibility-permission, 사진 업로드·검증·정리는 → specs/003-image-upload, 태그 정규화·자동완성·태그 입력 위치는 → specs/008-tag, 목록 카드·글 상세의 표시("수정됨" 등)는 → specs/005-post-reading, 내 글 관리의 "수정 중" 배지·[변경 취소] 버튼과 삭제·휴지통은 → specs/006-manage-delete, 알림은 → specs/011-notification, AI 태그 추천(실패해도 발행 성공)은 → specs/013-ai-tag-suggest.
- 개인 확장(공통 범위 아님): 발행 이력·되돌리기(김민서), 각주·수식·Mermaid·임베드(허용 시 특정 동영상 사이트만 + 격리), 코드 복사 버튼, 목차 화면, 외부 배지 도메인 허용, 여러 글 공개 범위 한꺼번에 바꾸기.
- 에디터 종류(WYSIWYG·Markdown·Toast UI 등)는 각자 자유이며, 에디터가 다크 테마를 지원하는지는 → specs/016-dark-mode.
- 자동 저장의 시간·횟수 값(1초·3초·30초·1분·24시간·5초에 1번·1MB)은 원문이 "초기값"으로 둔 설정값이다. 태그 최대 개수도 설정값(기본 10개)이다.
- 원문은 자동 저장 단계의 제목 길이 검사를 따로 적지 않았다. 저장되는 글·작업본의 제목 최대 100자, 본문 최대 100,000자 제한이 저장 단계에도 적용된다고 가정한다.
- 미리보기는 "로그인 필요"만 정해져 있어 이메일 인증 여부와 상관없이 로그인한 회원이 쓸 수 있다고 가정한다.
- 서버 쪽 임시 보관소의 보존 데이터·캐시 분리와 메모리 한도는 아키텍처 정리(M30)에서 정한다. 사용자 관점의 요구(밀어내지 않음, 장애 시 영구 저장소로 전환)는 이 spec의 FR-018이 정한다.
- 원문 간 충돌 처리: ① 태그 규칙 — 05 §4(2026-10-02)는 "소문자·앞뒤 공백 제거·중복 제거, 각 1~30자"만 적었으나 22(2026-10-04·10-06)의 정규화(NFKC, 띄어쓰기 → 하이픈, 허용 문자 외 거부, 금칙어)가 더 최근이므로 → specs/008-tag 기준을 따른다. ② 빈 임시글 정리 — 01 결정 기록(만든 지 24시간 + 제목·본문 빈 글)보다 04 §2-5(마지막 수정 후 24시간 + 서버 쪽 임시 보관분 없음 조건 추가)가 세부 규칙이므로 04를 따른다(충돌이 아니라 구체화).

- **브라우저 저장** ([04 §2-2](../../docs/04-draft-and-image.md)): IndexedDB(예: localforage) 키 `draft:{memberId}:{postId}` = `{ title, contentMd, baseVersion, dirty, pendingImages, updatedAt }`, 백업 `draft-backup:{memberId}:{postId}` 7일, 로그아웃 시 `draft:{memberId}:*`·`draft-backup:{memberId}:*` 삭제. `visibilitychange`·`pagehide`(fetch keepalive)·`beforeunload`. 비교는 `jsdiff`.
- **Redis** ([04 §2-3·§2-4](../../docs/04-draft-and-image.md), [05 §6·§7](../../docs/05-publish.md)): `autosave:post:{postId}` Hash(memberId, title, contentMd, version, savedAt) TTL 24h, `autosave:dirty` Set. 버전 확인 + 저장은 Lua 스크립트 하나(키가 없으면 DB `edit_version` 기준). 발행 후 삭제는 "버전 ≤ 발행 때 확인한 버전"일 때만 지우는 Lua. 발행 멱등 키 `idem:publish:{memberId}:{key}` = `{hash, IN_PROGRESS | 응답}` `SET NX EX 600`. 운영 설정 AOF `appendfsync everysec`, `maxmemory-policy noeviction`, 장애 시 Circuit Breaker로 DB 직접 저장 ([02 §2·§2-1](../../docs/02-architecture.md)).
- **스케줄러**: 1분마다 dirty → DB 반영(임시글은 `post` `WHERE status='DRAFT' AND edit_version < :version`, 발행 글은 `post_draft` UPSERT `WHERE post_draft.edit_version < EXCLUDED.edit_version`), Redis 키는 지우지 않음. 매일 새벽 빈 임시글 정리. `@Scheduled` + ShedLock ([04 §2-4·§2-5](../../docs/04-draft-and-image.md)).
- **API** ([04 §2-3](../../docs/04-draft-and-image.md), [05 §5](../../docs/05-publish.md), [12 §7-6](../../docs/12-content-sanitize.md)): `PUT /api/posts/{postId}/autosave {title, contentMd, baseVersion}` → 200 `{version}` / 409 `VERSION_CONFLICT`(`details.server = {title, contentMd, version, savedAt}`) / 404 / 429(`Retry-After`) / 413. `POST /api/posts/{postId}/publish` + 헤더 `Idempotency-Key`(UUID) `{title, contentMd, tags, visibility, baseVersion}` → 200 `{url, publishedAt, firstPublicAt, editedAt, version}` / 400 / 404 / 409 `VERSION_CONFLICT` / 409 `IN_PROGRESS` / 422 `IDEMPOTENCY_KEY_REUSED`. `POST /api/markdown/preview {contentMd}` → `{html}`. 오류 코드 `TITLE_REQUIRED`·`TITLE_TOO_LONG`·`CONTENT_REQUIRED`·`CONTENT_TOO_LONG`·`TOO_MANY_TAGS`·`INVALID_TAG`·`INVALID_VISIBILITY`·`PENDING_IMAGES`·`CONTENT_TOO_COMPLEX`, 본문 형식 `{ code, message, errors: [{ field, code, message }], details }`(O8).
