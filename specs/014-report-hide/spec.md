## User Scenarios & Testing *(mandatory)*

### User Story 1 - 문제 있는 글·댓글 신고하기 (Priority: P1)

이메일 인증을 마친 회원이 남의 글이나 댓글에서 [신고]를 누르고 사유(스팸·광고 / 욕설·혐오 / 음란·선정 / 개인정보 노출 / 저작권 침해 / 기타)를 골라 접수한다. 같은 대상을 다시 신고해도 한 건으로 남고, 작성자는 누가 신고했는지 알 수 없다.

**Why this priority**: 운영자가 개입할 근거가 되는 입력 경로다. 신고가 없으면 관리자 처리(US2)도 시작되지 않는다.

**Independent Test**: 인증 회원·인증 전 회원·비회원·작성자 본인으로 같은 공개 글을 신고해 각각 접수·인증 안내·로그인 안내·거부가 나오는지, 같은 회원이 두 번 신고해도 대기 중 신고가 1건인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 인증 회원이 남의 공개 글을 볼 때, **When** 사유 "스팸·광고"로 신고하면, **Then** "신고가 접수됐어요. 검토 후 처리할게요"가 보이고 신고가 대기 상태로 접수된다 (43 완료 기준 1).
2. **Given** 같은 회원이 이미 신고해 대기 중인 대상, **When** 다시 신고하면, **Then** 새 신고를 만들지 않고 성공으로 응답하며 신고는 1건 그대로다 (43 완료 기준 1, 42 §8).
3. **Given** 사유 "기타"를 고르고 설명을 비웠을 때, **When** 신고하면, **Then** 설명이 필요하다는 오류로 거부된다 (H-2).
4. **Given** 자기 글·댓글, **When** 신고를 요청하면, **Then** 자기 것은 신고할 수 없다는 오류로 거부된다. 화면에서는 작성자에게 [신고] 버튼이 보이지 않는다 (43 완료 기준 2, 42 §11).
5. **Given** 비회원 또는 이메일 인증 전 회원, **When** [신고]를 누르면, **Then** 로그인 또는 이메일 인증 안내를 받고 신고는 접수되지 않는다 (42 P-6, 2026-10-07 회의 H6).
6. **Given** 비공개·휴지통·숨김 상태라 내가 볼 수 없는 대상, **When** 신고를 요청하면, **Then** 없는 대상과 같은 404 응답을 받는다 (43 §2, 42 §3 ③).
7. **Given** 한 회원이 1분 안에 5건을 신고했을 때, **When** 6번째 신고를 하면, **Then** 요청이 거부된다 (H-13).

### User Story 2 - 관리자가 쌓인 신고를 한 번에 판단하고 숨기기 (Priority: P1)

관리자는 신고 관리 화면에서 대상별로 묶인 대기 신고를 보고, 신고 시점의 스냅샷만으로 판단해 "숨기기(사유)" 또는 "문제없음(반려)"을 고른다. 그 대상의 대기 신고는 모두 같은 결과로 닫히고, 신고자마다 처리 결과가, 숨긴 경우 작성자에게 숨김 사유가 알림으로 간다.

**Why this priority**: 신고 기능의 목적(콘텐츠를 실제로 내리는 것)을 완성하는 흐름이다. 자동 숨김은 없으므로 이 흐름이 유일한 조치 수단이다(H-4).

**Independent Test**: 같은 글에 회원 3명이 신고한 뒤 관리자가 숨기기를 처리해, 대기 신고 3건이 모두 닫히고 신고자 알림 3개·작성자 알림 1개가 생기며, 작성자 외 모든 사람에게 그 글이 비공개 글과 똑같이 사라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 일반 회원, **When** 신고 관리 화면 주소로 가면, **Then** 없는 페이지(404)가 보인다. 비회원이면 로그인 화면(401)으로 간다 (43 완료 기준 3, 42 P-10).
2. **Given** 신고 뒤 작성자가 글을 비공개로 바꿨을 때, **When** 관리자가 처리 화면을 열면, **Then** 신고 시점의 스냅샷과 "현재: 비공개" 상태만 보이고 현재 원문은 열어 볼 수 없다 (43 완료 기준 4, H-5).
3. **Given** 한 글에 대기 신고 7건, **When** 관리자가 "숨기기, 사유 스팸·광고"로 처리하면, **Then** 7건이 모두 같은 결과로 닫히고 처리한 관리자와 시각이 기록된다 (43 완료 기준 7, H-3).
4. **Given** 위 처리 직후, **When** 결과를 확인하면, **Then** 신고자 7명에게 "조치했어요" 처리 결과 알림이, 작성자에게 "운영 정책에 따라 숨겨졌어요 (사유: 스팸·광고)" 알림이 하나 가고, 작성자 쪽 정보에는 신고자가 드러나지 않는다 (43 완료 기준 10·11, H-9·H-10).
5. **Given** 관리자가 "문제없음"으로 처리하면, **When** 결과를 확인하면, **Then** 대기 신고가 모두 반려로 닫히고 신고자들에게 "운영 정책 위반은 아니었어요" 알림이 가며 대상은 그대로 보인다.
6. **Given** 숨겨진 글, **When** 작성자 외 사람이 상세·홈·블로그·태그·검색·트렌딩을 보면, **Then** 비공개 글과 똑같이 404이고 어떤 목록·글 수에도 나오지 않는다 (43 완료 기준 5, C-POST-4와 같은 규칙).
7. **Given** 숨겨진 글, **When** 작성자가 상세를 보면, **Then** "운영 정책에 따라 숨겨진 글이에요 (사유: 스팸·광고). 다른 사람에게는 보이지 않아요"와 함께 보이고, 내 글 관리에는 [숨김] 배지가 붙는다.
8. **Given** 관리자, **When** 남의 글·댓글 내용을 수정하거나 삭제하려 하면, **Then** 거부된다 (43 완료 기준 9, 42 P-11).

### User Story 3 - 숨긴 댓글 표시 (Priority: P2)

관리자가 댓글을 숨기면, 다른 사람(글 주인 포함)에게는 작성자 정보 없이 "운영 정책에 따라 숨겨진 댓글이에요"가, 댓글 작성자 본인에게는 원문과 "숨겨졌어요 (나만 보여요)"가 보인다. 답글 흐름은 유지된다.

**Why this priority**: 댓글 숨김은 글 숨김과 같은 처리 흐름(US2)을 쓰고, 표시 규칙만 다르다.

**Independent Test**: 답글이 달린 댓글을 숨긴 뒤 다른 회원·글 주인·댓글 작성자로 각각 보고, 문구·버튼·댓글 수가 규칙대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 숨긴 댓글, **When** 다른 회원이나 글 주인이 보면, **Then** "운영 정책에 따라 숨겨진 댓글이에요"만 보이고 그 아래 답글은 그대로 보인다 (43 완료 기준 6, H-7).
2. **Given** 숨긴 댓글, **When** 댓글 작성자가 보면, **Then** 원문과 "숨겨졌어요 (나만 보여요)"가 보이고 [수정]·[답글]은 없으며 [삭제]는 할 수 있다 (21 §9).
3. **Given** 댓글이 숨겨지면, **When** 글의 댓글 수를 보면, **Then** 1 줄어든다. 해제하면 다시 늘어난다 (21 CM-11).

### User Story 4 - 숨김 해제와 원래대로 돌아오기 (Priority: P2)

관리자가 처리됨 탭에서 숨긴 글·댓글의 숨김을 해제하면, 좋아요·댓글·목록 위치가 숨기기 전과 똑같이 돌아온다. 해제는 알림을 보내지 않는다.

**Why this priority**: 잘못된 조치를 되돌릴 수 있어야 하지만, 숨김(US2)이 먼저 있어야 한다.

**Independent Test**: 좋아요 12개·댓글 3개가 있는 글을 숨겼다가 해제해, 좋아요·댓글 수와 홈 목록 위치가 처음과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 좋아요 12개인 글을 숨겼을 때, **When** 숨긴 동안 확인하면, **Then** 좋아요·댓글 행은 지워지지 않고 함께 가려진다 (43 완료 기준 12).
2. **Given** 그 글, **When** 관리자가 숨김을 해제하면, **Then** 좋아요 수 12, 댓글이 그대로 보이고 홈 목록의 원래 위치(최초 공개 시각 기준)로 돌아온다.
3. **Given** 숨김 해제, **When** 작성자의 알림을 보면, **Then** 새 알림이 없다 (H-10).
4. **Given** 숨긴 글을 작성자가 수정해 다시 발행했을 때, **When** 결과를 보면, **Then** 숨김은 풀리지 않는다 (43 §4-1).

### User Story 5 - 회원 정지 (Priority: P3)

관리자는 신고 처리 화면이나 회원 화면에서 회원을 1일·7일·30일·영구로 정지하고 사유를 남긴다. 정지되는 순간 그 회원은 모든 기기에서 로그아웃되고, 기간 동안 로그인할 수 없다. 기간이 지나면 다음 로그인 때 자동으로 풀린다.

**Why this priority**: 반복 위반에 단계적으로 대응하는 수단이지만, 콘텐츠 숨김만으로도 1차 운영은 가능하다.

**Independent Test**: 회원을 7일 정지해 기존 세션이 즉시 끊기고 로그인이 거부되며 안내 문구가 보이는지, 기한을 지난 시점에 로그인하면 자동 해제되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 중인 회원, **When** 관리자가 7일 정지(사유 입력)하면, **Then** 그 회원의 모든 기기 세션이 즉시 끊긴다 (43 완료 기준 8, 42 P-7).
2. **Given** 정지된 회원, **When** 로그인하면, **Then** 비밀번호가 맞아도 거부되고 "정지된 계정이에요 (11월 1일 14:00까지). 사유: 스팸·광고"가 보인다. 영구 정지는 기한 없이 안내된다 (43 §6, 07 §6).
3. **Given** 정지 기한이 지난 회원, **When** 로그인하면, **Then** 정지가 자동으로 풀리고 로그인된다 (배치 없이) (43 완료 기준 8).
4. **Given** 정지된 회원의 글·댓글, **When** 다른 사람이 보면, **Then** 그대로 보인다 (정지와 숨김은 별개) (42 P-7).
5. **Given** 관리자, **When** 다른 관리자를 정지하려 하면, **Then** 거부된다 (H-12).
6. **Given** 사유를 비웠을 때, **When** 정지하려 하면, **Then** 거부된다 (H-8).

### Edge Cases

- 신고 대기 중 대상 글이 휴지통을 거쳐 완전 삭제되면 그 사건은 "대상 없음"으로 자동 종료되고(처리 시각 기록, 처리 관리자 없음), 알림·이벤트는 생기지 않는다 (13 §2-5, → specs/006-manage-delete).
- 신고 대기 중 작성자가 탈퇴를 신청하면 신고는 대기를 유지하고, 30일 뒤 익명 처리 때 그 회원 콘텐츠의 대기 사건이 "대상 없음"으로 닫힌다 (→ specs/015-withdraw). 이 경우 스냅샷은 탈퇴 신청부터 최대 약 60일 남는다 (2026-10-07 결정).
- 신고자가 탈퇴하면 신고 기록은 익명 처리된 회원을 그대로 가리키고, 그 신고의 설명은 30일 뒤 비워진다 (13 §3-3 6-3).
- 처리된 뒤 같은 대상을 다시 신고하면 새 사건으로 접수된다 (2026-10-07 회의 E4).
- 처리 화면에서 대상이 이미 숨김·휴지통·작성자 탈퇴 상태이면 현재 상태로 표시되고, 대상이 사라졌으면 "대상 없음"으로 자동 종료된다 (43 §3).
- 숨긴 댓글은 답글 유무와 관계없이 항상 자리가 남는다(해제할 수 있어야 하므로). 삭제된 댓글("삭제된 댓글이에요")·탈퇴한 사용자의 댓글("탈퇴한 사용자의 댓글이에요")과 문구가 다르다 (43 §4-2).
- 숨긴 댓글로 생긴 알림은 지워진다 (21 §9, → specs/011-notification).
- 숨김 알림을 받은 뒤 숨김이 해제됐으면 그 알림은 사유 없이 "…숨겨졌었어요 (지금은 다시 보여요)"로 보인다 (25, → specs/011-notification).
- 신고 횟수 저장소가 멈춘 동안에는 1분 5건·하루 50건 제한 없이 통과한다 (02 §2-1 H8).
- 탈퇴 유예 중인 회원은 정지할 수 없다 (13 §3-2). 정지 중 회원의 탈퇴 경로는 specs/015-withdraw의 미결 사항을 따른다.
- 정지 회원은 비밀번호 재설정(로그인 전 기능)은 할 수 있다 (42 §9).

## Requirements *(mandatory)*

### Functional Requirements

**신고하기 (H-1, H-2, H-9, H-13, 43 §2)**

- **FR-001**: System MUST 글과 댓글을 신고 대상으로 지원해야 한다. 회원(닉네임·소개) 신고는 범위 밖이다 (H-1).
- **FR-002**: System MUST 신고 사유로 스팸·광고 / 욕설·혐오 / 음란·선정 / 개인정보 노출 / 저작권 침해 / 기타 중 하나를 받고, 기타일 때만 설명(최대 200자)을 필수로 받아야 한다 (H-2).
- **FR-003**: System MUST 신고를 로그인하고 이메일 인증을 마친 회원(관리자 포함)에게만 허용해야 한다. 비회원은 로그인 필요(401), 인증 전 회원은 이메일 인증 필요(403)로 거부한다 (42 P-6·§8, C-AUTH-1).
- **FR-004**: System MUST [신고] 버튼을 작성자 본인에게는 보이지 않게 하고, 비회원·이메일 인증 전 회원에게는 보이되 누르면 로그인 또는 이메일 인증 안내를 보여주어야 한다 (42 §11, 2026-10-07 회의 H6).
- **FR-005**: System MUST 자기 글·댓글에 대한 신고를 업무 규칙 위반(400)으로 거부해야 한다 (42 §8, 2026-10-07 회의 E8).
- **FR-006**: System MUST 신고자가 볼 수 없는 대상(비공개·휴지통·숨김·작성자 탈퇴 유예)과 없는 대상의 신고에 똑같이 404로 응답해야 한다 (43 §2, 42 §3, 01 §3 원칙 3).
- **FR-007**: System MUST 한 대상에 처리 대기 중인 신고 사건을 하나만 두고, 같은 회원이 같은 대기 사건에 다시 신고하면 새로 만들지 않고 성공으로 응답해야 한다. 사건이 처리된 뒤의 신고는 새 사건으로 접수한다 (H-3, 42 §8, 2026-10-07 회의 E1·E4).
- **FR-008**: System MUST 대상에 대한 첫 신고 때 판단용 스냅샷을 남겨야 한다: 글은 제목 + 본문 원문 앞 2,000자, 댓글은 내용 전체, 그리고 대상 작성자 (H-5, 43 §2).
- **FR-009**: System MUST 신고를 회원당 1분 5건, 하루 50건으로 제한하고 넘으면 거부해야 한다. 횟수 저장소 장애 동안에는 통과시킨다 (H-13, 02 §2-1 H8).
- **FR-010**: System MUST 접수 후 "신고가 접수됐어요. 검토 후 처리할게요"를 보여주고, 신고 접수로는 알림을 만들지 않아야 한다 (43 §2).
- **FR-011**: System MUST 작성자가 누가 신고했는지 어떤 화면·알림으로도 알 수 없게 해야 한다 (H-9, 43 완료 기준 10).

**관리자 처리 (H-3~H-5, H-12, 43 §3)**

- **FR-012**: System MUST 관리자 기능 화면을 관리자만 열 수 있게 하고, 비회원에게는 로그인 필요(있는 주소·없는 주소 모두), 로그인한 일반 회원에게는 404로 응답해야 한다 (42 P-10, 43 완료 기준 3).
- **FR-013**: System MUST 신고 관리 화면에 [대기]·[처리됨] 탭을 두고, 대기 탭은 대기 신고가 있는 대상을 대상별로 묶어 신고 수 많은 순 → 최근 신고 순으로 보여주어야 한다. 각 항목에는 대상 종류, 스냅샷 제목(댓글은 내용 일부), 작성자 블로그 주소, 신고 수와 사유별 수, 최근 신고 시각이 보인다 (43 §3).
- **FR-014**: System MUST 처리 화면에 스냅샷, 대상의 현재 상태(공개 / 비공개 / 휴지통 / 이미 숨김 / 작성자 탈퇴), 신고 수·사유별 수·기타 설명, 작성자 정보(가입일, 이전에 숨겨진 콘텐츠 수, 정지 이력)를 보여주어야 한다 (43 §3).
- **FR-015**: System MUST 관리자가 신고 시점 스냅샷만 볼 수 있게 하고, 현재 비공개·휴지통인 원문은 관리자도 열어 볼 수 없게 해야 한다 (H-5, 06 §2, 43 완료 기준 4).
- **FR-016**: System MUST 처리를 "숨기기(사유 선택)" 또는 "문제없음(반려)" 중 하나로 받고, 그 대상의 대기 신고를 한 번에 모두 같은 결과로 닫으며, 처리한 관리자와 처리 시각을 기록해야 한다 (H-3, 43 완료 기준 7).
- **FR-017**: System MUST 신고 수와 관계없이 자동으로 숨기지 않고, 관리자 처리로만 숨겨야 한다 (H-4).
- **FR-018**: System MUST 관리자에게 글·댓글의 숨김·해제만 허용하고, 내용 수정·삭제는 허용하지 않아야 한다 (42 P-11, 43 완료 기준 9).
- **FR-019**: System MUST 관리자가 자기 글·댓글을 숨기거나, 자기가 신고자인 사건을 처리하거나, 다른 관리자를 정지하는 것을 거부해야 한다 (H-12).
- **FR-020**: System MUST [NEEDS CLARIFICATION: 42 §5-2·§6·§11은 관리자에게 글·댓글의 [숨김]·[숨김 해제] 행동과 버튼을 따로 주지만, 43은 숨김을 신고 처리 화면(대기 사건)에서만, 해제를 처리됨 탭에서만 정의한다. 신고 없이 관리자가 직접 숨길 수 있는지, 그 경우 사건 기록·알림·대기 신고 처리를 어떻게 할지 정해야 한다] 관리자 숨김의 진입 경로를 정해진 방식으로만 제공해야 한다.

**숨김 효과 (H-6, H-7, 43 §4)**

- **FR-021**: System MUST 숨긴 글을 작성자 외 모든 사람(관리자 포함)에게 비공개 글과 똑같이 다뤄야 한다: 상세 404, 홈·블로그·태그·검색·트렌딩·피드·sitemap·글 수에서 제외 (H-6, 06 R-2a, 43 완료 기준 5, → specs/004-visibility-permission). 관리자는 처리 화면의 스냅샷으로만 본다.
- **FR-022**: System MUST 숨긴 글을 작성자 본인에게는 상세에서 "운영 정책에 따라 숨겨진 글이에요 (사유: {사유}). 다른 사람에게는 보이지 않아요" 안내와 함께 보여주고, 내 글 관리에 [숨김] 배지를 붙여야 한다. 작성자 본인이 볼 때도 숨긴 글은 공개 목록에 나오지 않는다 (43 §4-1, 06 R-2a·V-8, → specs/005-post-reading, specs/006-manage-delete).
- **FR-023**: System MUST 숨긴 글의 작성자가 수정·다시 발행·공개 범위 변경·삭제를 계속할 수 있게 하되, 이런 행동으로 숨김이 풀리지 않아야 한다 (43 §4-1).
- **FR-024**: System MUST 숨긴 글의 댓글·좋아요를 지우지 않고 글과 함께 가리며, 좋아요 수를 그대로 두어야 한다 (43 §4-1, 06 V-7, 43 완료 기준 12).
- **FR-025**: System MUST 숨긴 댓글을 다른 사람(글 주인 포함)에게 작성자 정보 없이 "운영 정책에 따라 숨겨진 댓글이에요"로, 댓글 작성자에게는 원문 + "숨겨졌어요 (나만 보여요)"로 보여주고, 그 답글은 그대로 보여주어야 한다 (H-7, 43 완료 기준 6, → specs/007-comment).
- **FR-026**: System MUST 숨긴 댓글의 수정과 그 댓글에 대한 답글을 막고, 작성자 본인의 삭제는 허용해야 한다. 숨긴 댓글은 답글 유무와 관계없이 자리가 남고 글의 댓글 수에서 빠진다 (H-7, 21 §9·CM-11).

**숨김 해제 (43 §4-3)**

- **FR-027**: System MUST 관리자가 처리됨 탭에서 숨긴 글·댓글의 숨김을 해제할 수 있게 하고, 해제하면 노출·좋아요 수·댓글·목록 위치(최초 공개 시각 기준)가 숨기기 전과 같아지며 댓글 수가 다시 더해져야 한다 (43 §4-1·§4-3, 43 완료 기준 12).

**알림 (H-10, 43 §7)**

- **FR-028**: System MUST 처리 결과를 신고자마다(신고 한 건마다) 알려야 한다: 숨김이면 "조치함", 반려면 "문제없음". 알림에는 대상 내용·작성자를 넣지 않는다 (H-10, → specs/011-notification).
- **FR-029**: System MUST 숨김 시 작성자에게 "운영 정책에 따라 숨겨졌어요 (사유)" 알림을 한 번 보내야 하며, 이 알림·관련 정보에 신고자를 넣지 않아야 한다 (H-10, 43 완료 기준 11).
- **FR-030**: System MUST 숨김 해제, "대상 없음" 자동 종료, 회원 정지에는 알림을 보내지 않아야 한다 (H-10, 43 §7).

**대상 변화·기록 보관 (43 §5, 13 §2-5)**

- **FR-031**: System MUST 신고 대기 중 대상이 비공개로 바뀌어도 신고를 대기로 유지하고, 관리자는 스냅샷으로 판단하게 해야 한다 (43 §5).
- **FR-032**: System MUST 대상 글·댓글이 완전히 지워지면 그 대기 사건을 "대상 없음"으로 자동 종료하고(처리 시각 기록, 처리 관리자 없음), 사건 기록·대상 작성자·스냅샷은 남겨야 한다 (43 §5, 13 §2-5, 2026-10-07 결정 "신고 사건 일자").
- **FR-033**: System MUST 처리(자동 종료 포함)된 지 30일이 지난 사건의 스냅샷과 그 사건 신고들의 설명을 비우되, 사건·상태·사유·처리 일자는 남겨야 한다 (13 §2-5, 2026-10-07 회의 H5).
- **FR-034**: System MUST 작성자 탈퇴 유예 중에는 대기 신고를 유지하고, 신고자가 탈퇴해도 신고 기록은 남겨야 한다. 30일 뒤 처리는 → specs/015-withdraw (43 §5, 13 §3-3 6-3).

**회원 정지 (H-8, 43 §6)**

- **FR-035**: System MUST 관리자가 신고 처리 화면 또는 회원 화면에서 회원을 1일 / 7일 / 30일 / 영구로 정지할 수 있게 하고, 사유(최대 200자)를 필수로 받아야 한다. 숨기기와 함께 또는 따로 할 수 있다 (H-8, 43 §3·§6).
- **FR-036**: System MUST 정지하는 순간 그 회원의 상태를 정지로 바꾸고 모든 기기의 로그인 세션을 직접(사후 알림에 의존하지 않고) 끊어야 한다. 정지 회원의 기존 글·댓글은 그대로 보인다 (42 P-7, 20 §3-5, 43 완료 기준 8).
- **FR-037**: System MUST 정지 회원의 로그인을 거부하고 "정지된 계정이에요 ({종료 시각}까지). 사유: {사유}"(영구면 기한 없이)를 보여주며, 남아 있는 세션의 쓰기 요청은 계정 정지(403)로 거부해야 한다 (43 §6, 07 §6, 02 §5, → specs/001-account-auth).
- **FR-038**: System MUST 정지 기간이 지난 회원이 로그인을 시도하면 그때 정지를 해제(해제 시각 기록, 해제 관리자 없음)하고 로그인시켜야 한다. 별도 일괄 작업은 두지 않는다 (43 §6, 07 §6).
- **FR-039**: Users (관리자) MUST be able to 정지를 수동으로 해제할 수 있어야 하며, 해제한 관리자와 시각이 기록된다 (43 §6, 51 `member_suspension`).
- **FR-040**: System MUST 정지마다 이력(사유, 시작·종료 시각, 정지한 관리자, 해제 시각·해제한 관리자)을 남기고, 회원당 해제되지 않은 정지는 하나만 두어야 한다 (2026-10-07 회의 E3·E5).
- **FR-041**: System MUST 탈퇴 유예 중인 회원은 정지할 수 없게 해야 한다 (13 §3-2).

### Key Entities *(include if feature involves data)*

- **신고 사건**: 한 대상(글 또는 댓글)에 대한 처리 단위. 대상 종류·대상(사라지면 비움)·대상 작성자·신고 시점 스냅샷(제목, 내용 최대 2,000자)·상태(대기 / 숨김 / 반려 / 대상 없음)·처리 관리자·처리 시각·생성 시각. 한 대상에 대기 중 사건은 하나.
- **신고**: 신고자 한 명의 신고. 소속 사건·신고자·사유·설명(기타만 필수)·생성 시각. 한 사건에 같은 신고자는 한 번. 처리 결과 알림은 신고마다 하나.
- **숨김 표시**: 글·댓글마다 숨긴 시각·숨긴 관리자·숨김 사유. 숨김 여부가 공용 노출 조건에 들어간다.
- **회원 정지 이력**: 정지 대상 회원·사유·시작·종료(영구면 없음)·정지 관리자·해제 시각·해제 관리자. 현재 정지 여부는 회원 상태로 본다.
- **회원**: 역할(일반 / 관리자), 상태(활동 / 정지 / 탈퇴 유예).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 숨긴 글이 작성자 외 사람의 상세·목록·검색·트렌딩·태그·글 수에 나타나는 경우가 0건이다.
- **SC-002**: 같은 회원이 같은 대기 대상을 여러 번 신고해도 대기 신고는 1건이다 (동시에 보내도 같다).
- **SC-003**: 관리자 한 번의 처리로 그 대상의 대기 신고가 100% 닫히고, 신고자 수만큼의 처리 결과 알림과 작성자 알림 1개가 생긴다.
- **SC-004**: 작성자에게 전달되는 화면·알림·정보에서 신고자를 알아낼 수 있는 경우가 0건이다.
- **SC-005**: 정지 처리 후 그 회원의 다음 요청부터 로그인 상태가 아니며, 정지 기간 내 로그인 성공이 0건이다.
- **SC-006**: 숨김 해제 후 좋아요 수·댓글 수·목록 위치가 숨기기 전과 100% 같다.
- **SC-007**: 일반 회원이 관리자 화면 존재를 확인할 수 있는 응답 차이가 0건이다 (있는 주소·없는 주소 모두 같은 응답).
- **SC-008**: 처리된 지 30일이 지난 사건에 스냅샷·신고 설명이 남아 있는 경우가 0건이다.

## Assumptions

- **Tier C 기능이다** (01 §2-3 "신고·관리자 숨김", 강 P2 / 나 MUST Step 8 / 김 3차). 원문 43은 "초안 (항목 확인 중)" 상태이며, 2026-10-07 회의(E1·E3~E8·H1·H5·H6)로 바뀐 부분은 회의 결정을 따랐다.
- 신고 저장 구조는 43 원문의 단일 신고 표가 아니라 2026-10-07 회의 E1로 확정된 "신고 사건 + 신고" 구조를, 정지는 회원 컬럼이 아니라 E3의 "정지 이력" 구조를 따른다 (51).
- 스냅샷 항목은 51 기준(제목·내용·대상 작성자)이다. 43 §2가 적은 "블로그 주소·공개 범위" 스냅샷은 51에 칸이 없어, 처리 화면의 블로그 주소·현재 상태는 처리할 때 조회한다고 본다.
- 관리자 지정·해제 방법은 원문에 없어 범위 밖으로 둔다(운영자가 직접 지정한다고 본다).
- 숨김을 해제해도 사건의 처리 결과(숨김)는 기록으로 남는다고 본다. 원문은 해제 시 사건 상태 변경을 정하지 않았다.
- 신고 횟수 제한(1분 5건·하루 50건)은 성공·중복 응답을 가리지 않고 신고 요청 수로 센다고 본다.
- **개인 확장(범위 밖)**: 회원 신고(H-1), 이의 제기(H-11), 관리자 알림, 글 주인의 댓글 삭제(42 P-8).
- 공용 노출 조건은 specs/004-visibility-permission, 글 상세·목록 표시는 specs/005-post-reading, 내 글 관리 배지·완전 삭제는 specs/006-manage-delete, 댓글 표시·댓글 수는 specs/007-comment, 알림 종류·문구는 specs/011-notification, 로그인 거부·세션은 specs/001-account-auth, 탈퇴 30일 처리는 specs/015-withdraw가 담당한다.
- 트렌딩 점수에서 숨긴 댓글을 뺄지는 specs/012-trending-search의 미결 사항이다.

## Implementation Notes (for /speckit-plan)

- 스키마(통합 V1, [51 §2·§3](../../docs/51-erd-unified.md)): `report_case`(`target_type` POST|COMMENT, `post_id`·`comment_id` FK `ON DELETE SET NULL`, `target_author_id`, `snapshot_title` varchar(100), `snapshot_content` varchar(2000), `status` PENDING|HIDDEN|REJECTED|CLOSED_NO_TARGET, `handled_by`, `handled_at`, `created_at`), `report`(`case_id`, `reporter_id`, `reason` SPAM|ABUSE|SEXUAL|PRIVACY|COPYRIGHT|OTHER, `detail` varchar(200), `created_at`, `UNIQUE (case_id, reporter_id)`), 대기 사건 하나는 부분 UNIQUE `uq_report_case_open_post`·`uq_report_case_open_comment`(E4). `post`·`comment`의 `hidden_at`·`hidden_by`·`hidden_reason`. `member_suspension`(`reason`, `started_at`, `ends_at`, `suspended_by`, `lifted_at`, `lifted_by`) + `member.status = 'SUSPENDED'`. 43 원문 ERD(단일 `report`, `UQ(reporter_id, target_type, target_id)`, `member.suspended_until`·`suspended_reason`, `report.closed_at`)는 대체됐다.
- 자기 신고 금지·기타 설명 필수는 Service 검사 (`ck_report_self` 상실 E8, `ck_report_detail`은 NULL 통과 — 51 "원문 유지와 표기 판단"). 회원당 열린 정지 하나도 Service 규칙(E5).
- 공용 조건: [06 §7 R-2a](../../docs/06-visibility.md) `hidden_at IS NULL`(H1), `canRead` 작성자 예외. 인덱스 `ix_post_feed`·`ix_post_blog` WHERE에 `hidden_at IS NULL` 반영됨.
- API: [43 §2](../../docs/43-report-hide.md) `POST /api/reports { targetType, targetId, reason, detail }` → 200(중복 포함) / 400 `CANNOT_REPORT_OWN`·`REPORT_DETAIL_REQUIRED` / 401 / 403 `EMAIL_NOT_VERIFIED` / 404 / 429. 화면 `/admin/reports`, `/admin/members/{handle}`(`/admin/**` 전체 로그인 필요, 일반 회원 404 — Spring Security 설정, 42 P-10). 중복은 `ON CONFLICT DO NOTHING`.
- 요청 제한: Redis 카운터 1분 5건·하루 50건, Redis 장애 시 통과([02 §2-1](../../docs/02-architecture.md)).
- 이벤트([20 §3-5](../../docs/20-domain-events.md), 커밋 후 발행): `ReportResolved(reportId, reporterId, targetType, targetId, result, resolvedAt)` 신고 한 건마다(`HIDDEN`→`ACTION_TAKEN`, `REJECTED`→`NO_VIOLATION`, `CLOSED_NO_TARGET`은 이벤트 없음), `ContentHidden(targetType, targetId, ownerId, postId, hiddenAt)`(신고자 ID 없음), `ContentUnhidden(…, unhiddenAt)`(알림 없음), `MemberSuspended(memberId, until, suspendedAt)` — 43 §7의 `reason`은 20 EV-3에 따라 빠졌다. 세션 삭제는 이벤트가 아니라 정지 Service가 직접.
- 알림 종류 `REPORT_RESOLVED`(`report_id`, `result`), `CONTENT_HIDDEN`(사유는 표시할 때 `hidden_reason`에서 읽음) — [25](../../docs/25-notification.md). `notification.report_id` → `report(id)` `ON DELETE SET NULL`(`fk_notification_report`, 회의 O2).
- 대상 삭제·스냅샷 비우기: [13 §2-5](../../docs/13-delete-withdraw.md) — 글 완전 삭제 0단계에서 `report_case` PENDING → `CLOSED_NO_TARGET`(`handled_at = now()`, `handled_by = NULL`), 매일 새벽 ShedLock 배치로 `handled_at` 30일 지난 사건의 `snapshot_*`·`report.detail` NULL(전용 인덱스 없음).
- 정지 로그인 처리: [07 §6](../../docs/07-auth.md) — 열린 정지(`lifted_at IS NULL`)의 `ends_at`이 지났으면 `lifted_at` 기록 + `status = ACTIVE`; 정지 회원의 남은 세션 쓰기 요청 403 `ACCOUNT_SUSPENDED`(H7). 유예 회원 정지 불가는 `ck_member_withdrawn`.
