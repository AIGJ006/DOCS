## Clarifications

### Session 2026-10-08

- Q: 트렌딩 "남의 댓글 작성자 수"에서 관리자가 숨긴 댓글을 뺄까? → A: 뺀다(`hidden_at IS NULL`). 글에 보이는 댓글 수와 기준이 같다 (FR-005) (민서 확정 2026-10-08)
- Q: 검색 엔진용 sitemap을 012가 맡을까? → A: 012가 맡는다. 요청 때마다 공용 노출 조건(`VisibilityFilter`)으로 공개 글·블로그 주소를 만들어 삭제·비공개 글이 즉시 빠진다 (FR-040 신설) (민서 확정 2026-10-08)
- Q: 사람 검색어도 띄어쓰기로 단어를 나눌까? → A: 나누지 않는다. 띄어쓰기와 맨 앞 `@`를 지운 한 덩어리(2글자 이상)로 닉네임·블로그 주소에서 부분 일치로 찾는다 (FR-036) (민서 확정 2026-10-08)
- Q: 검색 결과의 주변 문장을 Markdown 원문 그대로 보여 줄까? → A: 원문 그대로. 먼저 HTML 이스케이프하고 그다음 검색어를 강조한다 (FR-023·FR-033·FR-034) (민서 확정 2026-10-08)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 키워드로 공개 글 찾기 (Priority: P1)

방문자(비회원 포함)가 검색창에 단어를 입력하면, 공개·발행된 글 가운데 모든 단어가 들어간 글을 목록과 같은 카드로 9개씩 본다. 기본 정렬은 관련도순(제목 → 태그 → 본문 단계)이고, 각 카드에는 검색어가 나온 부분의 앞뒤 문장이 강조되어 보인다.

**Why this priority**: 세 팀원 문서에 모두 있는 기능이고(강 P1, 나 MUST), 원하는 글을 찾는 유일한 수단이다. 비공개 글이 새지 않아야 한다는 C-POST-4 기준을 직접 검증하는 경로이기도 하다.

**Independent Test**: 공개 글·비공개 글·휴지통 글·숨긴 글·탈퇴 신청한 작성자의 글을 섞어 두고 3글자 이상 단어로 검색해, 공개·발행 글만 단계 순서대로 9개씩 나오고 [더 보기]로 넘겨도 중복·누락이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 제목에 "트랜잭션"이 있는 공개 글, 본문에만 있는 공개 글, 같은 단어가 제목에 있는 비공개 글이 있을 때, **When** "트랜잭"으로 검색하면, **Then** 제목에 있는 글이 먼저, 본문에만 있는 글이 그다음에 나오고 비공개 글은 나오지 않는다 (33 완료 기준 1·2·4, C-POST-4).
2. **Given** 검색어가 "롬복"(2글자)일 때, **When** 검색하면, **Then** 제목·태그에 있는 글만 나오고 본문에만 있는 글은 나오지 않으며, 결과 위에 "두 글자 단어는 제목·태그에서만 찾았어요"가 보인다 (33 완료 기준 3).
3. **Given** 검색어가 "트랜잭션 정리 a"일 때, **When** 검색하면, **Then** "a"는 무시되고 "트랜잭션"과 "정리"가 모두 들어간 글만 나온다 (Q-3).
4. **Given** 결과가 9개보다 많을 때, **When** [더 보기]를 연달아 누르면, **Then** 이미 본 글이 다시 나오거나 건너뛰는 글이 없다 (33 완료 기준 5, C-READ-1).
5. **Given** 본문에 `<script>`가 글자로 들어 있는 글이 검색될 때, **When** 결과 카드의 주변 문장을 보면, **Then** 검색어 강조 외의 어떤 HTML도 실행되지 않고 `<script>`는 글자로 보인다 (33 완료 기준 7, C-POST-1).
6. **Given** "100% 할인"·"snake_case"처럼 `%`·`_`가 들어간 검색어일 때, **When** 검색하면, **Then** 그 글자를 그대로 포함한 글만 나온다 (33 완료 기준 6).
7. **Given** 일치하는 글이 없을 때, **When** "롬복"으로 검색하면, **Then** "'롬복'에 대한 글이 없어요"(2글자 안내 포함)가 보인다.

### User Story 2 - 홈에서 요즘 반응이 많은 글 보기 (Priority: P2)

방문자가 홈의 [트렌딩] 탭을 누르면 최근 7일 안에 처음 공개된 글 가운데 반응(좋아요·남의 댓글·조회)이 많은 글을 점수 순으로 9개씩 본다. 순위는 10분마다 갱신되고, 보는 도중 순위가 바뀌어도 보던 순위 그대로 이어서 볼 수 있다.

**Why this priority**: 홈 화면의 두 번째 탭으로, 새로운 독자가 좋은 글을 발견하는 통로다(강 P1, 나 MUST, 김 3차). 검색보다 우선순위가 엇갈려 P2로 둔다.

**Independent Test**: 새 글·하루 된 글·6일 된 글·8일 된 글, 자기 댓글만 많은 글, 조회만 많은 글, 한 작성자의 글 5개, 비공개 글로 순위를 계산해 32 §6의 결과와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 반응을 받은 1시간 된 글과 하루 된 글이 있을 때, **When** 트렌딩을 보면, **Then** 1시간 된 글이 위에 있다 (32 완료 기준 1).
2. **Given** 작성자가 자기 글에 댓글을 20개 달았고 다른 반응이 없을 때, **When** 순위가 갱신되면, **Then** 그 글은 트렌딩에 나오지 않는다 (32 완료 기준 2, T-4·T-5).
3. **Given** 한 작성자의 글 5개가 모두 상위 점수일 때, **When** 트렌딩을 보면, **Then** 그 작성자의 글은 3개까지만 나온다 (32 완료 기준 3).
4. **Given** 8일 전에 처음 공개되어 좋아요가 100개인 글이 있을 때, **When** 트렌딩을 보면, **Then** 그 글은 나오지 않는다 (T-3).
5. **Given** 1페이지를 본 뒤 10분이 지나 순위가 새로 계산됐을 때, **When** [더 보기]를 누르면, **Then** 처음 보던 순위의 다음 글이 이어서 나오고 중복·누락이 없다 (32 완료 기준 5).
6. **Given** 1페이지를 본 뒤 아직 안 본 글 2개가 비공개·휴지통으로 바뀌었을 때, **When** [더 보기]를 누르면, **Then** 그 두 글은 건너뛰고 다음 글로 9개를 채운다 (32 완료 기준 6).
7. **Given** 반응이 있는 글이 하나도 없을 때, **When** 트렌딩 탭을 열면, **Then** "아직 트렌딩 글이 없어요"와 [최신 글 보기]가 보이고, 최신 글로 채워지지 않는다.

### User Story 3 - 사람 찾기와 블로그 안 검색 (Priority: P3)

방문자가 검색 결과의 [사람] 탭에서 닉네임이나 블로그 주소로 회원을 찾고, 어떤 블로그(`/@주소`) 안에서는 그 작성자의 글만 검색한다.

**Why this priority**: 회원 = 블로그 구조라서 나민서 안의 "블로그 검색"이 사람 탭과 같다(Q-1). 블로그 안 검색은 글 검색에 작성자 조건 하나만 더하면 된다(Q-7). 글 검색이 먼저 있어야 의미가 있어 P3로 둔다.

**Independent Test**: 같은 닉네임을 가진 활동 회원과 탈퇴 신청 회원을 두고 사람 검색을 해 활동 회원만, 정확히 일치하는 회원이 먼저 나오는지 확인한다. 블로그 안 검색은 다른 작성자의 같은 단어 글이 섞이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 닉네임이 "김민서"인 활동 회원과 탈퇴 신청한 회원이 있을 때, **When** 사람 탭에서 "김민서"를 검색하면, **Then** 활동 회원만 나온다.
2. **Given** 블로그 주소가 정확히 "kim7550"인 회원과 부분만 일치하는 회원이 있을 때, **When** "kim7550"을 검색하면, **Then** 정확히 일치하는 회원이 먼저 나오고 결과는 최대 20명이다.
3. **Given** 두 작성자가 같은 단어로 글을 썼을 때, **When** 한 작성자의 블로그 안에서 그 단어로 검색하면, **Then** 그 작성자의 공개 글만 나온다.
4. **Given** 검색창에 `#spring` 한 단어를 입력했을 때, **When** 검색하면, **Then** 태그 `spring`의 글 목록 페이지로 이동한다 (22 T-11, → specs/008-tag).

### Edge Cases

- 검색어가 공백·1글자 단어로만 이루어져 남는 단어가 없으면 "두 글자 이상 입력해 주세요"를 보여주고 검색하지 않는다.
- 검색어가 50자를 넘거나 단어가 6개 이상이면 50자로 자르고 앞의 5단어만 쓴다.
- `#` 뒤에 띄어쓰기가 있거나 `#`만 있거나 태그 규칙에 맞지 않으면 보통 검색으로 처리한다 (22 T-11).
- 같은 방문자가 1분에 30번을 넘게 검색하면 요청이 거부되고 잠시 후 다시 시도하라는 안내를 받는다. 요청 횟수 저장소가 멈춘 동안에는 제한 없이 통과한다 (02 §2-1 H8).
- 트렌딩을 보는 도중 30분이 지나 보던 순위가 사라지면 "순위가 새로 바뀌었어요" 안내 후 최신 순위를 처음부터 보여준다.
- 이미 화면에 있는 트렌딩·검색 카드의 글이 그 뒤 비공개·삭제되면 카드는 남고, 누르면 없는 글과 같은 404 화면이 나온다 (10 §4-3과 같음).
- 트렌딩 순위 저장소가 멈추면 즉시 계산한 첫 9개를 보여주고 [더 보기]는 없다 (임시 대체 경로, T-9).
- 트렌딩은 최대 100개(9개씩 12번)까지이며, 그 뒤에는 [더 보기]가 없다.
- 관리자가 숨긴 글, 친구 공개 글은 트렌딩·검색 어디에도 나오지 않는다 (공용 조건, → specs/004-visibility-permission, specs/014-report-hide).
- 숨겨진 댓글은 트렌딩의 "남의 댓글 작성자 수"에 들어가지 않는다 (FR-005).

## Requirements *(mandatory)*

### Functional Requirements

**트렌딩 (32)**

- **FR-001**: System MUST 홈 상단에 `[최신] [트렌딩]` 탭을 제공하고 기본 탭은 최신이며, 트렌딩 탭은 자기 주소로 직접 열 수 있어야 한다 (T-1, 32 §5).
- **FR-002**: System MUST 트렌딩 글을 전체 글 목록과 같은 카드·9개씩·[더 보기]로 보여주고, 순위 숫자는 표시하지 않아야 한다 (T-1, 32 §5, → specs/005-post-reading).
- **FR-003**: System MUST 트렌딩 대상을 공용 노출 조건(공개·발행, 휴지통 아님, 관리자 숨김 아님, 작성자 탈퇴 신청 아님)을 만족하고 **최초 공개 시각이 7일 이내**인 글로 한정해야 한다 (T-3, 32 §3-1, 06 R-2a → specs/004-visibility-permission).
- **FR-004**: System MUST 트렌딩 점수를 `(3 × 좋아요 수 + 2 × 남의 댓글 작성자 수 + 0.1 × 조회 수) ÷ (최초 공개 후 경과 시간(시간 단위) + 2)^1.5`로 계산해야 한다. 좋아요·조회 수는 각 기능이 중복·자기 반응을 걸러 낸 누적값을 쓴다 (T-2, → specs/009-like-view).
- **FR-005**: System MUST "남의 댓글 작성자 수"를 글 작성자를 뺀 서로 다른 댓글 작성자 수로 세고 삭제된 댓글과 관리자가 숨긴 댓글은 제외해야 한다. 같은 사람이 여러 번 댓글을 달아도 1명이다. 글에 보이는 댓글 수(21 CM-11)와 같은 기준이다 (T-4, 43 "다른 담당자와 맞출 것", Clarifications 2026-10-08)
- **FR-006**: System MUST 좋아요 1개 이상 **또는** 남의 댓글 작성자 1명 이상인 글만 트렌딩에 넣어야 한다. 조회만 많은 글, 자기 댓글만 있는 글은 나오지 않는다 (T-5).
- **FR-007**: System MUST 한 작성자의 글을 트렌딩에 최대 3개까지만 넣어야 한다. 작성자 안에서도 점수 → 최초 공개 최신 → 글 번호 큰 순으로 고른다 (T-6).
- **FR-008**: System MUST 트렌딩을 점수 높은 순으로 정렬하고, 동점이면 최초 공개 시각 최신 → 글 번호 큰 순으로 정렬해야 한다 (32 §2, 나민서 D-10).
- **FR-009**: System MUST 순위를 **10분마다** 미리 계산해 상위 **100개**를 보관하고, 사용자의 요청 때 전체 순위를 다시 계산하지 않아야 한다 (T-7). 계산은 여러 서버 중 한 곳에서만 실행된다.
- **FR-010**: System MUST [더 보기]가 사용자가 처음 받은 순위 목록(스냅샷)을 기준으로 이어지게 해서, 보는 도중 새 순위가 생겨도 중복·누락이 없어야 한다 (T-8).
- **FR-011**: System MUST 각 순위 목록을 만든 뒤 **30분** 동안 보관하고, 보관이 끝난 순위로 [더 보기]를 요청하면 "순위가 새로 바뀌었어요"를 안내하고 최신 순위를 처음부터 보여주어야 한다 (32 §4).
- **FR-012**: System MUST [더 보기] 때 그 사이 볼 수 없게 된 글(비공개·휴지통·숨김·작성자 탈퇴 신청)은 건너뛰고 다음 글로 채워 9개를 맞춰야 한다 (32 §4 ③).
- **FR-013**: System MUST 순위 보관소를 쓸 수 없을 때 즉시 계산한 첫 9개를 보여주고 [더 보기]는 제공하지 않아, 트렌딩 탭이 비지 않게 해야 한다 (T-9, 32 완료 기준 7, 02 §2-1).
- **FR-014**: System MUST 탭 아래에 "최근 7일 동안 반응이 많은 글 · 10분마다 갱신"을 표시해야 한다 (32 §5).
- **FR-015**: System MUST 트렌딩 글이 없으면 "아직 트렌딩 글이 없어요"와 [최신 글 보기]를 보여주고, 최신 글로 채우지 않아야 한다 (32 §5).
- **FR-016**: System MUST 비회원도 트렌딩을 볼 수 있게 하고, 뒤로 가기 때 불러온 카드·이어보기 위치·스크롤을 30분 동안 복원해야 한다 (32 §5, 10 §4-4).

**검색 — 검색어 처리 (33 §2)**

- **FR-017**: System MUST 검색 결과에 **글**(기본)과 **사람**(닉네임·블로그 주소) 두 탭을 제공해야 한다 (Q-1).
- **FR-018**: System MUST 검색어를 유니코드 정규화(NFC)하고 앞뒤 공백을 지우고 50자로 자른 뒤 띄어쓰기로 단어를 나누며, 1글자 단어는 버리고 최대 5단어까지만 써야 한다 (Q-2, Q-3, 33 §2).
- **FR-019**: System MUST 2글자 단어는 제목·태그에서만, 3글자 이상 단어는 제목·태그·본문에서 찾아야 한다 (Q-2).
- **FR-020**: System MUST 모든 단어가 (각 단어가 찾을 수 있는 곳 어딘가에) 들어 있는 글만 결과로 내야 한다 (AND, Q-3).
- **FR-021**: System MUST 대소문자를 무시하고, `%`·`_`·`\` 같은 특수문자는 와일드카드가 아니라 글자 그대로 찾아야 한다 (33 §2).
- **FR-022**: System MUST 태그는 검색어를 소문자로 바꿔 태그 이름과 부분 일치로 비교해야 한다 (33 §2, → specs/008-tag 정규화 규칙, C-TAG-1).
- **FR-023**: System MUST 본문 검색은 작성자가 쓴 원문 기준으로 하며 코드 블록 안의 글자도 찾아야 한다 (33 §2).
- **FR-024**: System MUST 남는 단어가 없으면 "두 글자 이상 입력해 주세요"를 보여주고, 2글자 단어가 하나라도 있으면 결과 위에 "두 글자 단어는 제목·태그에서만 찾았어요"를 보여주어야 한다 (33 §2).
- **FR-025**: System MUST 검색어 전체가 `#`으로 시작하는 한 단어이고 태그 규칙을 통과하면 그 태그의 글 목록 페이지로 이동시켜야 한다. 그 밖의 경우(`#` 뒤 띄어쓰기, `#`만, 정규화 실패)는 보통 검색으로 처리한다 (22 T-11, → specs/008-tag).

**검색 — 대상과 정렬 (33 §3·§4)**

- **FR-026**: System MUST 검색 대상을 공용 노출 조건(공개·발행, 휴지통 아님, 관리자 숨김 아님, 작성자 탈퇴 신청 아님)으로 한정해야 하며, 친구 공개 글은 검색에 나오지 않는다 (33 완료 기준 1, 06 §3, C-POST-4, → specs/004-visibility-permission).
- **FR-027**: System MUST 기본 정렬인 관련도순을 다음 단계 순서로 보여주어야 한다: ① 모든 단어가 제목에 있음 → ② ①이 아니고 모든 단어가 제목 또는 태그에 있음 → ③ ①②가 아니고 모든 단어가 제목·태그·본문(3글자 이상 단어만) 어딘가에 있음. 단계 안에서는 최초 공개 최신 → 글 번호 큰 순이며, 점수는 매기지 않는다 (Q-4, 33 §3-1).
- **FR-028**: System MUST 한 단계가 끝나면 같은 페이지에서 다음 단계로 이어 9개를 채워야 한다 (33 §3-1).
- **FR-029**: Users MUST be able to 정렬을 최신순(모든 단어가 어딘가에 있는 글을 최초 공개 최신순)으로 바꿀 수 있어야 한다 (33 §3-2).
- **FR-030**: System MUST 검색 결과를 9개씩 [더 보기]로 넘기며 중복·누락이 없어야 한다 (33 완료 기준 5, 33 §3-3).
- **FR-031**: System MUST 블로그 페이지 안에서 검색하면 같은 규칙에 그 블로그 주인의 글이라는 조건만 더해 검색해야 한다 (Q-7).

**검색 — 결과 표시 (33 §5)**

- **FR-032**: System MUST 글 결과를 전체 글 목록과 같은 카드로 보여주되, 미리보기 3줄 자리에 검색어가 나온 부분의 앞뒤 문장을 보여주어야 한다 (Q-6, → specs/005-post-reading).
- **FR-033**: System MUST 주변 문장을 Markdown 원문 그대로(서식 기호를 지우지 않음) 본문(본문에 없으면 제목)에서 검색어가 처음 나온 곳의 앞뒤 40자로 만들고, 앞뒤가 잘리면 `…`를 붙여야 한다 (33 §5).
- **FR-034**: System MUST 주변 문장 전체를 먼저 안전한 글자로 바꾼(이스케이프) **다음에** 검색어 부분만 강조해야 하며, 결과에 강조 표시 외의 HTML이 들어가지 않아야 한다 (Q-6, 33 완료 기준 7).
- **FR-035**: System MUST 결과가 없으면 "'{검색어}'에 대한 글이 없어요"를 (해당하면 2글자 안내와 함께) 보여주어야 한다 (33 §5).
- **FR-036**: System MUST 사람 검색어는 단어로 나누지 않고, 띄어쓰기와 맨 앞 `@`를 지운 한 덩어리(2글자 이상, 아니면 "두 글자 이상 입력해 주세요")로 닉네임·블로그 주소에서 대소문자를 무시한 부분 일치로 찾아야 한다. 결과는 프로필 사진·닉네임·`@블로그주소`·소개 첫 줄로 보여주고, 닉네임·주소가 정확히 일치하는 회원을 먼저, 탈퇴 신청한 회원은 빼고, 최대 20명까지 보여주어야 한다 (33 §5, 09 N-2, Clarifications 2026-10-08).

**검색 — 보호·기록 (33 §5, Q-8)**

- **FR-037**: System MUST 같은 방문자(회원은 회원 기준, 비회원은 방문자 식별 기준 — 조회수와 같은 식별 방식)의 검색을 1분에 30번으로 제한하고, 넘으면 429 `TOO_MANY_REQUESTS`로 거부해야 한다. 요청 횟수 저장소 장애 동안에는 제한 없이 통과시킨다 (Q-8, 31 §2-1, 02 §2-1 H8).
- **FR-038**: System MUST 검색 결과 페이지가 검색 엔진에 색인되지 않도록 표시해야 한다 (Q-8).
- **FR-039**: System MUST 검색어를 회원 정보와 함께 저장하지 않고, 운영 기록에는 검색어 길이와 걸린 시간만 남겨야 한다 (33 §5).

**사이트 지도 (sitemap, 02 SEO 행, Clarifications 2026-10-08)**

- **FR-040**: System MUST 검색 엔진용 사이트 지도(`/sitemap.xml`)를 제공해야 한다. 요청 때마다 공용 노출 조건으로 공개 글의 정규 주소와 공개 글이 1개 이상 있는 활동 회원의 블로그 주소를 만들어, 삭제·비공개·숨김·작성자 탈퇴 신청 글이 즉시 빠져야 한다. 친구 공개 글은 넣지 않는다 (06 §3 노출 표, 13 §5 C-POST-5 기준 1, 20 §5 구독 표).

### Key Entities *(include if feature involves data)*

- **트렌딩 순위 목록(스냅샷)**: 10분마다 만들어지는 상위 최대 100개 글의 순서. 만든 시각으로 식별하고 30분 동안 보관된다. 사용자의 [더 보기] 위치는 "어느 순위 목록의 몇 번째"로 표현된다.
- **트렌딩 점수 재료**: 글의 누적 좋아요 수·누적 조회 수(각 기능이 관리), 작성자를 뺀 서로 다른 댓글 작성자 수, 최초 공개 시각. 새로 저장하는 데이터는 없다.
- **검색어**: 정규화·자르기를 거친 최대 5개 단어 목록. 단어마다 길이에 따라 찾는 곳(제목·태그 / 제목·태그·본문)이 정해진다. 회원 정보와 함께 저장하지 않는다.
- **글 검색 결과 항목**: 목록 카드 정보 + 강조된 주변 문장. 관련도순에서는 단계(①②③)와 최초 공개 시각·글 번호로 이어보기 위치를 정한다.
- **사람 검색 결과 항목**: 활동 중인 회원의 프로필 사진·닉네임·블로그 주소·소개 첫 줄.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 글 10만 개에서 검색 응답의 95%가 500ms 이내다 (33 완료 기준 8, 김민서 PERF-6). 설계 검증에서는 최악 101ms였다 (33 §8-2).
- **SC-002**: 트렌딩 요청 응답의 95%가 200ms 이내이며, 요청 때 전체 순위 계산을 하지 않는다 (32 완료 기준 4, PERF-5).
- **SC-003**: 비공개·친구 공개·휴지통·관리자 숨김·탈퇴 신청 작성자의 글이 트렌딩·검색 결과에 나오는 경우가 0건이다 (32 완료 기준 1, 33 완료 기준 1).
- **SC-004**: 트렌딩·검색 모두 [더 보기]를 끝까지 넘겼을 때 중복·누락이 0건이다 (보는 도중 순위가 바뀌거나 글이 비공개로 바뀌는 경우 포함).
- **SC-005**: 본문에 HTML·스크립트가 들어 있는 글을 검색해도 결과 화면에서 실행되는 스크립트가 0건이다.
- **SC-006**: 순위는 10분 간격으로 갱신되어, 새로 반응을 받은 글이 늦어도 10분 안에 순위에 반영된다.
- **SC-007**: 순위 보관소가 멈춘 동안에도 트렌딩 탭을 연 사용자는 (반응이 있는 글이 있으면) 빈 화면을 보지 않는다.

## Assumptions

- **Tier C 기능이다.** 01 §2-3에서 검색·트렌딩은 "공통 2차 후보"이며 화면·기능 구현 순서는 1차 공통이 끝난 뒤 다시 정한다. 검색 전용 저장 구조(부분 일치 색인)는 통합 V1에 이미 들어 있다.
- 공용 노출 조건(공개·발행·휴지통 아님·숨김 아님·작성자 탈퇴 신청 아님)은 specs/004-visibility-permission이 정의하고, 이 기능은 그대로 재사용한다. 숨김 규칙은 specs/014-report-hide, 탈퇴 유예 규칙은 specs/015-withdraw를 따른다.
- 목록 카드·9개씩·[더 보기]·날짜 형식·뒤로 가기 복원은 specs/005-post-reading, 좋아요·조회 수의 중복 제거는 specs/009-like-view, 태그 정규화와 `#태그` 이동은 specs/008-tag를 따른다.
- 트렌딩의 순위 보관소 장애 시 즉시 계산은 원문이 "(임시)"로 둔 대체 경로이며, 그대로 기본값으로 채택한다 (32 T-9, 02 §2-1 "각 문서의 대체 경로").
- 사람 탭의 검색어도 글 검색과 같은 정리 규칙(정규화·자르기)을 쓴다고 본다. 원문은 사람 탭에 단어 길이 규칙을 따로 적지 않았다.
- 검색 시 "최근 글 몇 개 안에서 먼저 찾는" 범위(기본 3,000)는 성능을 위한 설정값이며, 실제 데이터가 쌓이면 다시 재서 조정한다 (33 §4). 결과 순서에는 영향이 없다.
- **개인 확장(범위 밖)**: 트렌딩의 오늘/주/월 탭, 사이드바 인기 글 5개, 첫 글·새 작가 탭, 주제·태그별 트렌딩 (T-11). 검색의 기간·주제 조건, 의미·하이브리드 검색, 자동 완성, 인기 검색어, 다른 검색 엔진 (Q-9).
- 트렌딩 점수식 B("최근 반응" 방식) 전환은 범위 밖이며, 일별 조회 기록은 그 대비로만 유지된다 (T-10).
- 검색 테스트 데이터는 같은 문장을 반복해 만든 것이므로, 구현 후 실제와 비슷한 데이터로 성능을 다시 잰다 (33 §8).

## Implementation Notes (for /speckit-plan)

원문의 기술 결정 요약. 상세는 링크한 절을 본다.

**트렌딩**

- 계산 쿼리: [32 §3-1](../../docs/32-trending.md) — `post`(`like_count`, `view_count`, `first_public_at`) + 글마다 `count(DISTINCT comment.author_id)`(작성자 제외, `deleted_at IS NULL`), `row_number() OVER (PARTITION BY author_id)`로 작성자당 3개, `LIMIT 100`. 대상 조건은 06 §7 공용 조건(`VisibilityFilter`)을 그대로 쓴다(2026-10-07 회의 H1로 `hidden_at IS NULL` 포함). 범위는 `ix_post_feed`로 좁힌다.
- 스냅샷: [32 §3-2](../../docs/32-trending.md) — 10분마다 ShedLock으로 한 서버에서 실행, Redis `RPUSH trending:{스냅샷ID}` + `EXPIRE 1800`, `SET trending:current {스냅샷ID}`. 스냅샷 ID는 `yyyyMMddHHmm`.
- API: [32 §4](../../docs/32-trending.md) — `GET /api/posts/trending?cursor=…&size=9`. 원문 커서는 `{스냅샷ID}:{위치}`이나, 2026-10-07 회의 O8과 [10 §4-2](../../docs/10-post-list.md)에 따라 불투명 Base64URL JSON(`snap` 필드 추가)으로 감싼다. 스냅샷 만료 시 `410 SNAPSHOT_EXPIRED`. 글은 `LRANGE` 후 SQL 1번으로 카드 컬럼 조회(10 §7). Redis 장애 시 §3-1을 바로 실행하고 `nextCursor: null`.
- 화면 주소 `/?tab=trending` ([32 §5](../../docs/32-trending.md)).
- 스키마 변경 없음. 글이 많아지면 `ix_comment_post_author ON comment (post_id, author_id) WHERE deleted_at IS NULL` 검토(지금은 넣지 않음, [32 ERD 변경 제안](../../docs/32-trending.md), 51 §4).
- `post_view_daily`는 트렌딩이 아니라 작성자 통계 + 점수식 B 대비로 유지 (T-10, 31 W-7).

**검색**

- 인덱스: [33 §6](../../docs/33-search.md) — `pg_trgm` 확장 + GIN `ix_post_title_trgm`, `ix_post_content_trgm`, `ix_member_nickname_trgm`, `ix_member_handle_trgm` (통합 V1 [51 §3](../../docs/51-erd-unified.md)에 포함). trigram은 3글자 단위라 2글자 검색어는 인덱스를 못 쓴다(Q-2 근거). `CREATE EXTENSION`은 DB 관리자 권한이 필요할 수 있다(배포 확인).
- 실행: [33 §4](../../docs/33-search.md) — 단계마다 ① 최근창(`blog.search.recent-window=3000`) 안에서 10개(9 + 다음 확인용 1) → ② 모자라면 가장 긴 단어로 제목·태그·본문 후보를 각각 인덱스 조회해 `UNION` 후 전체 조건 확인. 태그 `EXISTS`를 `OR`에 섞으면 본문 인덱스를 못 써 1,129ms가 걸렸다(§8).
- 매칭: `ILIKE` + `%`·`_`·`\` 이스케이프, 본문은 `content_md`. 블로그 안 검색은 `AND p.author_id = :blogOwner`.
- API: [33 §5](../../docs/33-search.md) — `GET /api/search/posts?q=…&sort=relevance|latest&cursor=…`, `GET /api/search/people?q=…`, 블로그 안 검색 `/@{handle}?q=…`. 응답에 `snippetHtml`, `notice: "TWO_CHAR_TITLE_TAG_ONLY"`. 원문 커서 `{단계}:{first_public_at}:{id}`는 O8 불투명 커서로 감싼다. 원문의 "`GET /search` 화면 (SSR)"은 2026-10-07 회의 H7(화면 React + REST)로 React 화면 주소로 읽는다.
- 요청 제한: 방문자 키는 [31 §2-1](../../docs/31-view-count.md)(`m:`/`v:`/`h:`), 1분 30번 초과 시 429. Redis 장애 시 통과([02 §2-1](../../docs/02-architecture.md)).
- 검색 결과 페이지 `<meta name="robots" content="noindex">`.
- 검색 색인 갱신 등에 쓸 이벤트: `PostWentPublic`, `PostEdited`, `PostVisibilityChanged`, `PostTrashed`·`Restored`·`Purged`, `ContentHidden`·`Unhidden` ([20](../../docs/20-domain-events.md) 맞출 것 표).
- 성능 측정 근거: [33 §8](../../docs/33-search.md), [32 §6](../../docs/32-trending.md).
